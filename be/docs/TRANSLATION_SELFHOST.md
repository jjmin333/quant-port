# 해외 뉴스 제목 번역 — Papago 대체 설계

> 상태: **구현 완료** (2026-09-03). 이 문서는 제안서에서 **기록**으로 바뀌었다 —
> 실제로 무엇을 골랐고 무엇이 제안과 달랐는지는 §0에 있다.
> 작성 2026-09-02. 관련 코드: `be/internal/service/news_translate.go`,
> `be/internal/marketdata/papago.go`, `be/docs/api-quotas.md`.

## 0. 실제로 무엇이 됐나 — 제안과 달라진 두 가지

### ① 모델은 0.6B가 아니라 **1.7B**다

설계서는 T1(0.6B)로 시작해 모자라면 올린다고 적었다. 실측에서 **0.6B가 회사 이름을
지어냈다** — 배치라 초 단위 차이가 값이 아닌데, 틀린 번역은 값이다:

| 원문 | 0.6B | 1.7B |
|---|---|---|
| Nvidia stock slips as investors weigh AI spending outlook | **에버넷의** 주가가 하락 | **엔비디아** 주가 하락 |
| Fed holds rates steady amid inflation concerns | Fed **금리 인상**은 … 안정 | Fed, … **금리 안정 유지** |
| Broadcom beats earnings estimates … | **보트콤**은 … 예측을 깨고 | **브로드컴**, … 예상치를 뛰어넘어 |

속도는 **오히려 비슷했다**(0.6B 988~1,615ms / 1.7B 856~1,158ms, 같은 문장).

### ② 「이름 잠그기」를 새로 넣었다 — 이게 없으면 못 쓴다

1.7B도 이름을 틀린다. 그리고 그 틀림은 **§4의 어떤 검사로도 안 잡힌다**:

> Jim Cramer has a strong message for **Nvidia** stock investors
> → 짐 크라머가 **인텔** 주식 투자자들에게 강한 메시지를 보냈다

문장은 자연스럽고 길이도 맞고 한글도 있다. **엔비디아 기사가 인텔 기사가 되는 것**은
번역 품질 문제가 아니라 사실의 문제다.

그래서 이름은 모델에게 맡기지 않는다. 그 기사에 어떤 종목이 붙어 있는지 우리가 이미
알고(태깅 파이프라인) 한국어 이름도 카탈로그에 있으므로, 모델에는 **자리표시자**를
주고 그 자리에 우리가 아는 이름을 넣는다(`internal/translate/names.go`).
자리표시자 모양은 실측으로 골랐다 — `@@1@@`는 사라지고, `Kv1`은 대문자화되고,
`$QPZ0`는 그대로 살아남는다.

### 실측 비교 (2026-09-03, 저장된 Papago 번역 20건 대 자체 모델)

```
go run ./cmd/compare-translation -n 20 -csv out.csv
```

**Papago를 지금 부를 수 없다 — NCP 자격증명이 만료돼 401을 낸다.** 그래서 DB에 이미
쌓인 `headline_ko`(키가 살아 있던 동안 Papago가 남긴 값)와 비교했다. 비교 명령은
`updated_at`이 하루 넘은 행만 본다 — 최신 행은 자체 모델이 방금 넣은 것이라 그대로
쓰면 **자기 자신과 비교**하게 된다(실제로 처음에 그렇게 나왔다).

읽어 본 결과: **Papago가 더 나은 것 6~7건, 자체 모델이 나은 것 1~2건, 나머지 비슷.**
자체 모델이 나은 예는 Papago가 "Post Q2 Earnings"의 Post를 **포스트 홀딩스**로 읽은
건이었고, 나쁜 예는 대부분 **낱말 하나**였다(rates→요금, bear market→암울한 시장,
student loan→학생 대출, midday→중간, retreat→회귀). 그 낱말들은 `glossary.go`의
조건부 규칙으로 좁혔다 — 규칙마다 「원문에 이 영어 표현이 있을 때만」이 붙는다.

속도는 **건당 1.8~2.8초**(2 스레드). 하루 200건이면 6~9분이고, 2분마다 24건씩
흩어지므로 체감되는 지연이 없다.

### ③ Papago를 **코드에서 걷어냈다**

Papago 키가 죽은 뒤 **최근 3일 해외 기사의 14.2%(509건)가 번역 없이 쌓여 있었다.**
자체 모델은 비용 절감이 아니라 지금 유일하게 도는 번역기다.

**키를 갱신하지 않기로 했으므로**(사용자 결정, 09-03) 폴백으로 남겨 두지 않고 지웠다:

| 지운 것 | 자리 |
|---|---|
| `marketdata.PapagoClient` | 텍스트·웹 번역 클라이언트 |
| `translate.Papago` | 사슬의 두 번째 엔진 |
| `config.PapagoConfig` · `PAPAGO_CLIENT_*` | 설정 |
| `apibudget`의 `papago_text`·`papago_web`·`papago` | 할당량 항목 셋 |
| `NewsReaderService.translateUSReader` | 리더 본문 번역 |

**폴백이 없다는 뜻이다.** 자체 모델이 실패하거나 검증(§4)을 통과하지 못한 제목은
**영어로 남는다** — 목록에서 사라지는 것이 아니라 원문 그대로 나온다. 화면은
「번역이 안 된 기사」와 「원래 영어인 기사」를 구분해 보여 주지 않으므로,
그 건수는 `translate.Chain.Snapshot()`의 Rejected로만 알 수 있다. 그 수가 조용히
올라가는 것이 이 구조에서 유일하게 위험한 상태다.

**이미 저장된 리더 본문 번역은 그대로 쓴다** — Papago가 살아 있을 때 만든 진짜
번역이라 버릴 이유가 없다. 새로 만들지 않을 뿐이다(`loadStoredTranslation`).
리더 본문을 자체 모델로 옮기지 않는 이유는 §1에 있다 — 제목은 배치라 몇 초가
걸려도 되지만 본문은 사람이 기다리고 기사 한 건이 2,000단어다.

## 1. 지금 무엇을 번역하고 있나

두 가지인데 **성격이 완전히 다르다.** 이 문서가 다루는 것은 앞의 하나뿐이다.

| 대상 | API | 호출 방식 | 하루 물량 | 지연 허용 |
|---|---|---|---|---|
| **기사 제목** | `papago_text` | 2분마다 백필 24건 (`runUSTranslationBatch`) | 신규 **100–200건** | **무제한** — 배치다 |
| 리더 본문 | `papago_web` | 사용자가 리더를 열 때 1회 | 50–200건 | 사람이 기다린다 |

제목은 **배치**다. 사용자가 기다리는 것이 아니라 폴러가 2분마다 24건씩 밀어 넣고,
번역이 붙기 전 기사는 목록에 아예 나오지 않는다(`isUSTranslationReady`). 그래서
**한 건에 5초가 걸려도 아무 문제가 없다** — 200건 × 5초 = 하루 17분이고, 그 17분은
2분 간격으로 흩어진다.

이 사실이 모델 선택을 결정한다. 실시간 번역기를 만드는 것이 아니므로 "작고 빠른"
모델을 고를 이유가 없고, **같은 자원으로 가장 잘 번역하는 것**을 고르면 된다.

본문은 반대다. 사람이 화면을 보며 기다리고, HTML 구조를 보존해야 하며, 기사 한
건이 2,000단어다. ARM 2코어에서 소형 LLM으로 돌리면 **분 단위**가 걸린다.
→ **본문은 이 제안의 범위 밖**이다. 지금은 **번역하지 않고 원문을 보여준다**(§0-③).

## 2. 제약 — 이 박스에서 돌아야 한다

`docs/PERFORMANCE_DESIGN.md`와 같은 전제다.

- **VM.Standard.A1.Flex — 2 OCPU (ARM64 Ampere), 12 GiB.** GPU 없음.
  x86 전용 바이너리·이미지는 **후보에서 탈락**한다.
- 이 박스에는 이미 API(상한 1 GiB) · Redis · 배치 워커 8개가 산다.
- **배치 전용 인스턴스(2 OCPU / 12 GiB)가 예정**돼 있다. 번역기는 배치라서
  그쪽이 제자리다 — API와 같은 박스에 두면 번역 버스트가 살아 있는 요청과 CPU를
  다툰다.
- 라이선스는 **상업적 이용이 가능해야 한다.**
  → `facebook/nllb-200-distilled-600M`은 품질이 좋지만 **CC-BY-NC 4.0(비상업)**이라
  이 자리에서 탈락한다. 흔히 첫 후보로 꼽히므로 먼저 적어 둔다.

## 3. 구조

번역기를 **별도 컨테이너의 HTTP 서비스**로 두고, Go 쪽은 인터페이스 하나만 본다.
지금 `NewsStore`가 `st.papago`를 직접 들고 있는 것이 문제다 — 구현을 바꾸려면
호출부를 고쳐야 하고, 두 구현을 나란히 돌려 비교할 수가 없다(§4의 그림자 운영이
불가능하다).

```
be/internal/translate/
  translator.go   Translator 인터페이스 + 결과 검증
  papago.go       기존 PapagoClient 어댑터
  local.go        translator 컨테이너 HTTP 클라이언트
  chain.go        1순위 → 2순위 폴백
  glossary.go     금융 용어 사전 (fixUSStockTranslation이 여기로 옮겨 온다)
```

```go
// 한 건이 아니라 묶음을 받는다. 배치 24건을 한 번에 넘기면 모델을 매번
// 깨우지 않고, 컨테이너가 KV 캐시와 배치 처리를 알아서 쓴다.
type Translator interface {
    Name() string
    TranslateENtoKO(ctx context.Context, texts []string) ([]string, error)
}
```

`chain.go`는 **1순위가 실패하거나 §4의 검증을 통과하지 못하면 2순위로 내려간다.**
설정으로 순서를 바꾼다:

```
TRANSLATE_PROVIDER=local        # local | papago | local,papago(폴백) | papago,local
TRANSLATE_LOCAL_URL=http://translator:8100
```

컨테이너 쪽 계약은 최소한으로 한다 — 나중에 모델을 갈아 끼워도 Go를 안 고치게.

```
POST /translate  {"texts": ["...", "..."], "src": "en", "tgt": "ko"}
  → 200 {"texts": ["...", "..."], "model": "lmt-60-0.6b-q5_k_m", "ms": 1840}
GET  /health     → 200 {"ok": true, "model": "...", "loaded": true}
```

docker-compose에 `translator` 서비스를 추가하고 `deploy.resources.limits.memory`를
모델에 맞춰 못 박는다. **API 컨테이너와 같은 실수를 반복하지 않는다** — 상한을
안 주면 cgroup 상한에 부딪혀 OOM 킬을 당하고, 그러면 번역이 조용히 멈춘다.

## 4. 품질을 지키는 세 겹

MT를 그대로 믿으면 안 된다는 증거가 이미 코드에 있다 — `fixUSStockTranslation`은
Papago가 "stock"을 **"재고"**로 옮겨서 생긴 함수다. 모델을 바꾼다고 이 문제가
사라지지 않는다. 종류만 달라진다.

**(1) 엔티티 마스킹.** 티커·회사명을 번역 전에 자리표시자로 바꾸고 후에 되돌린다.
`Micron`이 "마이크론"이 되는 것은 좋지만 `MU`가 "무"가 되면 안 된다. 우리는 기사에
붙은 `symbols`와 `stocks` 카탈로그의 한글명을 이미 들고 있으므로, **번역기에게
맡기지 말고 우리가 아는 이름으로 직접 박아 넣는다.**

**(2) 용어 사전.** `glossary.go`로 옮기고 목록을 키운다. 지금은 재고→주식 하나뿐이다.

**(3) 받아들이기 전 검증.** 이 셋 중 하나라도 걸리면 그 번역을 버리고 폴백한다.

- 한글이 한 글자도 없다 (번역이 안 됐다)
- 원문 대비 길이가 2.5배를 넘거나 0.3배 미만이다 (환각·잘림)
- 같은 어절이 4회 이상 반복된다 (소형 LLM의 전형적인 실패 양상)

검증에 걸린 건수는 메트릭으로 남긴다. **이 수가 올라가면 모델이 나빠진 것이고,
그것을 모르면 화면에 이상한 제목이 조용히 쌓인다.**

## 5. 모델 후보

셋 다 ARM64 CPU에서 돌고, 라이선스가 상업적 이용을 허용하며, 컨테이너 하나에 들어간다.
속도는 **2 OCPU 기준 추정치**다 — 도입 전에 실측해야 한다(§7).

### T1 · LMT-60-0.6B — 권장

- **무엇**: NiuTrans의 번역 전용 모델. Qwen3-0.6B-Base 위에 60개 언어 234개 방향으로
  학습했고 한국어가 포함된다. **Apache-2.0.**
- **왜 이것인가**: 범용 채팅 모델이 아니라 **번역만 하도록 만든 모델**이다. 제목
  번역에서 소형 범용 LLM이 자주 하는 짓 — 설명을 덧붙이거나, "번역: "을 앞에 달거나,
  원문을 그대로 뱉는 것 — 이 구조적으로 덜하다.
- **자원**: llama.cpp GGUF Q5_K_M ≈ 550 MB. 컨테이너 상한 **1 GiB**면 충분.
- **속도(추정)**: 제목 한 건 1.5–3초. 하루 200건 ≈ **10분**.
- **위험**: 0.6B는 작다. 긴 제목이나 말장난이 섞인 헤드라인에서 무너질 수 있다.
  §4의 검증이 그때 Papago로 내려보낸다.

### T2 · LMT-60-1.7B — 품질이 모자랄 때

같은 계열의 한 단계 위. Q4_K_M ≈ 1.1 GB, 컨테이너 상한 2 GiB.
속도 추정 4–7초/건 → 하루 200건 ≈ **20분**. **여전히 배치로는 아무 문제가 없다.**
T1으로 시작해 §7의 비교에서 부족하면 여기로 올린다 — 컨테이너 환경변수 하나다.

### T3 · opus-mt-en-ko (CTranslate2 int8) — 가장 가볍지만

- 77M 파라미터, int8 ≈ 120 MB, 제목당 **100 ms 미만**. 컨테이너 상한 512 MiB.
- 문제는 품질이다. OPUS의 en→ko 말뭉치가 얇아 금융 헤드라인에서 약하다.
- **자원이 정말 없을 때의 답**이지 지금 우리 상황의 답은 아니다. 하루 200건에
  10분을 쓸 여유가 있는데 품질을 깎을 이유가 없다.

### 탈락

| 모델 | 이유 |
|---|---|
| `nllb-200-distilled-600M` | **CC-BY-NC 4.0 — 비상업 전용** |
| `EXAONE-3.5-2.4B` | 한국어는 강하나 라이선스 확인 필요 + 범용 모델이라 T1보다 무겁고 통제가 어렵다 |
| `madlad400-3b-mt` | 품질은 좋지만 3B가 이 박스에서 배치 창을 너무 오래 잡는다 |
| 7B 이상 전부 | 2 OCPU ARM에서 제목 한 건에 30초 이상 |

## 7. 도입 순서

**전환 전에 두 번역을 나란히 놓고 사람이 본다.** 이건 생략할 수 없다 — MT 품질은
지표로만 보면 멀쩡한데 화면에서 읽으면 이상한 경우가 흔하다.

1. `be/internal/translate/` 패키지와 `Translator` 인터페이스를 만들고, **Papago를
   그 뒤로 옮긴다.** 이 단계에서 동작은 하나도 안 바뀐다.
2. `translator` 컨테이너를 T1으로 띄우고 `/health`까지 확인.
3. **그림자 운영**: 최근 US 기사 300건을 두 엔진으로 번역해 CSV로 뽑는다
   (`cmd/compare-translation`). 화면에는 아무 영향이 없다.
4. 그중 50건을 사람이 읽고 판정한다 — 셋 중 하나로: 같음 / 자체 모델이 나음 /
   Papago가 나음. **Papago가 나은 것이 20%를 넘으면 T2로 올린다.**
5. 실측치를 이 문서에 적는다 — 제목당 초, 컨테이너 RSS, 검증 실패율.
6. `TRANSLATE_PROVIDER=local,papago`로 전환. 메트릭을 일주일 지켜본다.
7. 검증 실패율이 낮으면 `TRANSLATE_PROVIDER=local`로 Papago를 끊는다.

되돌리기는 **환경변수 하나**다(`TRANSLATE_PROVIDER=papago`). 그것이 이 구조의 값어치다.
