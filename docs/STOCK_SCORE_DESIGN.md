> 작성일: 2026-08-08 · **상태: 설계안 (미구현)**

## 1. 문제 정의 — 현행 점수는 "종합 점수"가 아니다

`daily_close_score.go`의 현행 가중치:

| 구성 | 비중 | 성격 |
|------|------|------|
| RSI(14) | 30% | 기술 |
| 추세 (종가 vs SMA20/50) | 25% | 기술 |
| MACD vs 시그널 | 20% | 기술 |
| 뉴스 감성 | 15% | 심리 |
| 52주 밴드 내 위치 | 10% | 기술 |

**기술적 지표가 85%**다. 밸류에이션·재무·실적·내부자는 한 글자도 들어가 있지 않다. 그런데 화면에는 "점수"라는 중립적 이름으로 노출된다.

더 심각한 건 **결측 시 재정규화와 결합했을 때의 실제 동작**이다. 아래 §2.3에서 실측하듯 전체 종목의 대부분은 일봉이 35~59개뿐이라 `SMA50`·`52주 위치`를 계산할 수 없다. 그 종목들에서 현행 점수는:

```
RSI(30%) + MACD(20%) → 재정규화 → RSI 60% + MACD 40%
```

즉 **대다수 종목의 "종합 점수"는 사실상 RSI 점수**다. 사용자가 재무가 탄탄한 종목의 낮은 점수를 보고 납득하지 못하는 건 당연하다. 이것이 "터무니없다"의 1차 원인이다.

## 2. 실측 — 설계를 결정한 데이터 (2026-08-08 기준)

임계값을 추측으로 정하면 반드시 터무니없는 점수가 나온다. 실제 DB를 측정한 결과가 설계의 근거다.

### 2.1 커버리지 (활성 종목 17,901개)

| 축 | 계산 가능 종목 | 비율 | 원천 |
|----|---------------|------|------|
| 가격 (종가) | **8,714** | 49% | `stock_daily_closes` |
| 수익성 (ROE·영업이익률·부채비율 중 1개 이상) | **6,617** | 37% | `stock_fundamentals` |
| 수익성 (3개 전부) | 4,376 | 24% | 〃 |
| 성장 (매출 or EPS YoY) | **6,843** | 38% | 〃 |
| PSR | 2,872 | 16% | 종가 × 주식수 / 매출 |
| PBR | 2,841 | 16% | 종가 × 주식수 / 자본 |
| **PER** | **1,271** | **7%** | 종가 / EPS |

> **가격 원천을 바꿔야 한다.** `symbol_last_prices`는 1,157행뿐이라 PER 계산 가능 종목이 263개에 그친다. 이번 세션에 적재한 `stock_daily_closes`(8,714종목)를 가격 원천으로 쓰면 PER 263→1,271, PBR 513→2,841로 늘어난다. 점수 배치는 `symbol_last_prices`가 아니라 `stock_daily_closes`를 봐야 한다.

**PER 커버리지 7%는 밸류에이션을 필수 축으로 둘 수 없다는 뜻이다.** 가치 축은 선택적·커버리지 게이트 대상이다.

### 2.2 분포 — 절대 임계값이 불가능한 이유

| 지표 | p5 | p25 | p50 | p75 | p95 | min | max |
|------|-----|-----|-----|-----|-----|-----|-----|
| ROE (%) | -196 | -24.2 | **3.25** | 13.7 | 140 | -14,957 | **227,162** |
| 영업이익률 (%) | -1,887 | -25.4 | **1.92** | 11.4 | 40.0 | **-2,112,685** | 28,699 |
| 부채비율 (%) | -345 | 18.3 | **74.1** | 196 | 972 | -7,169,000 | 306,700 |
| 매출 YoY (%) | -74.3 | -6.0 | **4.34** | 18.4 | 158 | -393 | 1,631,667 |
| EPS YoY (%) | -461 | -47.5 | **9.38** | 66.9 | 348 | -128,837 | **2,276,367,794** |

`ROE 227,162%`, `EPS 성장률 22억%`. 자본잠식 직전의 미세한 분모, 껍데기 회사, 단위 혼입이 만드는 값들이다.

**"ROE 15% 이상이면 만점" 같은 절대 기준을 쓰면 이 종목들이 전부 만점을 받는다.** 순위(백분위) 기반 정규화 + 윈저라이즈가 선택이 아니라 필수인 이유다.

### 2.3 기술적 지표 — 일봉 개수 계단

| 일봉 수 | 종목 수 | 계산 가능한 지표 |
|---------|---------|-----------------|
| < 15 | 19 | 없음 |
| 15–34 | 130 | RSI(14) |
| **35–59** | **7,477** | RSI · MACD · SMA20 |
| 60–199 | 27 | + SMA50 |
| 200+ | 1,065 | + SMA200 · 52주 밴드 |

7,477종목이 35~59개 구간에 몰린 건 이번 백필이 종목당 40개를 받아온 결과다. 시간이 지나면 개선되지만, **52주 밴드·SMA200은 앞으로 수개월간 사실상 사용 불가**다. 이걸 전제로 설계해야 한다.

### 2.4 배치 계산 불가능한 데이터

| 데이터 | 왜 불가능한가 |
|--------|--------------|
| **내부자 거래** | `InsiderTabService`가 DART/EDGAR **라이브 호출**(24h 캐시). EDGAR는 분당 8회를 앱 전체가 공유 — 17,901종목 배치 불가 |
| **뉴스 감성** | LLM이 기사별 라벨링. 전 종목 = LLM 비용 폭발. `news_articles`에 **감성 컬럼 자체가 없음**(실측: 컬럼 목록에 sentiment 없음) |
| **분기 실적 히스토리** | `FinancialHistoryService`도 DART 라이브 호출 |

> `DAILY_CLOSE_DESIGN.md` §6 초안은 내부자를 10% 가중 축으로 두었으나, **이 데이터는 배치로 존재하지 않는다.** 가중 축으로 두면 전 종목에서 결측 → 재정규화되어 사실상 무의미해진다. 본 설계는 이를 **온디맨드 보정**으로 분리한다.

### 2.5 섹터 데이터 없음

`information_schema` 전수 조사 결과 **섹터/업종 컬럼이 어느 테이블에도 없다.** (검색에 걸린 `eps_basic`은 `%sic%` 패턴의 오탐)

PER 40은 반도체에서 평범하고 은행에서 비정상이다. 섹터 없이 전체 유니버스를 한 줄로 세우면 밸류에이션 점수는 사실상 "업종 판별기"가 된다. §8에 조달 방법을 정리했다.

### 2.6 ETF

`ARCX/BATS/NASDAQ/OOTC` 등 `asset_type='etf'` 종목이 **4,306개**. `model.IsFundamentalsApplicable`이 이미 false를 반환한다. 재무 축이 원천적으로 없으므로 일반 종목과 같은 라벨의 점수를 주면 안 된다.

## 3. 설계 원칙

1. **순위(백분위) 정규화** — 절대 임계값 금지. §2.2의 꼬리값이 이유
2. **결측은 0점이 아니다** — 비중에서 제외 후 재정규화 (현행 유지)
3. **그러나 재정규화만으로는 부족하다** — 커버리지가 낮으면 중립(50)으로 수축시킨다 (§5.2). 재정규화만 하면 "RSI만 있는 종목이 95점"이 나온다
4. **점수는 서버가 계산한다** — LLM은 문장만. 기존 원칙 유지 (`daily_close_score.go` 주석 참조)
5. **단일 숫자를 단독 노출하지 않는다** — 5개 서브스코어·백분위·커버리지를 항상 함께 (§6)
6. **배치 축과 온디맨드 축을 분리한다** — §2.4

## 4. 정규화 방법

### 4.1 피어 그룹

섹터가 없으므로 현재 가능한 최선:

```
피어 그룹 = (asset_type, market) × 시가총액 3분위
```

- `market`: KRX / KOSDAQ / KONEX / NASDAQ / NYSE / AMEX …
- 시가총액 = 종가(`stock_daily_closes`) × `COALESCE(f.shares_outstanding, s.shares_outstanding)` — **오늘 바로 계산 가능**(6,976종목이 주식수 보유)
- 그룹 최소 표본 **30** 미만이면 상위 그룹(market 전체 → asset_type 전체)으로 폴백

시가총액 분위를 넣는 이유: 대형주와 마이크로캡은 PBR·부채비율 분포가 전혀 다르다. 섹터가 없는 상태에서 얻을 수 있는 가장 효과적인 보정이다.

### 4.2 지표 → 0~100

```
1. 윈저라이즈: 피어 그룹 내 p1 / p99 로 클리핑     ← ROE 227,162% 제거
2. 순위 백분위: pct = rank / (n-1) × 100
3. 방향 정렬: 낮을수록 좋은 지표(PER·PBR·PSR·부채비율)는 100 - pct
```

순위를 쓰는 이유:
- 정의상 0~100에 갇힘 → 폭주 불가능
- 이상치에 완전 면역 (227,162%든 1조%든 "1등"일 뿐)
- 유니버스가 바뀌어도 자동 재보정
- **사용자에게 설명 가능**: "코스피 대형주 중 상위 18%"

### 4.3 성장률의 함정 — 음수 기저

EPS가 -10 → +1 이면 "+110% 성장"으로 계산된다. 의미 없는 값이다.

```
직전 기저 ≤ 0 이면 → 해당 성장 지표를 "결측"으로 처리 (큰 양수 금지)
```

§2.2의 `EPS YoY max = 22억%`가 정확히 이 경로로 생긴 값이다.

## 5. 축 정의와 합성

### 5.1 5축

| 축 | 기본 비중 | 입력 (전부 배치 가능) | 커버리지 |
|----|----------|---------------------|---------|
| **추세** (Technical) | 30% | RSI14 · MACD · SMA20/50 · 52주 위치 (`candle_bars`) | 8,679 |
| **수익성** (Quality) | 25% | ROE · 영업이익률 · 순이익률 · 부채비율↓ · 유동비율 | 6,617 |
| **성장** (Growth) | 20% | 매출 YoY · EPS YoY (§4.3 가드 적용) | 6,843 |
| **가치** (Valuation) | 15% | PER↓ · PBR↓ · PSR↓ (종가 × 주식수 기반) | 1,271~2,872 |
| **심리·수급** | 10% | 뉴스 감성 · 내부자 순매수 — **온디맨드 전용** | 극소 |

각 축은 내부 지표들의 **가용한 것만 평균**한다. 축 내부에서도 결측은 제외한다.

**추세 축은 일봉 수에 따라 단계적으로 구성한다** (§2.3):

| 일봉 | 추세 축 구성 | 축 신뢰도 |
|------|-------------|----------|
| < 15 | 축 자체 결측 | — |
| 15–34 | RSI만 | 0.5 |
| 35–59 | RSI · MACD · SMA20 대비 | 0.8 |
| 60+ | + SMA50 추세 | 1.0 |
| 200+ | + 52주 위치 | 1.0 |

축 신뢰도는 §5.2의 커버리지 계산에 그대로 곱해 들어간다. 현행처럼 "RSI만 있는데 만점"이 나오지 않게 하는 장치다.

### 5.2 합성 — 커버리지 수축 (핵심)

```go
raw      = Σ(wᵢ · sᵢ) / Σ(wᵢ)            // 가용 축만
coverage = Σ(wᵢ · confᵢ) / Σ(전체 wᵢ)    // conf = 축 신뢰도
shrink   = min(1.0, coverage / 0.60)
final    = 50 + (raw − 50) × shrink
```

동작 예시:

| 상황 | coverage | raw | final |
|------|----------|-----|-------|
| 5축 전부 있음 | 1.00 | 82 | **82** |
| 추세+수익성+성장 (재무 있음) | 0.75 | 82 | **82** |
| 추세만, 일봉 40개 | 0.30×0.8=0.24 | 90 | **66** |
| 추세만, 일봉 20개 | 0.30×0.5=0.15 | 90 | **60** |

**"RSI 하나로 90점"이 구조적으로 불가능해진다.** 이것이 §1에서 지적한 신뢰 붕괴의 직접적 해법이다.

하드 게이트:

```
coverage < 0.20  →  점수 NULL, "데이터 부족" 표기 (현행 '-' 유지)
```

### 5.3 온디맨드 보정 (심리·수급)

배치 점수 계산 후, 해당 종목을 실제로 조회할 때만:

```
final += clamp(뉴스감성 보정, -5, +5) + clamp(내부자 보정, -5, +5)
```

- 뉴스 감성: `NewsSentimentSummary.AverageScore`(-100~100) → ±5
- 내부자: 최근 30건 순매수 비율 → ±5
- **합계 ±10을 넘지 않는다.** 라이브 API 성공 여부에 따라 점수가 크게 흔들리면 안 된다
- 보정 적용 여부를 응답에 명시 (`adjustments: {news: +3, insider: -1}`)

### 5.4 ETF

`IsFundamentalsApplicable == false` → 재무 3축 원천 결측. 커버리지 0.30 상한에 걸려 자동으로 수축되지만, **라벨을 분리한다**: `scoreKind: "technical_only"`. FE는 "추세 점수"로 표기하고 종합 점수와 같은 자리에 놓지 않는다.

## 6. 표기 — 사용자가 받아들이게 만드는 부분

숫자 하나만 던지면 반드시 거부당한다. 함께 노출할 것:

```
종합 76점  (B+)
KOSPI 대형주 2,409종목 중 상위 14%
데이터 커버리지 ●●●●○ 75%

추세    ████████░░ 71
수익성  █████████░ 88
성장    ██████░░░░ 62
가치    ████░░░░░░ 44
심리    — (데이터 없음)
```

### 6.1 등급 밴드

| 점수 | 등급 |
|------|------|
| 80+ | A+ |
| 70–79 | A |
| 60–69 | B+ |
| 50–59 | B |
| 40–49 | C+ |
| 30–39 | C |
| < 30 | D |

합성 점수는 여러 균등분포의 가중합이라 중심극한정리로 **평균 50 부근의 종형**이 된다(§7.1에서 검증 필수). 따라서 A+(80점 이상)는 대략 상위 2~3%가 되어 등급이 의미를 갖는다.

### 6.2 등급 히스테리시스

점수가 79↔80을 오가며 등급이 매일 바뀌면 신뢰를 잃는다.

```
등급 변경은 밴드 경계를 2점 이상 넘어설 때만 (A→A+ 는 82 이상, A+→A 는 78 이하)
```

### 6.3 하지 말 것

- **소수점 표기 금지** — `76.4점`은 없는 정밀도를 주장한다
- **"매수/매도" 문구 금지** — 점수는 상태 진단이지 행동 지시가 아니다
- **미래 수익률 표현 금지** — "상승 가능성 76%" 같은 표기는 근거가 없다
- **면책 문구 필수** — 이미 LLM 프롬프트에 있는 "투자 자문이 아님"을 점수 UI에도

## 7. 검증 — "터무니없지 않음"을 증명하는 절차

설계보다 이 절이 중요하다. 아래를 통과하지 못하면 노출하지 않는다.

### 7.1 분포 검증 (배치 직후, 자동)

| 항목 | 합격 기준 |
|------|----------|
| 평균 | 50 ± 3 |
| 표준편차 | 12 ~ 18 |
| 0점 / 100점 종목 수 | 각 0.5% 미만 |
| 히스토그램 | 단봉(unimodal), 양 끝 뭉침 없음 |

표준편차가 8 미만이면 전부 "보통"이라 무의미하고, 22를 넘으면 극단으로 튄다.

### 7.2 사후 검증 케이스 (회귀 테스트로 고정)

| 케이스 | 기대 |
|--------|------|
| ROE 227,162% 껍데기 회사 | 상위 10% 진입 **불가** (윈저라이즈 검증) |
| 일봉 20개뿐인 신규 상장 | 점수 60 이하로 수축 (커버리지 검증) |
| 재무 우량 + 주가 급락 종목 | 수익성 축 高 / 추세 축 低 가 **분리 표시** |
| ETF | `technical_only` 라벨 |
| EPS 적자 → 소폭 흑자 전환 | 성장 축이 만점이 **아님** (§4.3) |

### 7.3 예측력 검증 (데이터 축적 후)

`DAILY_CLOSE_DESIGN.md` §9.1의 경고를 그대로 승계한다.

> 00:00 배치 점수는 그날 종가를 **이미 보고** 만든 값이다. `score(D)` vs `return(D)`를 비교하면 사후 설명이지 예측이 아니다. **반드시 `score(D)` vs `return(D+1)`**로 평가할 것.

- 정보계수(IC): score(D) vs return(D+1) 순위상관
- 점수 십분위별 평균 D+1 수익률의 **단조성**
- **최소 40~60거래일 축적 후에만 노출.** 표본이 적을 때의 적중률은 노이즈다

현재 `stock_daily_closes`에 26거래일(2026-07-01~08-07) × 8,714종목이 쌓여 있으므로, 앞으로 한 달이면 이 검증이 가능해진다.

### 7.4 안정성

```
|score(D) − score(D−1)| 의 p95 < 5점
```

이를 넘으면 추세 축 비중이 과도하거나 백분위 그룹 표본이 부족한 것이다.

## 9. 스키마 · 파이프라인

### 9.1 스키마

```sql
-- 피어 백분위는 유니버스 전체를 한 번에 훑어야 나온다 → 배치 산출물을 저장
CREATE TABLE IF NOT EXISTS stock_scores (
  symbol        VARCHAR(32) NOT NULL,
  trade_date    DATE        NOT NULL,
  score         TINYINT     NULL,      -- 최종 0~100 (수축 적용 후), 불가 시 NULL
  score_kind    VARCHAR(16) NOT NULL,  -- composite | technical_only
  grade         VARCHAR(2)  NULL,      -- A+ ~ D
  coverage      DECIMAL(4,3) NOT NULL, -- 0.000~1.000
  peer_group    VARCHAR(64) NOT NULL,  -- 예: us:NASDAQ:cap3
  peer_pct      TINYINT     NULL,      -- 피어 내 백분위
  breakdown     JSON        NOT NULL,  -- {technical, quality, growth, valuation, sentiment} 원본
  inputs        JSON        NOT NULL,  -- 사용된 원지표 실수치 (사후 감사용)
  computed_at   TIMESTAMP(3) NOT NULL,
  PRIMARY KEY (symbol, trade_date),
  KEY idx_stock_scores_date (trade_date)
) ENGINE=InnoDB;
```

- `breakdown`을 원본 그대로 저장 → **비중을 바꿔도 과거를 재계산할 수 있다** (기존 설계 원칙 승계)
- `inputs` 저장 → "이 점수는 왜 이런가"를 사후에 감사 가능. LLM이 아닌 서버 계산이므로 완전 재현된다
- `stock_daily_closes.score`(현행 컬럼)는 이 테이블에서 복사해 유지하거나, FE를 조인으로 전환

### 9.2 배치

```
시장 마감 +30분 (DailyCloseService.RunScheduler 뒤에 연결)
  1. 종가 적재 완료 대기 (기존)
  2. 유니버스 스냅샷 로드: stocks ⨝ stock_fundamentals ⨝ stock_daily_closes(최신) ⨝ candle_bars(1d)
  3. 피어 그룹 분할 → 그룹별 윈저라이즈 + 순위 백분위
  4. 축 점수 → 합성 → 수축 → 등급
  5. stock_scores UPSERT
  6. 분포 검증(§7.1) 자동 실행, 기준 미달 시 로그 경고 + 적재 보류
```

- **업스트림 API 호출 0회.** 전부 이미 DB에 있는 데이터
- 유니버스 전체를 메모리에 올려도 17,901행 × 수십 필드 = 수십 MB 수준
- 멱등: PK `(symbol, trade_date)` UPSERT
- 6단계가 중요하다 — 분포가 깨진 채로 사용자에게 나가지 않도록 배치 스스로 게이트

### 9.3 API

```
GET /api/v1/stocks/{symbol}/score          # 최신 1건 + breakdown + peer_pct + coverage
GET /api/v1/stocks/{symbol}/score/history?limit=60
```

기존 `daily-closes` 응답의 `score`는 그대로 두고(하위 호환), 상세 화면만 새 엔드포인트를 쓴다.

## 10. 구현 순서

1. `stocks`에 시가총액 계산 + 피어 그룹 산출 (§4.1) — 스키마 변경 없이 배치 내부에서
2. 백분위 정규화 유틸 + 윈저라이즈 (유닛 테스트: §2.2의 실제 꼬리값을 입력으로 고정)
3. 4개 배치 축 (추세·수익성·성장·가치) + 축 신뢰도
4. 합성 + 커버리지 수축 + 등급 (§5.2, §6.1) — **유닛 테스트로 §5.2 표의 4개 시나리오 고정**
5. `stock_scores` 마이그레이션 + 배치 + §7.1 분포 게이트
6. API + FE 5축 분해 표시 (§6)
7. 섹터 컬럼 추가 → 피어 그룹 교체 (§8-1)
8. 예측력 검증 모듈 (§7.3) — **40거래일 축적 후**

1~4는 DB 스키마 변경 없이 가능하므로 먼저 계산만 돌려보고 §7.1 분포를 확인한 뒤 5로 넘어가는 것을 권장한다.

## 11. 리스크

| 항목 | 내용 |
|------|------|
| **섹터 부재** | 해결 전까지 가치·수익성 축은 "업종 편향"을 안고 간다. §8-1 우선 처리 |
| **PER 커버리지 7%** | 가치 축은 대부분 종목에서 결측 → 커버리지 수축으로 흡수되지만, 밸류에이션이 점수에 반영된다고 **과장 표기하면 안 된다** |
| **일봉 40개 한계** | 52주·SMA200 부재. `daily_close_fetch.go`의 `Count: 40`을 늘리면 개선되나 Toss 호출량 증가 |
| **백분위의 상대성** | 유니버스가 전부 하락해도 상대 순위는 유지된다. "점수가 높다 = 오른다"가 아니라 "동종 대비 낫다"임을 UI에 명시 |
| **다중 인스턴스** | 배치 리더 선출 없으면 중복 실행. UPSERT라 데이터는 안전 (AGENT_STATE TODO와 동일 사안) |
| **면책** | 점수 노출 시 투자 자문이 아님을 반드시 병기 |
