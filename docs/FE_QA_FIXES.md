## 1. 검색 — 세 증상, 한 뿌리 (BUG-03 · BUG-04 · R-3)

가장 오래 파고든 곳이다. 세 가지가 별개로 보였지만 둘은 같은 뿌리였다.

### 무엇이 실제로 일어나고 있었나

`stocks` 테이블에는 `english_name`이 **한글 이름 그대로 복사된 행**이 섞여 있다
(카탈로그 보강 전 행). 관련도 점수는 한글 질의에도 `english_name`을 함께 봤기 때문에,
그런 행만 단어 일치 +800 · 부분 일치 +400 = **+1,200점을 더 받았다.**

```
「삼성」 검색                         점수
  삼성 미국다우존스 TR ETN            5,700   ← english_name이 한글이라 +1,200
  삼성전자                            4,500
```

점수가 1차 정렬 기준이었으므로 ETN이 본주를 이겼다 — 실측으로 **상위 20개가 전부 ETN**,
삼성전자는 21번째였다.

그리고 검색은 1위 종목을 카탈로그 보강 대상으로 올린다(`triggerCatalogBackfill`).
보강이 그 행의 `english_name`을 제대로 된 영문으로 바꾸면 점수가 5,700 → 4,500으로
떨어져 **다음 호출에서는 아직 보강 안 된 다음 ETN이 1위가 됐다.** 이것이
「같은 검색어인데 호출마다 결과가 한 칸씩 밀린다」의 정체다 — 검색할수록 순위가 흘러가는
구조였다. (DB 확인: `530127`~`530129`는 `english_name`이 「삼성 미국다우존스 TR ETN」,
`530120`~`530125`는 내 프로브 호출 직후 시각으로 `updated_at`이 찍혀 있었다.)

### 고친 것

**`be/internal/repository/stock_search.go`**

1. **한글 질의에는 `english_name`을 보지 않는다.** 한글이 영문 표기와 일치할 일은 없으므로,
   그 조건이 참이 된다는 것 자체가 「english_name에 한글이 들어 있다」는 뜻 — 즉 `name`
   매치의 중복 계산이다.
2. **관련도를 1,000 단위 칸으로 묶고**(`relevanceTierSize`) 정렬 기준을 다시 세웠다:

   ```
   관련도 칸 → 상품 우선순위 → 시가총액(KRW) → 상장주식수 → 심볼
   ```

   정확 일치(+50,000)·심볼 일치(+10,000) 같은 **의미 있는 차이는 그대로 살고**, 자잘한
   가산점은 같은 칸에 묶여 「본주 우선 → 큰 회사 우선」이 판단하게 된다.
3. **마지막 기준을 심볼로 못박았다.** 예전에는 상장주식수까지만 비교했는데 ETN 다수가
   1,000,000주로 같아 그 뒤가 정해지지 않았고, 결국 DB가 주는 순서에 맡겨졌다.
4. **국내 종목코드 인식**(`LooksLikeDomesticCode`). 라틴 질의를 전부
   `asset_type != 'domestic'`로 몰아내던 필터가 `005930`까지 걸러 **0건**을 만들고 있었다.

**`be/internal/repository/stocks.go`** — 후보 질의에 `ORDER BY symbol ASC`를 박았다.
표시 순서와는 무관하고, **`LIMIT`이 잘라내는 창을 고정**하기 위한 것이다. 정렬 없는
`LIMIT`은 어떤 행이 들어올지 스토리지 엔진에 맡긴다. 상한도 500 → 1,000으로 올렸다
(흔한 검색어 실측: 삼성 98 · 전자 48 · 코리아 62 · 인버스 160 · KODEX 239 · 스팩 74).

### 시가총액 정렬을 「느리지 않게」

`시가총액 = shares_outstanding × 최신 종가`라 조인이 필요한데, `/stocks/search`는
**비로그인도 부를 수 있는 공개 경로**다. 요청마다 3.85M행 테이블을 조인하면 검색
트래픽이 DB(운영 1 ECPU)를 잠식한다.

**전 종목 스냅샷을 한 번에 받아 15분 TTL로 재사용한다** — `stock_market_caps.go`.

쿼리 계획을 재서 골랐다:

```
EXPLAIN SELECT symbol, MAX(trade_date) FROM stock_daily_closes GROUP BY symbol
→ type=range  key=PRIMARY  rows=37,465  Extra="Using index for group-by"   ← 루스 인덱스 스캔
```

PK가 `(symbol, trade_date)`라서 「심볼별 최신 날짜」가 **인덱스만으로** 끝난다 —
테이블을 건드리지 않는다. 전체 스냅샷 1회 = 10,797행, 프로세스 기동 포함 0.70초.
날짜 슬라이스(`trade_date >= CURDATE() - 12일`) 대안도 재봤지만 102,539행을 읽어야 해서
오히려 무겁다. 스냅샷 적재가 실패하면 **오래된 스냅샷을 그대로 쓴다** — 여기서 nil을
돌려주면 그 순간의 검색만 순서가 달라지는데, 그게 정확히 이번에 고치려던 증상이다.

국내·미국이 한 결과에 섞일 수 있어 USD는 `market_fx_rates`의 환율로 KRW 환산한다.

### 결과 (실측)

```
「삼성」 4회 반복 — 전부 동일
  005930 삼성전자 | 005935 삼성전자우 | 009150 삼성전기 | 207940 삼성바이오로직스 …
  ↑ 본주가 시가총액 순으로, 파생상품은 뒤로

「삼성 인버스」 → total 17, ETN이 정상적으로 나온다  (걷어내지 않았다)
「005930」 → 삼성전자 · 「00593」 → 삼성전자·삼성전자우 · 「000660」 → SK하이닉스
응답 시간 0.33s (5회 편차 ±0.02s)
```

## 2. 치명 (P0)

### BUG-01 · 모달 안 자동완성이 마우스로 클릭되지 않던 것

자동완성 패널은 `createPortal(document.body)`로 나가는데, Radix Dialog가 열리면
`react-remove-scroll`이 **`document.body`에 `pointer-events: none`**을 건다. 패널이 그 값을
물려받아 목록은 보이는데 클릭만 먹지 않았다.

포털을 걷어내고 입력칸 아래 절대배치하는 방법도 검토했지만, 두 모달 다
`overflow-y-auto`/`overflow-hidden`이라 목록이 잘린다 — **포털이 있는 이유가 그것이다.**
그래서 포털은 두고 상속만 끊었다(`pointerEvents: "auto"`). 더해서 Radix의
DismissableLayer가 이 클릭을 「바깥 클릭」으로 보고 다이얼로그를 닫아 버리므로
`pointerdown`/`mousedown` 전파를 끊었다.

**검증**: 스탬프·일괄 추가 두 모달에서 `elementFromPoint`가 옵션을 돌려주고, 클릭이
선택으로 이어지며, 다이얼로그가 닫히지 않는다. E2E 스펙으로 고정했다
(`tests/ui/dialog-stock-picker.spec.ts` — 키보드로 우회하지 않는다).

### BUG-02 · 빈 공개 리포트가 한 번의 클릭으로 영구 발행되던 것

**서버와 화면 양쪽**을 막았다.

- 서버(`service/research.go`): `bodyMd`가 비면 400. 이 규칙은 화면 상태가 아니라
  **발행물의 최소 조건**이고, 화면에만 두면 다음 진입점이 생길 때 구멍이 다시 열린다.
- 화면: 본문이 없으면 버튼을 잠그고 **왜 잠겼는지 말한다**. 그리고 발행 전에
  종목·방향·공개범위와 **오늘 남은 발행 건수**를 담은 확인 창을 띄운다 — 발행은 하루 5건
  한도를 소모하는데 남은 수를 모르고 누르면 정작 쓰고 싶던 종목에서 막힌다.
  한도는 `ResearchPreview`에 `dailyCap`/`dailyRemaining`으로 실어 보낸다.

방어의 방향도 바로잡았다: 예전에는 훨씬 가벼운 「철회」에만 `window.confirm`이 있었다.

## 3. 실패를 실패라고 말하기 (BUG-09 · 10 · 11 · C-4 · A-3)

**BUG-10이 이 묶음에서 가장 위험했다.** 목표가가 저장돼 있는 계정에서 그 API만 막으면
`/targets`가 **첫 사용자용 온보딩 튜토리얼**을 띄웠고 실패 언급이 한 글자도 없었다.
사용자에게 그 화면은 「내 기록이 지워졌다」로 읽힌다.

원인은 `lib/price-targets.ts`의 스토어가 **실패를 통째로 삼키고** 있었던 것이다. 화면은
0건과 실패를 구분할 방법이 없었다. 스토어에 오류 상태를 두고(`usePriceTargetsState`)
401만 조용히 넘긴다 — 비로그인 방문자가 예시 모드로 구경하는 정상 경로이므로.

- **`lib/error-message.ts`** (신규): 서버·네트워크 오류를 사용자 문구로 바꾸는 한 곳.
  `{"error":"internal"}` 같은 봉투를 벗기고, 알려진 문자열을 매핑하고, 모르는 것은
  화면이 준 fallback을 쓴다 — **원문을 그대로 내보내는 경로가 없다.** 코드모드로
  `err instanceof Error ? err.message : "…"` **65곳**을 한 번에 옮겼다.
- **`components/common/load-error-state.tsx`** (신규): 실패 카드 + 「다시 시도」.
  "저장된 기록이 사라진 것은 아닙니다" 한 줄을 넣었다 — 빈 화면과 헷갈리면 사용자는
  다시 입력하기 시작한다.
- **`components/common/offline-banner.tsx`** (신규): 원인이 브라우저 바깥일 때는 화면
  하나가 아니라 앱 전체가 같은 말을 해야 한다.

**검증**: `/targets` API를 500으로 막고 — 실패 문구 O · 온보딩 튜토리얼 X · 다시 시도 O ·
원문 노출 X.

## 4. 진입점이 없던 것 (BUG-06 · BUG-07 · A-1)

추가 폼은 사이드 레일 안에 있고 그 레일은 보유 0건이면 렌더되지 않는다. 안내 카드의
CTA는 `/analysis`로 보냈고 거기에도, 종목 상세에도 보유 추가 버튼이 없었다 — **가입 직후
사용자는 첫 보유 종목을 등록할 방법이 아예 없었다.** (같은 사실이 프로젝트 e2e 주석에도
적혀 있었고, 그래서 그 테스트는 API로 보유를 심어 놓고 시작한다.)

- `AddHoldingDialog`(신규)로 같은 폼을 레일 밖에서도 연다 — 폼을 두 벌 만들지 않는다.
- 빈 화면 CTA를 「종목 추가하기」로 바꿔 그 폼을 연다.
- 종목 액션 줄에 **「보유 추가」**를 넣었다(§A-1). 그 줄에는 관심·스탬프·리포트·메모·
  목표가가 있는데 보유만 없었다.

메모장 「첫 메모 쓰기」(BUG-07)도 같은 종류였다 — `setSelectedId("new")`가 초기값과 같고
편집기는 반대 분기에 있어 **완전한 no-op**이었다.

### C-8 — 담은 가격을 지키는 일

관심종목의 「담은 가격」은 **「담은 뒤로 얼마나 움직였나」의 기준선**이고 그것이 이 기능의
존재 이유인데, 해제했다 다시 담으면 오늘 시세로 조용히 덮였다(실측 257,500 → 258,000).
`POST /watchlist`가 `addedPrice`를 선택적으로 받게 하고, 실행 취소가 그 값을 되돌린다.
처음 담는 경로는 생략하고 서버가 현재가를 찍는다.

## 7. 계정 관리 (A-6) — 새로 생긴 것

비밀번호 변경도 탈퇴도 **앱 어디에도 없었다.** 비밀번호를 잊으면 계정으로 돌아올 길이
없고, 그만두려는 사람은 데이터를 남긴 채 떠나야 했다.

셋 다 현재 비밀번호를 다시 받는다 — 로그인 세션은 오래 유지되고 남의 자리에 열린 채
남아 있을 수 있다.

**비밀번호를 바꾸면 모든 기기의 세션을 끊는다.** 바꾸는 이유의 대부분이 「누가 내 계정을
보고 있는 것 같다」인데 기존 refresh 토큰을 살려 두면 정확히 그 사람이 계속 들어와 있다.

**탈퇴는 소유 데이터를 한 트랜잭션에서 지우고, 발행한 리포트·댓글은 남긴다.** 그것들은
공개 기록이고 다른 사람의 댓글·평가가 붙어 있다 — 계정 하나가 사라졌다고 그 대화까지
사라지면 안 된다. 작성자 이름은 `users` 행과 함께 사라지므로(조회가 `LEFT JOIN users`)
화면에는 익명으로 남는다. 개인정보는 지우면서 남의 글은 지키는 경계다.

## 9. 손대지 않은 것

- **`react-hooks/set-state-in-effect` 59건.** 이번 작업 이전부터 있던 패턴이고 내가
  건드리지 않은 파일(`use-quote-detail.ts`, `use-market-indices.ts` 등)에서도 동일하게
  난다. 59곳의 이펙트 구조를 바꾸는 것은 이 작업의 범위를 넘고, 회귀 위험이 이득보다 크다.
- **뉴스 화면의 나머지 필터 6개를 URL에 싣는 것.** 여덟 개를 전부 붙이면 링크가 상태를
  설명하기는커녕 읽을 수 없게 된다. 돌아올 만한 값(정렬)만 실었다.
