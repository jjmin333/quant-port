## ▶ 새로 필요한 결정 — D2에서 파생

60분봉을 제거하면 **롤업 계층의 마지막 칸이 비어** 하나를 정해야 한다.

현재 사다리 (`candles_tiers.go:40`):
```
1m(3일) → 5m(7일) → 10m(14일) → 30m(30일) → 60m(60일) → 만료
                                              ↑ 이 칸이 사라진다
```

60m을 빼면 **30m이 마지막 계층**이 되는데, 그 보관 기간을 정해야 한다.

| 안 | 인트라데이 보관 | 저장량 변화 | 의미 |
|---|---|---|---|
| **(A) 60일 유지** | 30분봉을 60일까지 보관 | **+약 40MB** (30~60일 구간이 60분봉→30분봉이라 행 2배) | 지금과 같은 기간, 해상도는 오히려 좋아짐 |
| **(B) 30일로 축소** | 30일 넘으면 인트라데이 만료 | **−상당량** (30~60일 구간 소멸) | 인트라데이 히스토리가 절반으로 |

> **권장: (A)**. 추가 저장량이 약 40MB로 작고(`[HW]` 50 GiB 볼륨에서 무시 가능),
> **30~60일 구간의 해상도가 60분봉에서 30분봉으로 오히려 좋아진다.**
> (B)는 저장을 아끼지만 "두 달 전 인트라데이"를 볼 수 없게 되는 기능 축소다.
>
> ※ 추정치다. Phase 0의 **V7**(p_1m 커버리지 실측) 후 정확한 수치로 재확인한다.

# 3. 왜 이 순서인가 — 한 장 요약

문제를 **그룹별로** 나누면 처방이 갈린다. rate-limit이 그룹 단위로 걸리기 때문이다.

| 그룹 | 현재 | 원인 | 처방 | Phase |
|---|---|---|---|---|
| **`MARKET_DATA`** | 81~140 req/s **(초과)** | `tickFast` 80 req/s | **웹소켓 구독** → 0 | **3** |
| **`MARKET_DATA_CHART`** | 예열 + 콜드 37호출 **(초과)** | `tickSlow` · 콜드 미스 · 1d 낭비 | 예열 제거 · 1d 델타 · **일봉 DB 보장** · 콜드 축소 | **1·2·4** |
| `STOCK` | 검색마다 1호출 | 국내 후보 허구 | **마켓 판정**(조건문 하나) | **1** |
| `RANKING` | 고정 | — | 조치 불필요 | — |

**핵심 원리 하나**: 모든 처방의 목적은 같다 —
**「상류 호출량을 사용자 수에서 떼어내는 것」**.
웹소켓은 비용을 *동시 시청 심볼 수*로, 배치는 *고정값*으로, DB 계층은 *0*으로 바꾼다.

## Phase 2 — 60분봉 제거 + 배치 고정 비용화 (4일) · **D2·D3**

### 2-A. 60분봉 기능 제거 (D2)

**왜 이게 효과가 큰가** — 60분봉은 인터벌 중 **혼자 압도적으로 비싸다**:

| 인터벌 | 첫 화면 raw 1분봉 | **호출** |
|---|---|---|
| 1m | 200 | 1 |
| 5m | 600 | 3 |
| 10m | 1,200 | 6 |
| 30m | 3,600 | 18 |
| **60m** | **7,200** | **36** ← 제거 대상 |
| 1d | 200 | 1 |

**★ 부수 효과가 더 크다.** `maxIntradayRawBars = 7200`은 **60분봉 120개를 만들기
위한 값**이다(`120 × 60`). 60분봉이 사라지면 최대 필요량이 **30분봉 기준
`120 × 30 = 3,600`**으로 줄어든다. 그런데 이 상수는 **콜드 미스 경로에서도 쓰인다**:

```go
// intraday1mFetchTarget — 저장된 봉이 없으면 maxIntradayRawBars를 통째로 요청
target1m := s.intraday1mFetchTarget(ctx, symbol)   // 콜드면 7,200 → 3,600
```

> **콜드 미스 1회가 37호출 → 19호출로 거의 절반이 된다.**
> 이건 60분봉을 보든 안 보든 **모든 인트라데이 첫 열람**에 적용된다.

**작업 목록** (BE 7곳 · FE 6곳):

| 레이어 | 파일 | 내용 |
|---|---|---|
| BE 모델 | `model/quote.go:25` | `Interval60m` 제거 |
| BE 계층 | `service/candles_tiers.go:45` | `intradayTiers`에서 `{Interval60m, 60, 60}` 제거 → **보관 기간 결정 필요(위 ▶)** |
| BE 매핑 | `service/quotes.go:248` | `mapCandleInterval`에서 제거 |
| BE 집계 | `service/quotes_candles_agg.go:20` | `intervalMinutes`에서 제거 |
| BE 상수 | `service/quotes_candles_agg.go:38` | **`maxIntradayRawBars` 7200 → 3600** |
| BE 스트림 | `service/quotes_marketdata.go:18,344` | 스트림 인터벌 목록에서 제거 |
| **DB** | `repository/candle_bars_tiering_migrate.go:23` | 파티션 정의에서 `p_60m` 제거 |
| **DB 마이그레이션** | 신규 `migrations/06x_drop_60m.sql` | **`ALTER TABLE candle_bars DROP PARTITION p_60m`** |
| FE | `chart-fullscreen-modal.tsx:19` · `stock-chart-terminal.tsx:22` | `{ id: "60m", label: "60" }` 버튼 제거 |
| FE | `chart-time.ts:34` · `quotes-chart-prefs.ts:20` · `quotes-types.ts` · `quotes-mock-data.ts` | 타입·분기에서 제거 |

**`DROP PARTITION`을 쓰는 이유** `[HW]`: `DELETE`는 행 단위로 지우며 redo/undo를
쌓는데, 스토리지가 **29 MiB/s**다. `DROP PARTITION`은 **파일 단위**라 거의 즉시 끝난다.

**주의**:
- 사용자 저장 설정에 `60m`이 남아 있을 수 있다(`quotes-chart-prefs.ts`) →
  **알 수 없는 인터벌은 `30m`으로 폴백**하도록 마이그레이션 처리.
- `DROP PARTITION`은 **되돌릴 수 없다.** 롤업과 같은 성질이라 실행 전 확인 필수.
- 순서: **FE 배포(버튼 제거) → BE 배포 → 파티션 드롭.** 반대로 하면 FE가
  없는 인터벌을 요청한다.

## Phase 3 — 웹소켓 (2주) · **V2 통과 시**

`tickFast`를 구독으로 교체한다. **Tier 구조를 기다리지 않는다** — 건드리는 코드가 다르다.

```
지금:  tickFast → refreshTerminalSnapshot → publishQuoteUpdate → streamHub → SSE
                                          → refreshFormingBars
이후:  웹소켓 trade 프레임 ──────────────→ publishQuoteUpdate → streamHub → SSE
                          ──────────────→ refreshFormingBars (거래량까지 정확)
       웹소켓 orderbook 프레임 ─────────→ 터미널 스냅샷의 호가
```

**슬롯 배분(200)**: `trade` 140 + `orderbook` 60
→ 현재 `marketFastSymbolCap = 40` 대비 **체결 3.5배 · 호가 1.5배**, 비용은 **0**.

**필수 안전장치** (설계의 절반):

| 실패 | 대비 |
|---|---|
| LOSSY 프레임 드롭 | 심볼별 마지막 프레임 시각 감시 + **5분 REST 정합** + 구독 심볼도 백스톱 폴링 |
| 연결 2개 상한 (초과 시 오래된 것 종료) | **폴러 컨테이너 1곳만** 소유. 배포는 old drain → new |
| idle 180초 | 60초 `PING` |
| `server-shutdown` 프레임 | 즉시 재연결 + 전체 재선언 |
| 선언 5회/초 | 200ms 디바운스 + 승격/강등 **히스테리시스** |
| **웹소켓 전면 장애** | **폴링 코드를 지우지 않는다.** 플래그로 즉시 복귀 |

**부가 이득**: `trade` 프레임으로 **1분봉을 서버가 직접 생성**할 수 있어
`tickSlow`의 1m 폴링도 불필요해진다(정합용 5분 1회만 남김).

## Phase 4 — 차트 가용성 계약 (1주) · **D4**

> *"트래픽이 늘어도 차트를 정상적으로 확인할 수 없는 경우는 없어야 한다."*

**폴백 사다리** (D4는 5번만 정한다):

```
1. DB 계층 조회                      → 히트 시 7ms          ← 대부분 여기서 끝
2. 전경 예산으로 Toss 페치 (40봉=12호출)
3. 예산 소진/429 → 최대 2초 재시도    ← 버킷 리셋이 초 단위
4. 실패 + DB에 일부 있음 → 부분 구간   ← 봉 수만 적고 인트라데이는 맞음
5. 정말 아무것도 없음 → 「일봉으로 보기」 제안 (D4)
```

**콜드 페치 축소**: 첫 화면 120봉 → 40봉 (60분봉 기준 36 → 12호출), 나머지는
`NextBefore` 페이지네이션으로 점진 확장.

**예산 분리**: `MARKET_DATA_CHART`를 전경 70% / 배경 25% / 여유 5%.
배경은 `Allow()`(거부 시 스킵), 전경은 `Wait()`(상한 2초).

**검증**: `chart_fallback_total{reason=nodata}` 가 동시 열람 50·100·200명
부하에서 **0**인지 스테이징 정기 확인.

# 4-A. 무중단 운영 원칙

> 요구: *"작업 도중 서비스가 중단되지 않도록. 중단이 필요한 작업이면 종료 후 바로 재기동."*

## 먼저 정직하게 — API가 1대라 **완전 무중단은 구조적으로 불가능**하다

코드 배포에는 프로세스 교체가 따르고, 인스턴스가 하나뿐이라 **수 초의 순단**이 난다.
없앨 수 있는 것은 「긴 중단」과 「데이터 손실」이지 「순단」이 아니다.

**대신 지킬 것:**
1. 재기동은 항상 `be/scripts/restart.ps1 -Background` (Docker) — 프로젝트 표준.
   `/health`가 통과할 때까지 대기하고 **Tesseract 상태까지 확인**한다.
2. **상태는 전부 외부(MySQL·Redis)에 있다** — 재기동해도 데이터가 사라지지 않는다.
   프로세스 내부 캐시(뉴스 목록 등)만 비고, 그건 자동으로 다시 채워진다.
3. 순단이 나는 작업은 **장 마감 후 또는 새벽**에 몰아서 한다.
4. 한 번에 하나씩. 재기동 후 `/health` + 핵심 화면 확인 전에는 다음으로 안 넘어간다.

## 작업별 중단 특성

| 작업 | 중단 | 처리 |
|---|---|---|
| **Phase 0 측정** | **없음** | 읽기 전용. 운영 중 수행 가능 |
| Phase 1 코드 변경 | API 순단 수 초 | 배포 후 즉시 `restart.ps1 -Background` → `/health` 확인 |
| **60분봉 `DROP PARTITION`** | **거의 없음** | 파일 단위 삭제라 즉시. 단 메타데이터 락 순간 존재 → **장 마감 후** |
| 60분봉 FE/BE 배포 | API 순단 | **순서 고정: FE 배포 → BE 배포 → 파티션 드롭.** 반대로 하면 FE가 없는 인터벌을 요청 |
| Phase 2-B 배치 스케줄 추가 | 워커만 재기동 | **API 무중단** — 워커 컨테이너만 교체 |
| **Phase 3 웹소켓 배포** | **주의 필요** | 계정당 연결 2개 상한 → 새 프로세스가 붙으면 **기존 연결이 끊긴다**. **old drain → new** 순서 강제. 그동안 폴링 폴백이 받는다 |
| **`news_articles` MVI 추가** | **없음** (`LOCK=NONE`) | **04:00 KST**. 단 시작·종료 시 메타데이터 락 → **뉴스 폴러를 4분간 정지**시키고 진행 |
| 커넥션 풀 재조정 | API·워커 재기동 | 값만 바꾸면 되므로 짧다. `max_connections`는 **안 바꾸므로 MySQL 재기동 없음** |
| **P2-12 백업 테이블 드롭** | 거의 없음 | `DROP TABLE`은 파일 단위. 장 마감 후 |

**MySQL 재기동이 필요한 작업은 계획에 하나도 없다** — `max_connections`를
그대로 두기로 한 결정(1 ECPU) 덕분이다.

## 확인이 필요한 것

- **SSE 재연결**: API 재기동 시 열린 SSE 스트림이 전부 끊긴다.
  **FE가 자동 재연결하는지 확인해야 한다.** 안 하면 사용자가 새로고침할 때까지
  차트가 멈춘 것처럼 보인다 → Phase 1에서 확인하고, 없으면 재연결 로직을 먼저 넣는다.

# 4-B. 세션 중단 시 재개

> 요구: *"토큰이 만료되어 작업이 중단되면 사용량이 채워지는 오전 8시 20분에 바로 재개."*

**정직하게**: 세션이 사용량 한도로 끊기면 **내가 스스로 깨어날 수는 없다.**
대신 **끊긴 지점을 잃지 않게** 하는 것은 확실히 할 수 있고, 그게 이 프로젝트의
기존 규약이기도 하다(`AGENTS.md`: *"Start: read docs/AGENT_STATE.md. End: update it"*).

**그래서 이렇게 한다:**

1. **각 Phase를 끝낼 때마다 `docs/AGENT_STATE.md`를 갱신한다** — 무엇을 끝냈고
   무엇이 다음이며 어떤 값이 측정됐는지. 세션이 끊겨도 다음 세션이 그 파일만
   읽고 **정확히 이어서** 시작한다.
2. **작업 단위를 작게 자른다.** 한 커밋이 한 가지만 바꾸게 해서, 어디서 끊겨도
   중간 상태가 일관되게 남는다.
3. **중단 위험이 큰 작업은 되돌릴 수 있게 시작한다** — 파티션 드롭·인덱스 추가처럼
   비가역인 것은 **그 작업 하나만 하는 세션**에서 처리한다.

**8시 20분 재개 방법 두 가지:**
- **(권장) 세션을 다시 열고 "이어서 진행해"** — `AGENT_STATE.md`를 읽고 바로 이어간다.
- 예약 실행을 걸어 두는 방법도 있으나, **코드를 바꾸는 작업을 무인으로 돌리는 것**은
  파티션 드롭·마이그레이션이 섞인 이 계획에서 권하지 않는다.

# 6. 리스크와 중단 기준

| 리스크 | 대비 | 중단 기준 |
|---|---|---|
| **V2가 "공유"로 판명** | Phase 1·2·4는 무관 | Phase 3 폐기 → 폴링 최적화로 대체 |
