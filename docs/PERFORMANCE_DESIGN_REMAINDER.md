# 2. 차트 가용성 계약 — 트래픽이 늘어도 차트는 뜬다

## 지금 이 계약이 깨지는 경로

차트 한 장이 뜨려면 `MARKET_DATA_CHART`(캔들)와 `MARKET_DATA`(현재가·형성봉)가
둘 다 필요하다. 지금은 **두 버킷 모두 사용자 수에 비례해 고갈된다.**

```
① 콜드 인트라데이 1회 = 36 REST 호출 (7,200봉 ÷ 200)   → MARKET_DATA_CHART
② tickSlow 예열       = 대상 × 2호출 / 30초             → MARKET_DATA_CHART
③ tickFast 터미널     = 40종목 × 3호출 / 틱             → MARKET_DATA
④ /stocks/search      = 요청당 Toss GetStocks 1회       → STOCK  (3장)
⑤ tickPrice           = ceil(S/200) / 틱                → MARKET_DATA
```

**①이 특히 위험하다.** 차트를 여는 행위 자체가 36호출을 쓰므로,
동시에 차트를 여는 사용자가 늘면 **서로의 차트를 못 뜨게 만든다.**
한도 20/s 가정에서 **동시 차트 열람 1명이 1.8초어치 버킷을 독점**한다.

## 설계: 3중 방어

### 방어 1 — 차트가 상류에 의존하는 양을 줄인다 (원인)

**(a) 콜드 페치 축소** — 7,200봉을 받아 120봉을 그리는 것을 고친다.

| 안 | 첫 화면 봉 수 | 필요 1분봉 | REST 호출 | 예상 지연 |
|---|---|---|---|---|
| 현재 | 120 | 7,200 | **36** | ~1.7초 |
| **A. 표시 봉 축소** | 40 | 2,400 | **12** | ~0.55초 |
| **B. 점진적 렌더** | 40 먼저 → 배경 확장 | 2,400 + 배경 | 12 (전경) | **~0.55초 체감** |
| C. 상위 계층 우선 | DB 롤업 우선 조회 | 0 (적재된 경우) | **0** | ~7ms |

**C가 가장 좋지만 「한 번이라도 적재된 종목」에만 듣는다.** A·B와 함께 써야 한다.

**(b) 배치 사전 적재** — 예열을 「장중·API·사용자 비례」에서
「마감 후·배치 인스턴스·고정」으로 옮긴다. 일 델타는 종목당 2호출이라
3,000종목이 20/s에서 5분이다. **사용자가 10배가 돼도 5분 그대로다.**

### 방어 2 — 버킷을 예산으로 나눈다 (경합)

`toss.Client`에 **엔드포인트 그룹별 토큰버킷 + 우선순위**를 넣는다.
`PERFORMANCE_DESIGN.md`의 P0-3 옵션 D와 같은 것이되, **차트 전용 예산을 명시**한다.

```
MARKET_DATA_CHART 예산 배분 (V4에서 실측한 한도 기준)
  ├ foreground 사용자 차트 요청 : 70%   ← 절대 양보 안 함
  ├ background 배치 사전 적재   : 25%
  └ 여유                        :  5%
```

배경은 `Allow()`(거부되면 조용히 스킵), 전경은 `Wait()`(상한 2초).
**이러면 배경 작업이 아무리 늘어도 사용자 차트 요청은 통과한다.**

### 방어 3 — 상류가 실패해도 차트는 뜬다 (최후)

이게 계약의 핵심이다. **상류가 죽어도 빈 차트를 보여주지 않는다.**

```
차트 요청
 ├ 1. DB 계층(candle_bars 파티션) 조회        → 있으면 즉시 (실측 7ms)
 ├ 2. 없으면 Toss 전경 예산으로 페치          → 성공 시 저장 후 응답
 ├ 3. 예산 소진/429/타임아웃                  → 1의 부분 데이터라도 응답
 │                                              + 「일부 구간만」 메타 플래그
 └ 4. 아무것도 없음                            → 일봉으로 폴백 (영구 저장이라 항상 있음)
```

**4번이 보장의 근거다.** 일봉은 롤업·삭제 대상이 아니라 DB에 영구히 있고
(`057` 마이그레이션), 실측 7ms다. **인트라데이가 불가능한 최악의 순간에도
일봉 차트는 뜬다.**

### ⚠ 위 4번(일봉 폴백)은 **거의 쓰이지 않아야 한다** — 정정

처음에 "일봉 자동 전환"을 기본안으로 제안했는데 **철회한다.** 두 가지 이유다.

**(1) `/candles` 예산은 초 단위로 리셋된다.**
`market_data_store.go:541` 주석에 실측이 남아 있다 —
*"observed resets are as short as 1s"*. 즉 **「예산 소진」은 최대 1~2초 기다리면
풀리는 상태**다. 영구 실패가 아니다. 그런데 그걸 일봉 전환으로 처리하면
**고칠 수 있는 것을 포기하는 셈**이다.

**(2) 사용자가 1분봉을 눌렀는데 일봉이 나오면 시간축이 완전히 달라진다.**
첨부 화면의 `1 / 5 / 10 / 30 / 60 / 일 / 주 / 월` 중 `1`을 눌렀는데
일봉이 그려지면 「데이터가 늦다」가 아니라 **「엉뚱한 걸 보여준다」**가 된다.
이건 낡은 가격을 보여주는 것과 같은 종류의 잘못이다.

**개정된 폴백 사다리:**

```
1. DB 계층(candle_bars) 조회                → 있으면 즉시 (7ms)   ← 대부분 여기서 끝
2. 전경 예산으로 Toss 페치 (40봉 = 12호출)  → 성공 시 저장 후 응답
3. 예산 소진 / 429                          → **최대 2초 안에서 재시도**
                                               (버킷 리셋이 초 단위)
4. 재시도 실패 + DB에 일부라도 있음          → 부분 구간으로 그린다
                                               (봉 수가 적을 뿐 인트라데이는 맞다)
5. 정말 아무것도 없음 (극히 드묾)            → 여기서만 일봉을 **제안**한다
                                               (자동 전환이 아니라 선택지 제시)
```

**3번이 핵심이다.** 초 단위 리셋을 활용하면 4·5번까지 갈 일이 거의 없다.
그리고 이 대기는 **화면 최초 진입 시점**이라 FE가 어차피 로딩 중이므로
체감되지 않는다.

### 이 문제의 실제 대상 범위 (오해 방지)

「차트가 안 뜬다」가 아무 종목에서나 일어나는 게 아니다. 조건이 겹쳐야 한다.

| 조건 | 해당 여부 |
|---|---|
| **일 / 주 / 월봉** | **영향 없음** — 일봉은 롤업·삭제 대상이 아니라 DB에 영구 저장(`057`). 실측 7ms |
| **삼성전자 등 인기 종목의 인트라데이** | **사실상 영향 없음** — 누군가 계속 보므로 DB에 늘 있다 |
| 롱테일 종목의 인트라데이 **첫 열람** | **여기가 대상** — 1분봉이 롤업으로 접혀 사라졌거나 애초에 없음 |
| 위 + `/candles` 예산 소진이 **동시에** | 여기서만 폴백이 발동 |

> `▶ 선택 1 (개정)` — 위 사다리의 **5번**(정말 아무것도 없을 때)만 결정이 필요합니다:
> **(a) 「일봉으로 보기」를 제안**하고 사용자가 선택 (권장) /
> **(b) 일봉으로 자동 전환** /
> **(c) 빈 차트 + 재시도 버튼**
> 3번(초 단위 재시도)이 들어가면 5번에 도달하는 일 자체가 매우 드뭅니다.

## 계약 검증 방법

# 3. ★ 새로 발견 — `/stocks/search`가 요청 경로에서 Toss를 부르고 DB에 쓴다

감사가 *"나머지 약 163ms의 출처는 아직 모른다"*고 남긴 것의 정체다.

## 문제

`quotes_stocks.go:82` `SearchStocksCatalog`의 요청 경로:

```
1. stocks.Count(ctx, p)                        DB
2. stocks.Search(ctx, p)                       DB (최악 17,912행 풀스캔 14.7ms)
3. expandSearchWithRelatedProducts
   ├ ensureRelatedCatalogFromToss
   │   ├ stocks.ListBySymbols(candidates)      DB
   │   ├ toss.GetStocks(missing)               ★ 외부 API — 동기, 요청 경로 안
   │   └ stocks.Upsert(st)  × N                ★ DB 쓰기 — 심볼마다 1건
   ├ stocks.SearchByNameAnchors                DB
   └ stocks.SearchRelatedByUnderlyingSymbol    DB
```

**요청 하나에 DB 5~6회 + 외부 API 1회 + DB 쓰기 N회.** 163ms의 출처다.

**그런데 지연보다 심각한 것이 셋 있다:**

1. **공개 엔드포인트다.** `router.go:80`이 `OptionalAuth` 그룹에 둔다.
   **비로그인 사용자가 검색어를 던지는 것만으로 Toss 호출과 DB 쓰기를 유발**한다.
2. **`STOCK` 버킷을 `prefetchStockInfo`와 공유한다.** `tickFast`가 매 틱
   `/stocks`를 부르는데(`market_poller.go:196`), 검색 트래픽이 그 버킷을 먹으면
   **터미널 갱신이 함께 죽는다** — 2장의 가용성 계약에 직접 저촉된다.
   감사 실측에도 `/stocks` 429가 40건 있다.
3. **DB 쓰기 증폭.** 검색 한 번이 `stocks.Upsert`를 N번 낸다.
   `[HW]` 1 ECPU · 29 MiB/s에서 이건 작지 않다.

**증가 계수**: 검색 트래픽에 **선형**. 사용자가 늘면 그대로 늘어난다.
감사가 P2로도 분류하지 않은 항목인데, **실질 위험도는 P0급**이다.

## 목표

요청 경로에서 **외부 API 호출과 DB 쓰기를 제거**한다. 검색은 읽기여야 한다.

## 선택지

### A. 카탈로그 보강을 비동기로 (최소 변경)

`ensureRelatedCatalogFromToss`를 요청 경로에서 떼어내 배경 큐로 보낸다.
`triggerCatalogBackfill`이 **이미 비동기 트리거 패턴**을 쓰고 있으므로 그것을 재사용한다.

- **장점**: 변경이 작고 지연이 즉시 163ms → 15ms 수준으로 떨어진다.
  기존 패턴 재사용이라 새 개념이 없다.
- **단점**: **첫 검색에서 관련 종목이 안 보인다**(다음 검색부터 보인다).
  제품 동작이 미묘하게 바뀐다.
- **비용**: Toss 호출이 요청 수가 아니라 **미적재 심볼 수**에 비례하게 된다 — 급감.
- **난이도**: 하 (0.5일)

### B. A + 배치 선적재

A에 더해, **종목 카탈로그를 배치로 미리 채운다.**
스펙에 `GET /api/v1/stocks/all`이 있고 *"하루 1회 조회 후 로컬 캐싱을 권장"*한다고
문서가 직접 말한다(마켓당 수천 건, gzip 30KB).

- **장점**: 미적재 심볼이 **구조적으로 거의 사라진다.** A의 단점(첫 검색 누락)도
  대부분 없어진다. 상류 호출이 **하루 몇 회의 고정 비용**이 된다.
  이 저장소의 기존 원칙(외부 데이터는 배치 적재)과도 일치한다.
- **단점**: 배치 잡이 하나 는다. `stocks` 17,912행의 정기 갱신 비용.
- **비용**: `[HW]` 일 1회 전량 upsert가 29 MiB/s에 부담이 될 수 있어
  **변경분만 쓰기**가 필요하다(기존 `lastPriceChanged` 패턴과 동일한 발상).
- **난이도**: 중 (2일)

### C. 검색 결과 캐싱

`(q, market, limit, offset)` 키로 짧은 TTL 캐싱.

- **장점**: 반복 검색이 즉시. 구현이 가장 쉽다.
- **단점**: **키가 사용자 입력이라 P1-4와 같은 문제**를 그대로 갖는다.
  그리고 **첫 요청의 Toss 호출은 그대로 난다** — 근본 원인 미해결.
  검색어는 무한하므로 히트율도 낮다.
- **난이도**: 하
- **결론**: A·B의 보완재일 뿐 단독으로는 부족하다.

### D. 검색에 별도(더 낮은) 레이트리밋

- **장점**: 남용 방어에는 직접적.
- **단점**: 정상 사용자도 함께 막는다. 원인을 안 고치고 증상만 누른다.
- **결론**: A·B 이후에도 남는 위험에 대한 **보조 장치**.

## 추천

**`A` → `B` 순서.** A로 요청 경로에서 외부 호출을 즉시 걷어내고,
B로 미적재 자체를 없앤다. C·D는 이후 필요하면 얹는다.

## ★ 추가 발견 — 국내 종목 검색에서는 이 캐시가 **영원히 수렴하지 않는다**

`relatedSymbolCandidates`(`related_symbol_candidates.go:13`)가 만드는 후보를
국내 종목에 대입해 보면 문제가 드러난다. 이 함수는 **미국 레버리지 ETF**를
겨냥해 만들어졌다 — 3글자 티커에 `T`/`S`를 붙이거나(`AMD` → `TAMD`·`SAMD`),
앞 3글자에 `Q·U·G·X·D·L`을 붙인다.

그런데 **마켓 구분 없이 국내 종목에도 그대로 돈다.** `005930`을 넣으면:

```
sym = "005930", len >= 3  →  prefix "005"
  → 005Q, 005U, 005G, 005X, 005D, 005L   (6자 이하라 전부 통과)
len >= 2                  →  00XX
후보 7개 — 전부 존재하지 않는 심볼
```

그 결과:

```
stocks.ListBySymbols(후보 7개) → 하나도 없음 → missing = 7개
toss.GetStocks(missing)        → 결과 없음 → Upsert 0건
다음 검색에서도 missing = 7개  → 같은 호출 반복
```

**`missing`이 절대 줄지 않으므로 국내 종목 검색은 매번 Toss를 부른다.**
"첫 검색만 느리고 이후는 캐시된다"가 아니라 **영구적으로 매 검색마다 1호출**이다.

이건 성능 문제라기보다 **버그에 가깝다.** 그리고 3장 서두의 위험도를
한 단계 더 올린다 — 국내 종목 검색이 서비스의 주 사용 경로이기 때문이다.

### 이 발견이 선택지를 바꾼다

「첫 검색 누락」이라는 A의 단점이 **국내 종목에서는 애초에 존재하지 않는다** —
지금도 관련 종목이 채워지지 않기 때문이다. 즉 A는 국내 검색에서
**아무것도 잃지 않고** Toss 호출만 없앤다.

**그래서 선행 작업이 하나 늘어난다:**

- **A0. 마켓 판정 추가** — `relatedSymbolCandidates`를 미국 종목에만 적용한다.
  국내(6자리 숫자) 심볼에는 `knownRelatedETFOverrides`만 쓴다.
  **이것만으로 국내 검색의 Toss 호출이 0이 된다.** 변경은 조건문 하나다.
- **A1. 미조회 후보 negative caching** — 미국 종목이라도 후보가 존재하지 않으면
  그 사실을 캐싱해 재호출을 막는다. (수렴하게 만드는 장치)
- A2. 그 위에 비동기화 + 배치 선적재(B).

> `▶ 선택 2 (개정)` — 위 발견으로 원래 질문이 거의 무의미해졌습니다.
> **A0(마켓 판정)은 잃는 것이 없으므로 확인 없이 진행**하려 합니다.
> 남은 결정은 **미국 종목**에 대한 것뿐입니다:
> **(a) 비동기화 허용** — 미국 종목 첫 검색에서 관련 ETF가 한 박자 늦게 보임 (권장) /
> **(b) 동기 유지** — 미국 종목은 지금처럼 즉시 보이되 요청 경로에 Toss 호출이 남음
> (A1 negative caching이 있으면 호출 빈도는 크게 줄어듭니다)

|---|---|---|---|
| **A. 마지막에 일괄 재계산** | 영향 심볼 전체를 한 번의 `IN` 조회로 읽고, 한 번의 다중행 upsert로 쓴다 | 질의 수 **O(N) → O(1)**. 기존 배치 upsert 패턴 재사용 | 트랜잭션 안에서 잡는 락 범위가 넓어진다 |
| B. 비동기 재계산 | 등록은 즉시 응답, 보유 집계는 배경에서 | 응답이 가장 빠름 | **등록 직후 화면에 잔고가 안 맞는다** — 정합성 문제 |
| C. 현행 유지 | — | — | 임포트 규모에 선형 |

**추천: `A`.** B는 금융 데이터에서 "방금 등록했는데 안 보인다"를 만들어 부적절하다.
A의 락 범위 확대는 `holding_trades`가 **사용자별로 분리**돼 있어 사용자 간
경합이 없으므로 감수할 만하다(P1-8 주석의 판단과 동일).

## 5-2. 동시 일괄 등록의 중복 경합

**선택지**

**추천: `A`**, 단 **선행 작업이 필요하다** — 기존 데이터의 중복 실태 조사와

# 6. 이번에 새로 발견한 것 (감사에 없음)

## 6-1. SSE가 쓰기 마감 없이 goroutine·소켓을 무기한 잡는다

- **위치**: `quotes_marketdata.go:422`, `:489` — `rc.SetWriteDeadline(time.Time{})`
  그리고 `middleware.RequestTimeout`이 SSE를 제외한다.
- **DB 커넥션은 잡지 않는다**(확인 완료). 문제는 **goroutine과 HTTP 소켓**이다.
- **영향**: 죽은 클라이언트(모바일 백그라운드 전환, 네트워크 끊김)가
  **TCP 타임아웃까지** 자원을 잡는다. `[HW]` 2 OCPU 박스에서
  동시 SSE가 수천이 되면 goroutine보다 **소켓·파일 디스크립터**가 먼저 걸린다.
- **작업**:
  1. `ulimit -n`과 현재 동시 SSE 수를 지표로 노출 (**먼저**).
  2. **keepalive 하트비트**를 주기적으로 써서(예: 30초 `: ping\n\n`)
     끊긴 소켓을 조기에 감지 — 쓰기가 실패하면 그 자리에서 정리된다.
  3. 동시 SSE 상한을 두고 초과 시 폴링으로 유도.
- **난이도**: 하~중. **2장의 가용성 계약과 직결**되므로 우선순위가 낮지 않다.

## 6-2. `AllTrackedSymbols`가 매분 전역 `SELECT DISTINCT` 두 방을 낸다

- **위치**: `market_data_store.go:203` — `holdings.ListAllSymbols` +
  `watchlist.ListAllSymbols`, `refreshPinned`가 60초마다 호출.
- **영향**: 지금은 작지만 **`user_holdings`·`watchlist_items` 행 수에 선형**이다.
  `DISTINCT`는 인덱스가 있어도 전체 스캔에 가깝다.
  `[HW]` 29 MiB/s에서 사용자 10,000명이면 무시할 수 없다.
- **해결**: P0-1의 **수요 기반 구독(H)이 이 쿼리를 통째로 없앤다.**
  별도 작업이 아니라 그 작업의 부수 효과다. **독립 조치 불필요.**

# 6-3. 「실시간 차트」 화면의 Toss 소비 전수 조사와 최종 개선안

> 질문: *"저 화면이 Toss를 가장 많이 쓰는 화면인가? 저 화면을 전부 웹소켓으로
> 만들면 rate-limit이 방지되는가?"*

## 답: 가장 많이 쓰는 화면이 맞다. 그러나 웹소켓만으로는 **절반만** 해결된다.

먼저 스펙에서 확인한 **그룹 전수표**다. rate-limit은 그룹 단위로 걸리므로
"어느 그룹을 쓰는가"가 전부다.

| 그룹 | 엔드포인트 |
|---|---|
| **`MARKET_DATA`** | `/prices` · `/orderbook` · `/trades` · `/price-limits` |
| **`MARKET_DATA_CHART`** | `/candles` |
| `STOCK` | `/stocks` · `/stocks/{symbol}/warnings` |
| `STOCK_ALL` | `/stocks/all` |
| `RANKING` | `/rankings` |
| `MARKET_INFO` | `/exchange-rate` · `/market-calendar/*` |

## 화면 요소별 소비 (첨부 화면 기준)

| 화면 요소 | 그룹 | 현재 호출 방식 | 사용자 수에 비례? |
|---|---|---|---|
| **호가창** (우측 10호가) | `MARKET_DATA` | `tickFast` → `GetOrderbook`, **종목당 1회/틱** | **예** |
| **체결 목록** (하단) | `MARKET_DATA` | `tickFast` → `GetTrades(50)`, **종목당 1회/틱** | **예** |
| **현재가 헤더** (270,000원) | `MARKET_DATA` | `tickPrice` 배치 `/prices` (200종목/호출) | 예 (완만) |
| **형성봉** (차트 우측 끝) | — | `refreshFormingBars` — 위 가격 재사용 | 아니오 |
| **차트 본체** (1분봉) | **`MARKET_DATA_CHART`** | 콜드 **36호출** / 예열 종목당 2회·30초 | **예** |
| 종목 기본정보 (이름·통화) | `STOCK` | `prefetchStockInfo` 배치 1회/틱 | 아니오 (배치) |
| **좌측 랭킹 목록** | `RANKING` | 폴러 5분 주기 · 고정 슬롯 | **아니오 (고정)** |
| 추세 점수 94 | — | DB만 | 아니오 |
| 전일종가·상하한가·52주 | `MARKET_DATA`/DB | `buildQuoteDetailFromToss` (캐시 우선) | 아니오 |

### 현재 소비량 (정정 포함)

앞서 `tickFast`를 "40종목 × 3호출 = 120"이라 적었는데 **정정한다.**
`buildQuoteDetailFromToss`의 `resolveBestLivePrice`가 캐시를 먼저 보므로
(`quotes_enrich.go:52`) 정상 상태에서는 가격 호출이 나가지 않는다.

```
tickFast  = 40종목 × 2호출(orderbook + trades)  =  80 req/s   ← MARKET_DATA
tickPrice = ceil(S/200)                          =  1~60 req/s ← MARKET_DATA
                                        ────────────────────────
                             MARKET_DATA 합계     =  81~140 req/s
```

**랭킹은 문제가 아니다.** 코드 주석이 이미 이유를 적어 뒀다
(`market_rankings_poller.go:39`) — *"every symbol on it draws from the same
RANKING rate-limit bucket regardless of user count"*. 5분 주기 고정이라
사용자가 10,000명이어도 그대로다. **화면에서 가장 많은 종목을 보여주는 부분이
정작 비용이 0에 수렴한다.**

## 웹소켓으로 덮이는 것과 안 덮이는 것

웹소켓 채널은 **`trade`와 `orderbook` 둘뿐**이다.

| 화면 요소 | 웹소켓 대체 | 비고 |
|---|---|---|
| 호가창 | ✅ `orderbook` 채널 | |
| 체결 목록 | ✅ `trade` 채널 | |
| 현재가 헤더 | ✅ `trade` 채널 | 체결가 = 현재가 |
| 형성봉 | ✅ `trade`로 서버가 직접 생성 | 오히려 지금보다 정확해짐 |
| **차트 본체 (과거 캔들)** | ❌ **불가** | `/candles`는 REST 전용 |
| 전일종가·상하한가·52주 | ❌ 불가 | **일 1회면 충분** — 하루에 한 번 바뀌는 값 |
| 종목 기본정보 | ❌ 불가 | **일 1회 배치**(`/stocks/all`)로 충분 |
| 랭킹 목록 | ❌ 불가 | **이미 고정 비용** — 손댈 필요 없음 |

> **결론: 웹소켓은 `MARKET_DATA`를 0으로 만든다. 그런데 `MARKET_DATA_CHART`는
> 그대로 남는다.** 그리고 그게 바로 우려하신 **"차트를 못 보는 상황"의 원인**이다.
> 웹소켓만 하고 멈추면 **rate-limit은 방지되지 않는다** — 위치만 옮겨간다.

## 최종 개선안 — 그룹별로 다른 처방

rate-limit을 **그룹 단위로** 없애야 한다. 각 그룹이 원인이 다르므로 처방도 다르다.

### ① `MARKET_DATA` → **웹소켓 구독** (호출 0)

`tickFast`의 80 req/s를 통째로 제거한다. 커버리지는 40 → 140종목으로 늘어난다.
남는 REST는 **요청-시점 신선도 보장**의 배치 갱신뿐인데, 이건
**동시 진입자 수**에 비례하고 single-flight로 접히므로 초당 한 자릿수다.

### ①-b 정정 — 1분봉의 **실시간 부분도 웹소켓으로 덮인다**

앞에서 *"`MARKET_DATA_CHART`는 웹소켓으로 못 옮긴다"*고 단정했는데 **너무 넓게 말했다.**
`/candles` 안에서도 성격이 갈린다.

| 캔들의 종류 | REST 필요? | 이유 |
|---|---|---|
| **과거 봉** (차트 최초 로드·스크롤) | **필요** | 지나간 것은 스트림에 안 온다 |
| **진행 중인 봉 + 새로 완성되는 봉** | **불필요** | **`trade` 프레임으로 서버가 직접 만들 수 있다** |

체결 프레임은 `price · volume · timestamp`를 준다. **1분봉 OHLCV는 그 체결들을
1분 단위로 접은 것**이다. 즉 구독 중인 종목은 **1분봉을 REST 없이 생성**할 수 있다.

이건 이미 절반이 구현돼 있다 — `refreshFormingBars`가 지금도 **가격 하나로
형성봉을 갱신**한다. 다른 점은 지금은 그 가격이 1초 폴링에서 오고, 앞으로는
체결 스트림에서 온다는 것뿐이다. 그리고 체결 스트림 쪽이 **거래량까지 정확**하다.

**주의 — LOSSY다.** 프레임이 드롭되면 그 봉의 거래량이 실제보다 작아진다.
→ **주기적 정합**이 필요하다: 구독 종목이라도 **5분에 한 번**(또는 장 마감 후 1회)
REST로 완성 봉을 받아 덮어쓴다. 종목당 30초 2호출이 **5분 1호출**이 되므로
그래도 **−90%**다.

### 현재 1분봉 REST 호출 주기 (실측 근거)

```
marketSlowPollInterval = 30초                     (market_poller.go:17)
tickSlow → slowTargets(= active 집합) 종목마다 refreshRawCandles

refreshRawCandles (quotes_marketdata.go:158):
  ├ 1m: intraday1mFetchTarget = gap분 + 15봉  → 30초 주기면 약 15~16봉 → 1호출
  └ 1d: candleFetchCount(1d)  = 200봉         → 항상               → 1호출
                                                              ─────────────
                                        활성 종목당  =  2호출 / 30초
```

`active`는 `Touch`된 심볼이고 TTL 5분(`marketActiveTTL`)이다. **상한이 없다.**

| 활성 종목 수 | `MARKET_DATA_CHART` req/s | 한도(~20/s) 대비 |
|---|---|---|
| 40 | 2.7 | 13% |
| 100 | 6.7 | 33% |
| 200 | 13.3 | **67%** |
| **400** (10,000 DAU 추정) | **26.7** | **133% — 초과** |

**여기에 콜드 첫 열람 36호출이 얹힌다.** 감사가 측정한
*"30분간 `/candles` rate-limit exceeded 343건"*이 이 둘의 합이다.

> **눈에 띄는 낭비 하나**: `1d`를 **30초마다 200봉씩** 다시 받는다.
> 일봉은 하루에 한 번 바뀌는데 하루 2,880번 받는 셈이다.
> `1m`에는 `intraday1mFetchTarget`이라는 델타 최적화가 있는데 **`1d`에는 없다.**
> 이것만 고쳐도 이 경로의 호출이 **절반**이 된다 — 변경도 작다.

### ② `MARKET_DATA_CHART` → **사용자 수와 분리** (핵심)

여기가 웹소켓이 못 덮는 부분이고, **차트 가용성 계약(2장)의 본체**다.
세 가지를 동시에 한다.

| 조치 | 효과 |
|---|---|
| **장중 예열 제거** (`tickSlow`) | 배경 소비 → **0**. 사용자 수 비례 성분이 사라진다 |
| **콜드 페치 36 → 12호출** (첫 화면 40봉) | 차트 1회 열람 비용 **−67%** |
| **DB 계층 우선 조회** | 적재된 종목은 **호출 0** (실측 7ms) |
| **배치 사전 적재** (마감 후·별도 인스턴스) | 미적재를 구조적으로 줄임. **고정 비용** |
| **전경 70% 예산 + 초 단위 재시도** | 남은 호출이 사용자 요청에 우선 배정 |

핵심은 **"차트를 여는 행위"와 "상류 호출"의 연결을 끊는 것**이다.
DB에 있으면 0호출이고, 배치가 미리 채워 두면 대부분 DB에 있다.

### ③ `STOCK` → **배치 + 마켓 판정** (거의 0)

- `/stocks/search`의 국내 종목 Toss 호출 제거 (3장 A0) — **조건문 하나**
- `prefetchStockInfo`는 웹소켓 전환 시 `tickFast`와 함께 사라진다
- 종목 카탈로그는 `/stocks/all`로 **일 1회** (스펙이 직접 권장)

### ④ `RANKING` → **조치 불필요** (이미 고정)

## 최종 예상 소비량

| 그룹 | 현재 (10,000 DAU 추정) | 개선 후 | 사용자 수 비례? |
|---|---|---|---|
| `MARKET_DATA` | **81~140 req/s** (한도 초과) | **~2 req/s** | 동시 진입자에만 (완만) |
| `MARKET_DATA_CHART` | 예열 + 콜드 36호출 (초과 빈발) | **~2 req/s** | 신규 차트 열람에만 |
| `STOCK` | 1/틱 + 검색마다 1회 | **~0** (일 1회 배치) | **아니오** |
| `RANKING` | 0.013 req/s | 그대로 | **아니오** |

> **이 네 가지를 다 해야 "rate-limit이 방지된다"고 말할 수 있다.**
> 웹소켓 하나만으로는 ①만 해결되고, 사용자가 늘면 ②에서 다시 터진다 —
> 그리고 ②가 터지는 증상이 정확히 **"차트가 안 뜬다"**이다.

## 그래서 순서가 이렇게 된다

```
①  웹소켓 (MARKET_DATA)          ← 가장 크고 가장 급함 (지금 429의 주범)
②  차트 (MARKET_DATA_CHART)      ← ①을 해도 남는 것. 차트 가용성의 본체
③  검색·카탈로그 (STOCK)         ← 0.5일짜리인데 효과가 큼. ①과 병렬
④  랭킹 (RANKING)                ← 조치 없음
```

**③을 먼저 두는 이유**: 마켓 판정 조건문 하나로 국내 검색의 Toss 호출이
0이 되는데, 그 호출이 `STOCK` 버킷을 `prefetchStockInfo`와 다투고 있다.
비용 대비 효과가 이 목록에서 가장 좋다.

# 6-4. 일봉 차트는 Toss 없이 DB만으로 가능한가 — 확인 결과

> 질문: *"`daily_close_domestic`/`daily_close_overseas`가 종가를 영구 저장하는데,
> 이걸로 일봉 차트를 Toss 호출 없이 다 가져올 수 있는 구조인가?"*

## 답: `stock_daily_closes`로는 **불가능**하다. 그러나 `candle_bars`로는 **이미 되고 있다**.

### (1) `stock_daily_closes`에는 OHLC가 없다

`migrations/029_daily_closes.sql:11`의 컬럼 전부:

```
close_price · prev_close · change_amount · change_rate · volume · currency
score · ai_summary · analysis_source · analyzed_at · source
```

**시가·고가·저가가 없다.** 캔들(봉)은 OHLC 네 값이 있어야 그린다.
첨부 화면은 빨강/파랑 **봉 차트**이므로 이 표로는 못 그린다 — **선차트만 가능**하다.

### (2) 이 표는 원본이 아니라 파생물이다

마이그레이션 머리말이 직접 못 박아 뒀다:

> *"These are **read-optimised projections, not a second source of truth**:
> closes are derived one-way **from candle_bars**"*

`batch_job.go:10`도 같다 — `daily_close_domestic`은
*"re-projects KRX stock daily closes **from candle_bars**"*.

즉 **`stock_daily_closes`는 `candle_bars`의 그림자**다. 원본이 사라지면 이것도 못 만든다.
용도는 종가 목록·수익률 계산·리서치 피드·점수이지 차트가 아니다.

### (3) 차트 읽기 경로는 이 표를 아예 보지 않는다

```
loadLatestCandlesFromDB  (candles_db.go:152) → s.candles = candle_bars
loadHistoricalFromDB     (candles_db.go:81)  → s.candles = candle_bars
```

## 그런데 진짜 소스인 `candle_bars` p_1d로는 이미 가능하다

**세 가지가 이미 갖춰져 있다.**

**① 일봉은 영구 저장이다.**
`057` 롤업은 **인트라데이만** 접는다(`p_1m`→`p_5m`→…→만료).
`p_1d` 파티션은 **롤업·삭제 대상이 아니다.**

**② 읽기 경로가 이미 DB 우선이다.**

```go
// GetCandlesPage — 첫 페이지
if snap, ok := s.EnsureCandleSnapshot(...); ok { return ... }   // 장 마감이면 DB 우선

// GetCandlesPage — 과거 페이지 (스크롤)
if page, ok := s.loadHistoricalFromDB(ctx, symbol, interval, before); ok {
    return ...                                                   // DB 히트면 Toss 안 감
}
// DB miss일 때만 Toss backfill
```

**③ 적재 파이프라인이 이미 있다 — 그것도 세 개.**

| 배치 | 대상 | 깊이 |
|---|---|---|
| `daily_close_fetch_missing` | 저장된 종가가 **아예 없는** 종목 | 최근 40봉 |
| `daily_close_fetch_stale` | 일부 세션이 **빠진** 종목 | 최근 40봉 |
| `daily_close_fetch_history` | 과거가 **부족한** 종목 | 200봉 × 8페이지 = **최대 1,600봉 ≈ 6.4년** |

그리고 이들이 **`candle_bars`에 쓴다** — `fetchSymbolDailyCloses` 주석:
*"persists them to candle_bars, and projects the ones at or after since"*.

> **결론: 일봉 차트는 이미 Toss 없이 DB에서 나올 수 있는 구조다.**
> 단 그 소스는 `stock_daily_closes`가 아니라 **`candle_bars`의 `p_1d`**이고,
> 조건은 **그 종목의 p_1d가 채워져 있는가** 하나다.

## 이 확인이 설계에 주는 것

### ㉠ 차트 폴백 사다리의 마지막 칸이 튼튼해진다

2장의 폴백 5번(*"정말 아무것도 없으면 일봉"*)이 **실제로 거의 항상 성립**한다.
일봉은 영구 저장 + 세 배치가 채우고 + 읽기가 DB 우선이다.
**가용성 계약의 바닥이 확인된 셈이다.**

### ㉡ ★ 인트라데이 사전 적재를 새로 만들 필요가 없다

2장에서 *"배치 사전 적재를 도입하자"*고 제안했는데, **이미 그 패턴이 완성돼 있다.**
`daily_close_fetch_*`는 필요한 것을 전부 갖췄다:

- 대상 선정 쿼리 (`SymbolsWithoutCloses` / `SymbolsStaleBefore` / `SymbolsHistoryIncomplete`)
- **재개 가능** — 매 실행이 남은 대상을 다시 조회한다
- **레이트리밋 페이싱** — 심볼 간 `delay`, `getCandlesWithRetry`가 429를 처리
- `limit`으로 1회 실행량 제한
- 배치 큐·관리자 콘솔 연동

> **인트라데이용은 같은 구조를 `Interval1m`으로 복제하면 된다.** 새 설계가 아니라
> **기존 잡의 인터벌 매개변수화**에 가깝다. 2장의 "배치 사전 적재" 예상 공수를
> 낮춰 잡아도 된다.

### ㉢ ★ 그런데 「전 종목 자동 적재」는 되고 있지 않다

*"사용자가 한 번도 안 눌러본 종목도 1d가 쌓이는가?"* — **대상은 전 종목이 맞지만,
그걸 채우는 잡이 자동으로 돌지 않는다.**

**대상 선정은 확실히 전 종목이다.** `SymbolsWithoutCloses`(`daily_close_fetch.go:34`):

```sql
SELECT st.symbol FROM stocks st
 WHERE st.status = 'NORMAL'
   AND NOT EXISTS (SELECT 1 FROM stock_daily_closes dc WHERE dc.symbol = st.symbol ...)
```

`stocks` 마스터 전체가 기준이다. 사용자 조회 여부와 **무관하다.**

**문제는 스케줄이다.** 이름이 비슷한 두 종류를 구분해야 한다:

| 잡 | 스케줄 | Toss 호출 | 실제로 하는 일 |
|---|---|---|---|
| `daily_close_domestic` / `_overseas` | **자동** (KRX/US 마감+20분) · 전 종목 | **없음** | `candle_bars` → `stock_daily_closes` **투영만** |
| `daily_close_fetch_missing` | **수동 (worker-fetch)** | 있음 | Toss → `candle_bars` + 투영 |
| `daily_close_fetch_stale` | **수동 (worker-fetch)** | 있음 | 〃 |
| `daily_close_fetch_history` | **수동 (worker-fetch)** | 있음 | 〃 |

`batch_admin.go:132·142·152` 세 곳 모두 `Schedule: "수동 (worker-fetch)"`다.

> **즉 자동으로 도는 잡(`daily_close_domestic`)은 Toss를 부르지 않고,
> `candle_bars`에 이미 있는 것을 투영할 뿐이다.**
> `candle_bars`에 오늘 1d 봉이 없으면 투영할 것도 없다.

### 그래서 실제 적재 경로는 둘뿐이다

```
① 사용자가 그 종목을 조회      → getCandlesPageUncached → persistRawCandles  [자동, 조회 시점]
② 운영자가 fetch 배치를 실행   → Toss → candle_bars                          [수동]
```

**아무도 안 보고 운영자도 안 돌리면 그 종목의 1d는 갱신되지 않는다.**

현재 상태는 아마 이럴 것이다 — **과거 어느 시점(수동 배치를 돌린 때)까지는
전 종목이 채워져 있고, 그 뒤로는 조회된 종목만 최신**이다.
`SymbolsStaleBefore`의 주석이 정확히 그 상황을 묘사한다:

> *"A symbol that already has July closes but stopped at 08-06 ... is exactly
> the gap a user notices: the latest session is missing while older ones are fine."*

### ㉣ 그래서 이게 새 작업 항목이 된다 — `daily_close_fetch_stale` 자동화

**㉠에서 "일봉 폴백은 거의 항상 성립한다"고 썼는데, 그 전제가 자동으로는
유지되지 않고 있다.** 가용성 계약의 바닥을 진짜로 보장하려면 이걸 자동화해야 한다.

**비용 계산:**

```
recentDailyCloseBars = 40봉,  Toss count 최대 200  →  종목당 1호출
전 종목 17,912 × 1호출 = 17,912 호출
MARKET_DATA_CHART 한도 ~20/s  →  약 15분 (마감 후, 배치 인스턴스에서)
```

**하루 15분이면 매우 싸다.** 비교하면 `warnings_sync`가 이미
*"전 종목 매일 (약 17,900 · **2시간**)"*을 `STOCK` 버킷에서 돌고 있다.
그것의 1/8 비용이다.

그리고 이 비용은 **사용자 수와 완전히 무관한 고정값**이다 —
사용자가 10배가 돼도 15분 그대로다. 이 문서 전체가 지향하는 성질과 정확히 맞는다.

**얻는 것:**

| | 지금 | 자동화 후 |
|---|---|---|
| 아무도 안 본 종목의 일봉 | 마지막 수동 배치 시점에 멈춤 | **매일 최신** |
| 일봉 차트 폴백 성립 여부 | 보장 안 됨 | **보장됨** |
| 첫 열람 시 Toss 호출 | 필요 | **불필요** (DB 히트) |
| 인트라데이 콜드도 개선 | — | 1d가 있으면 폴백 바닥이 확실 |

> `▶ 선택 6` — `daily_close_fetch_stale`을 **마감 후 자동 스케줄**로 올릴까요?
> **(a) 매일 자동** (권장 — KRX 마감+30분 / US 마감+30분, 각 약 15분) /
> **(b) 주 1회 자동** (비용 1/7, 최대 7일까지 낡을 수 있음) /
> **(c) 수동 유지** (현행)
>
> **(a)를 강하게 권합니다.** 차트 가용성 계약의 바닥이 이것 하나에 달려 있고,
> 비용이 사용자 수와 무관한 하루 15분입니다.
> 다만 `daily_close_fetch_missing`은 *"상장폐지·우선주 등 조회 불가 코드가 많아
> 실패율이 높습니다(정상)"*라 자동화 시 로그가 시끄러워질 수 있어
> **`stale`만 자동화**하고 `missing`은 수동으로 두는 것을 제안합니다.

### ㉤ 흔한 오해 정리 — 일봉은 **삭제되지 않는다. 구멍이 날 뿐이다**

*"조회된 종목만 쌓이고 나중에 롤업으로 삭제될 테니까"* 라는 이해가 나올 수 있는데,
**앞부분은 맞고 뒷부분은 반대다.**

**롤업은 일봉을 건드리지 않는다.** 계층표가 유일한 진실인데
(`candles_tiers.go:40`) 거기에 `1d`가 **없다**:

```go
var intradayTiers = []intradayTier{
    {model.Interval1m,  1,  3},   // 3일 뒤 5m으로
    {model.Interval5m,  5,  7},
    {model.Interval10m, 10, 14},
    {model.Interval30m, 30, 30},
    {model.Interval60m, 60, 60},  // 60일 뒤 삭제
}
const intradayTierMaxAgeDays = 60
```

오히려 **롤업이 일봉을 보호한다.** `candle_rollup.go:104` 주석:

> *"마지막 계층(60분봉)은 접지 않고 **지운다** — **1일봉은 이미 더 정확하게,
> 더 길게 있으므로** 접으면 그것을 덮어써 배치 입력까지 오염된다."*

즉 60분봉을 일봉으로 접지 **않는** 이유가 "일봉이 더 정확하고 더 길기 때문"이다.
**일봉은 영구 저장이고, 한 번 쌓이면 사라지지 않는다.**

### 그러면 진짜 문제는 무엇인가 — **시계열의 구멍**

```
사용자 조회 → Touch → active (TTL 5분)
           → tickSlow가 30초마다 그 종목의 1d 200봉을 받아 candle_bars에 저장
           → 마감+20분, daily_close_domestic이 전 종목 대상으로 투영
           → 결과: 그날 조회된 종목만 그날 종가가 남는다
```

**삭제가 아니라 누락이다.** 아무도 안 본 날의 봉이 처음부터 안 들어온다.
그런 날이 쌓이면 일봉 차트에 **띄엄띄엄 구멍**이 생긴다.

`SymbolsStaleBefore`의 주석이 정확히 이 증상을 적어 뒀다:

> *"A symbol that already has July closes but stopped at 08-06 ... is exactly
> **the gap a user notices**: the latest session is missing while older ones are fine."*

> **그래서 `daily_close_fetch_stale` 자동화(`▶ 선택 6`)의 목적은
> 「삭제 대비」가 아니라 「구멍 메우기」다.**
> 그리고 `tickSlow`가 30초마다 1d를 받는 지금 방식은 —
> 조회 중인 종목에는 과잉이고(하루 2,880회), 조회 안 된 종목에는 0이다.
> **정확히 거꾸로 된 배분**이다. 배치로 옮기면 둘 다 고쳐진다.

### ㉥ 새로 측정할 것 (V-리스트에 추가)

| # | 확인할 것 | 방법 |
|---|---|---|
| **V7** | **`candle_bars` p_1d의 종목 커버리지** | `SELECT COUNT(DISTINCT symbol) FROM candle_bars PARTITION (p_1d)` vs `stocks` 17,912 |
| **V8** | 커버된 종목의 **평균 히스토리 깊이** | 심볼별 `MIN(bar_time)` 분포 |
| **V9** | 장중에도 일봉 과거 구간이 DB에서 나오는가 | `shouldLivePollSymbol`이 true일 때의 경로 확인 |

**V7이 중요하다.** 이 값이 낮으면 폴백 사다리의 바닥이 생각보다 얇다는 뜻이고,
`daily_close_fetch_missing`을 더 자주 돌려야 한다.
`HistoryIncompleteCount`가 **이미 구현돼 있으므로** 지표로 노출만 하면 된다.

# 7. 통합 우선순위

## ★ 정정 — 웹소켓을 뒤에 둔 것은 제 판단 착오였다

앞선 순서에서 웹소켓을 16번(약 5~6주 뒤)에 뒀는데, **근거가 틀렸다.**

당시 논리는 *"Tier 구조(15번)를 먼저 세워야 웹소켓이 안전한 교체가 된다"*였다.
그런데 **두 작업은 서로 독립이다.**

| 폴러 | 대상 | 대체 수단 |
|---|---|---|
| `tickFast` — 호가·체결·형성봉, 40종목, **120 호출/틱** | `active` 집합 (`Touch`) | **웹소켓 구독** |
| `tickPrice` — 가격, pinned 전체 | pinned | **Tier 구조 (F+H)** |

**웹소켓이 대체하는 것은 `tickFast`이고, Tier 구조가 최적화하는 것은
`tickPrice`다.** 서로 건드리는 코드가 다르다. 웹소켓은 Tier 구조를
기다릴 이유가 없다.

그리고 **`tickFast`가 `MARKET_DATA`의 압도적 주 소비자**다(120 호출/틱 vs
`tickPrice`의 1~60). 즉 **웹소켓이 가장 큰 문제를 가장 먼저 없앤다.**

### 웹소켓 교체가 실제로 건드리는 것

이미 있는 배관에 공급원만 바꿔 끼우는 일에 가깝다:

```
지금:  tickFast → refreshTerminalSnapshot → publishQuoteUpdate  → streamHub → SSE
                                          → refreshFormingBars

이후:  웹소켓 trade 프레임 ──────────────→ publishQuoteUpdate  → streamHub → SSE
                          ──────────────→ refreshFormingBars
       웹소켓 orderbook 프레임 ─────────→ 터미널 스냅샷의 호가 부분
```

- 구독 대상 = 지금의 `active` 집합. **새 개념이 아니다**(`Touch`가 이미 채운다).
- `capActiveTargets(active, 40)` → 구독 슬롯 **140**으로 확대.
- fan-out은 `streamHub`가 이미 한다 — **손댈 필요 없다.**

**단, 하나 남는다**: `trade` 프레임은 `price·volume·timestamp·currency`만 준다.
`QuoteDetail`의 **전일종가·상하한가·세션**은 안 온다. 그런데 이 값들은
**하루에 한 번 바뀌므로** 일 1회 + 세션 전환 시점에만 REST로 받으면 된다.
지금은 이걸 **1초마다** 다시 받고 있었다.

## 개정된 순서

| # | 작업 | 출처 | 선행 | 기간 |
|---|---|---|---|---|
| 0 | **실측·검증 V1~V6** (특히 **V2 웹소켓 별도 예산**) | 1장 | `▶선택 0` | 0.5일 |
| 1 | **`/stocks/search` A0 — 마켓 판정** (국내 Toss 호출 0) | 3장 | 없음 | **0.5일** |

## 하드웨어를 올릴 경우 달라지는 것

`[HW]`로 표시한 판단만 재검토하면 된다. 나머지는 하드웨어와 무관하다.

| 항목 | 지금 판단 | 하드웨어 상향 시 |
|---|---|---|
| P1-9 커넥션 풀 | API 16 / 워커 3 (1 ECPU 기준) | ECPU를 올리면 **비례 상향 가능** |
| P1-5 ngram FULLTEXT | **기각** (버퍼풀 4 GiB) | 메모리·IOPS 상향 시 **재검토 가치 있음** |
| P2-12 백업 테이블 | **즉시 드롭 권장** | 급하지 않아짐 (그래도 드롭이 맞다) |
| Redis `maxmemory` 1 GB | 상향 여지 있음 | 그대로 상향 |
| 차트 폴백 빈도 | DB 조회 7ms 전제 | 더 낮아짐 — **설계는 불변** |

**웹소켓·Tier 구조·검색 비동기화·차트 폴백 계약은 하드웨어와 무관하게 옳다.**
상류 API 한도는 하드웨어를 올려도 그대로이기 때문이다.
