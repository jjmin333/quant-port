「Redis 장애 시 API 500 금지」는 **원칙으로만 있었다.** 실제로 Redis를 내려 보니

전역 요청 예산(10초)이 먼저 끝났다.

## 1. 실측이 원칙과 달랐다

AGENT_STATE 개발 원칙 5는 「Redis 장애 시 API 500 금지 — MySQL 폴백」이다.
2026-09-09에 Redis 컨테이너를 내리고 재 봤다.

```
/api/v1/stocks/scores/top          200  0.007초   ← 폴백 정상
/api/v1/quotes/indices             200  0.002초   ← 폴백 정상
/api/v1/news/domestic              200  0.057초   ← 폴백 정상
/api/v1/stocks/005930/summary      502  10.003초  ← 실패
/api/v1/quotes/005930/terminal-snapshot 404 10.004초 ← 실패
```

**폴백은 있었다.** 목록·지수·환율·랭킹은 전부 정상이었다. 문제는 나머지 둘이
폴백까지 가는 데 걸린 시간이고, 그 10초가 `REQUEST_TIMEOUT_SECONDS`(기본 10)를
넘겨 502가 됐다. 사용자에게 10초 멎은 화면은 500과 다르지 않다.

## 2. 원인이 둘 겹쳐 있었다

**㉠ go-redis 기본 타임아웃이 장애용이 아니다.** `DialTimeout 5초` · `MaxRetries 3`.
정상 다이얼은 같은 도커 네트워크에서 1ms 미만이라, 5초는 오직 장애일 때만 쓰이는 값이다.

**㉡ DNS가 실패를 늦춘다.** 컨테이너가 없으면 `redis`가 NXDOMAIN이어야 하는데,
도커 리졸버가 호스트 상위 DNS로 넘기고 **ISP가 와일드카드로 자기 IP를 돌려준다**
(실측 `dial tcp 218.38.137.27:6379: i/o timeout` — `quant-port.com`을 가로채던 그 IP다).
「없는 호스트」가 아니라 「응답 없는 호스트」가 되어 다이얼이 타임아웃 끝까지 간다.

## 3. 타임아웃만으로는 부족했다

500ms로 줄이고 다시 쟀더니 **그대로 10초였다.** 한 요청이 Redis를 여러 번 부르기
때문이다 — 호출당 비용이 10분의 1이 되어도 호출 수만큼 곱해지면 예산을 다시 넘는다.

고쳐야 할 것은 「한 번의 실패를 얼마나 빨리 아는가」가 아니라
**「이미 아는 실패를 몇 번 다시 확인하는가」**였다.

### 회로 차단기 (go-redis 훅)

연속 실패 2회면 5초 동안 회로를 열고, 그동안의 명령은 **네트워크를 건드리지 않고
즉시 오류**를 돌려준다. 호출부는 평소의 Redis 오류와 똑같이 보므로 **26곳의 호출부를
하나도 고치지 않았다** — 훅이 클라이언트 한 곳에 붙어 전부를 덮는다.

### 실패/성공 판정을 셋으로 가른다

이게 이 변경에서 가장 까다로운 부분이었다. 처음에 둘로 갈랐더니 회로가 **5초마다
열렸다 닫혔다 진동**했다.

	nil · redis.Nil          → 살아 있다     (회로를 닫는다)
	연결 실패 · 타임아웃       → 죽었다       (회로를 연다)
	그 밖(프로토콜·명령 오류)   → 알 수 없다   (아무것도 하지 않는다)

셋째 칸이 필요한 이유: **ISP 가로채기 서버가 6379 TCP를 받아 준다.** 그래서 다이얼이
성공하고 Redis 프로토콜에서 실패하는데, 그 오류는 `net.Error`가 아니다. 「실패가
아니다 = 성공」으로 접으면 회로가 닫히고 다음 호출이 다시 대기 비용을 문다.

같은 이유로 **다이얼 성공은 회로를 닫지 않는다.** 회로를 닫아도 되는 근거는
「연결이 됐다」가 아니라 **「Redis가 명령에 답했다」**뿐이다.

`redis.Nil`(캐시 미스)을 실패로 세지 않는 것도 중요하다 — 세면 평소에 회로가 열려
캐시가 통째로 꺼지고, 부하가 전부 MySQL로 간다(운영 DB는 1 ECPU다).
