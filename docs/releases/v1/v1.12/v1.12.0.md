「사용자가 적은데도 가끔 엄청 느리다」의 원인을 실측으로 짚었다 — **캐시가 막 만료된

## 1. 「가끔씩 엄청 느려진다」 (사용자 지적 6)

### 무엇을 쟀나

마감 중 `/quotes/005930/terminal-snapshot`을 20회 연속으로 불렀다.

```
0.302  0.004  0.005  0.006  0.005  0.005  0.005  0.004  0.008  0.005
0.215  0.004  0.005  0.010  0.006  0.004  0.005  0.005  0.005  0.009
```

대부분 1.3~2ms인데 **서너 번이 200~300ms**다. 150배 차이가 규칙 없이 섞여 있고,
사용자 수와 무관하다 — 혼자 쳐도 이 모양이다.

### 원인

느린 쪽이 **캐시가 막 만료된 요청**이었다. 이 스냅샷의 Redis TTL이 1초라, 만료된
요청은 캐시에 아무것도 없는 상태로 상류(Toss)를 **동기로 부르고 기다렸다**. 그 200ms가
왕복 시간이다.

### 고친 것 — 낡은 값을 주고 뒤에서 새로 만든다

「사는 시간」과 「신선한 시간」을 나눴다. Redis TTL은 60초(`terminalSnapshotTTL`),
신선한 것은 그중 앞의 1초(`MarketDataQuoteCacheSec`)다. 신선하지 않으면 **그 값을 주고
갱신만 뒤로 보낸다**. 화면이 어차피 1초마다 묻고 있으므로 한 박자 전 값을 받는 것이
한 박자 기다리는 것보다 낫다.

캐시에 아무것도 없을 때(그 종목을 처음 열었을 때)만 예전처럼 기다린다.

**결과** — 25회 중 첫 요청(콜드)만 290ms, 나머지 24회가 4.6~11.7ms:

```
0.005 0.005 0.005 0.005 0.005 0.005 0.005 0.005 0.005 0.006
0.006 0.006 0.006 0.006 0.006 0.006 0.006 0.006 0.006 0.007
0.008 0.009 0.010 0.012 0.291
```

`loadQuoteDetailFromTerminalCache`(상세 헤더 가격을 정하는 사다리의 한 칸)는 **신선함을
다시 본다** — 60초 된 값을 「지금 값」으로 올리면 v1.11.0에서 고친 「목록과 상세가
다른 가격」이 되살아난다.

### 토스 한도를 배치가 혼자 쓰고 있었다

기동 로그에 이런 줄이 여섯 개 있었다:

```
toss api rate-limit low: GET /api/v1/rankings key=primary limit=5 remaining=1 resetSec=1
```

토스 한도는 **자격증명 하나당 1초에 5회**인데, 랭킹 배치의 호출 간격이 100ms(초당 10회,
키 둘을 번갈아 쓰므로 키마다 정확히 5)였다. `remaining=1`은 그 1초 창에 사용자 요청이
하나 들어올 자리밖에 없다는 뜻이다.

200ms로 늘렸다 — 키마다 초당 2.5회로 **창의 절반을 사용자 요청에 남긴다**. 기동 첫
적재가 0.8초에서 1.6초로 늘지만 그 값은 아무도 안 본다(화면은 DB·Redis만 읽는다).

**결과**: 기동 시 rate-limit 경고 **6건 → 1건**(남은 하나는 지수 캔들 경로).

## 2. 한 화면이 같은 것을 여러 번 묻던 것 (사용자 지적 6)

### `/quotes/batch` 다섯 번 → 한 번

비로그인 홈 한 화면에서 나가던 배치 요청:

```
symbols=000660,005930,069500,386380,122630,009150,102110,360750   (8)
symbols=000660,005380,005930                                      (3)
symbols=000950,004960,0091W0,019175,044780,047080,053950,073570   (8)
symbols=ADBE,CPRT,FDX,KR,ORCL,SUNB                                (6)
symbols=000660,005930,009150,069500,102110,122630,360750          (7)
```

**000660과 005930이 다섯 중 넷에 들어 있다.** 이 경로는 종목당 1 SELECT라 서른두 번
푼 것이 실제로는 스물세 종목이었고, 운영 DB는 1 ECPU다.

`cachedGet`이 이미 있었지만 키가 **URL 전체**라 심볼 목록이 한 글자만 달라도 다른
키였다. `lib/quote-batch`가 짧은 창(40ms) 안의 요청을 합쳐 한 번 부르고, 받은 행을
**종목 단위로** 적어 둔다 — 목록이 조금씩 다른 카드들이 서로의 결과를 쓴다.

### 가격 SSE 넷 → 둘

같은 이유로 연결도 넷이었다. `lib/list-price-hub`가 시장마다 하나씩 들고, 구독자들의
심볼을 합쳐 연결 하나를 연다. 합집합이 바뀌어도 60ms 기다렸다가 여는데, 카드들의 목록이
한 프레임에 다 채워지지 않아서 기다리지 않으면 카드 수만큼 열었다 닫는다.

**마감 중에는 아예 열지 않는다.** 예전에는 카드가 뜰 때마다 `reconcile`이 「연결이
없네」를 보고 다시 열고 서버는 그때마다 `session` 하나를 주고 끊었다 — 홈 한 화면
20초에 여섯 번이었다. 답이 「월요일 08:00에 열립니다」로 정해져 있는데 여섯 번 물은
셈이다.

### `auth/refresh` 폭주

비로그인 사용자에게 401은 정상이다. 그런데 `sessionFetch`가 401마다 갱신을 시도해서,
관심·보유·스탬프를 물을 때마다 `POST /auth/refresh`가 따라 나갔다 — 쿠키가 없으니
**답이 바뀔 수가 없는** 요청이다. 한 번 401·403을 받으면 그 뒤로는 묻지 않는다(로그인·
회원가입이 성공하면 다시 열린다). 5xx·네트워크 실패는 굳히지 않는다.

### 보유 화면의 열두 요청

보유 레일의 「다가오는 일정」만 배치를 안 쓰고 상위 12종목을 종목당 한 번씩 불렀다.
09-04에 관심·뉴스 화면은 `useUpcomingEvents`(배치 하나)로 옮겼는데 이 카드만 남아
있었다. **실측: 배치 1건 · 종목별 0건.**

### 합계

비로그인 홈 한 화면(16초):

| 엔드포인트              | 전 | 후 |
| ----------------------- | -- | -- |
| `quotes/batch`          | 5  | 1  |
| `quotes/prices/stream`  | 4+ | 2  |
| `auth/refresh`          | 401마다 | 1 |
| 그 외 (각 1건)          | —  | 10 |

## 3. 백그라운드 탭에서도 SSE를 유지한다 (사용자 요청 5)

가격 스트림 셋(목록 가격·상세 체결·봉)이 전부 `visibilitychange`에서 연결을 닫았다.
탭을 잠깐 옮겼다 돌아오면 다시 붙는데, 붙는 데 드는 것(요청·구독 등록·스냅샷 한 벌)이
붙어 있는 데 드는 것보다 훨씬 무겁다.

이제 숨는 것만으로는 끊지 않고 **3시간**(사용자 지정) 뒤에 놓는다. 판정은
`lib/stream-awake`가, 시계는 `hooks/use-stream-awake`와 허브가 맡는다. 다시 보일 때는
**죽어 있는 연결만** 되살린다 — 살아 있는 것을 다시 열면 스냅샷을 한 벌 더 받는 셈이라
끊지 않으려고 한 일을 스스로 되돌린다.

**폴링은 그대로 숨으면 멈춘다.** 스트림은 서버가 이미 만들어 둔 값을 밀어 주는 것이라
뷰어가 늘어도 DB 작업이 0이지만, 폴링은 왕복이 뷰어 수에 정비례한다.

## 4. 홈 지수 카드를 눌러도 모달이 안 뜨던 것 (사용자 지적 3)

범인은 `setPointerCapture` 한 줄이었다. 띠를 끌 수 있게 하려고 `pointerdown`에서 곧바로
포인터를 잡았는데, **포인터가 잡혀 있으면 브라우저는 뒤이어 오는 `click`을 누른 요소가
아니라 잡은 요소**(스크롤 뷰포트 div)에 보낸다. 셀 버튼의 `onClick`은 한 번도 불리지
않았다.

원인이 오래 안 잡힌 이유가 여기 있다 — 스크립트로 `cell.click()`을 부르면 모달이
정상적으로 열린다(캡처는 실제 포인터 입력에만 걸린다). 컴포넌트도 모달도 멀쩡한데
손으로만 안 되는 모양이라 「가끔 안 눌린다」로 보였다.

지금은 **4px 문턱을 넘긴 순간에** 잡는다. 덤으로 **손을 대고 있는 동안 띠를 멈춘다** —
멈춤 조건 셋(hover·포커스·모달)이 전부 PC의 것이라 터치에서는 아무것도 멈추지 않았고,
누른 셀과 뗀 셀이 다르면 `click`은 두 요소의 공통 조상(컨테이너)으로 간다.

**키워드 칩은 카드에서 하나만.** 「데스크톱 둘, 모바일 하나」였는데 데스크톱에서도
둘째 칩이 지수 이름을 덮었다 — 셀 폭이 224px 고정이고 이름만 `flex-1 truncate`라 칩이
하나 더 들어오면 줄어드는 것은 언제나 이름이다. 나머지 키워드는 눌러서 여는 지수
모달이 그대로 받는다.

## 5. 홈 뉴스 — 줄 수와 잘린 칩 (사용자 지적 2)

**줄 수**: 폰 5 · 태블릿 8 · PC 14(사용자가 정한 단계). PC에서 열넷인 이유는 옆 브리핑
카드의 높이를 채우기 위해서인데, 좁은 화면에서는 카드가 위아래로 쌓여 맞출 상대가
없다. **받는 개수는 그대로 열넷**이고 CSS로 감춘다 — 요청 URL이 폭마다 달라지면 캐시가
갈라지고, 폭을 재서 정하면 하이드레이션이 깨진다.

**잘린 칩**: 「코…」·「메리츠금…」처럼 한두 글자로 뭉개져 무슨 종목인지 못 읽었다.
측정 줄은 칩을 최대 셋까지만 그리는데, 기사에 걸린 칩이 열한 개면 화면에는 셋 옆에
**「+8」이 함께** 그려진다. 그런데 계산은 「보여줄 개수 = 잰 개수」인 경우 숨김을 0으로
보고 그 「+8」의 폭을 **빼먹었다**. 모자란 폭만큼 flex가 칩들을 눌러 줄인 결과가 「코…」다.

이제 숨김 수를 **총 개수 기준**으로 세고, 칩에 `shrink-0`을 줘서 눌리지 않게 했다.
하나도 안 들어가면 0개를 그린다 — 「+11 · 11분 전」이 뭉개진 이름보다 많은 것을 말한다.

## 6. 상단 가격과 차트 가격 (사용자 지적 4)

lightweight-charts는 축 오른쪽 끝에 **마지막 봉의 종가**를 적는다. 헤더는
`detail.currentPrice`(체결·호가·배치 캐시를 거친 값)라 **두 값이 서로 다른 길에서 온다.**

평소에는 형성 중인 봉을 화면이 현재가로 덧칠해서 둘이 같다(`applyLivePrice`). 그런데 그
덧칠은 **형성봉이 있을 때만** 되고, 서버가 형성봉을 안 주는 구간(일봉의 장 초반,
프리·애프터 세션)에서는 표가 조용히 어제 종가에 머문다.

그래서 표를 **헤더와 같은 값에 직접 묶었다**(`CandlestickChart`의 `livePrice`). 봉
데이터는 건드리지 않는다 — 일봉의 종가는 정의가 있는 값이라 시간외 가격으로 덮으면
그건 다른 종류의 거짓이다.

> **남은 확인**: 이 세션은 토요일(마감)이라 두 값이 원래 같았다. 갈라지는 구간(장 초반·
> 프리·애프터)의 실측은 개장 중에 확인해야 한다.

## 7. 비로그인 저장 버튼의 문구 (사용자 요청 1)

창 안의 저장 버튼은 셋 다 「로그인하고 저장」이었다. 제목은 창을 열 때 한 번 읽고 눈은
버튼으로 내려가므로, 그 자리에서 무엇을 하는지 말해야 하는 것은 버튼 쪽이다.

- 스탬프 폼 → **「로그인하고 스탬프 남기기」**
- 보유 추가 → **「로그인하고 포트폴리오 관리하기」**
- 목표가 → **「로그인하고 목표가 관리하기」**

**비활성화하지 않는다**(사용자 선택: 셋 다 목표가 모달과 같은 방식). 완전히 잠그면
비로그인 사용자는 로그인으로 갈 길을 그 자리에서 잃는다. 목적인 「401 원천차단」은
요청을 안 보내는 것으로 이미 달성된다.

규칙이 **폼 자신에게** 붙은 것이 이번 변경의 핵심이다. 예전에는 폼을 여는 버튼이
막았는데, 그건 버튼이 아는 규칙이라 다른 자리에서 폼을 띄우면 함께 오지 않는다 —
실제로 보유 화면의 「예시로 둘러보기」로 들어가면 활성 버튼이 그대로 보였다.
