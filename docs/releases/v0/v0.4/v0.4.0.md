## 1. 한 줄 요약

마켓 레이더/종목 상세 화면에서 헤더 주가와 일봉 차트 가격이 서로 다르게 보이던 문제를 **서버가 가격을 두 번 다른 알고리즘으로 계산하던 구조적 원인**부터 수정했습니다. 이어서 백엔드 로그를 뒤덮던 Toss API 429(rate-limit) 폭주를 실측 기반으로 추적해, `/api/v1/candles` 호출량을 **30초당 최대 36페이지 → 1페이지**로 줄이고, 실사용자가 보고 있지 않은 관심종목의 호가·체결 갱신을 제거해 **활성 조회 종목 수**에만 비용이 비례하도록 재설계했습니다.

## 3. 문제 1 — 헤더·차트 가격 불일치

### 원인

같은 심볼의 "현재가"를 한 틱 안에서 **두 함수가 각자 다른 정교함으로** 계산하고 있었습니다.

- 헤더(`quote_update`): `refreshTerminalSnapshot` → `rehydrateQuoteDetailWithSources` — 가격이 전일종가와 우연히 같아 보이면 `directTossPrice`/랭킹 마지막가로 보정하는 로직 포함
- 차트 forming 봉(`bar_update`): `refreshFormingBars`가 이 보정 없이 단순 `resolveBestLivePrice`를 **독립적으로 재호출**

추가로 일봉 `forming` 봉 분리 로직(`splitFormingCandle`)이 "배열 마지막 원소가 최신 봉"이라고 가정했는데, Toss 일봉 API는 **최신순(내림차순)** 응답이라 실제로는 항상 1년 전 봉을 검사하고 있었고, 그 결과 `bar_update` SSE가 아예 발행되지 않는 경우도 있었습니다.

### 수정

- `market_poller.go`: `refreshTerminalSnapshot`이 계산한 `detail.CurrentPrice`를 `refreshFormingBars`에 그대로 전달 — 같은 틱 안에서 숫자가 구조적으로 동일
- `splitFormingCandle`/`lastCompletedTime`/`applyLivePriceToCandleSnapshot`: 배열 순서에 의존하지 않고 **시간 값으로 최신 봉 탐색**하도록 변경
- FE `use-quote-candles.ts`: SSE가 죽어 있어도(개발 프록시가 스트림을 버퍼링하는 경우 실측 확인) 회복되도록 **2초 REST 폴백** 추가; 헤더 가격을 forming 봉에 직접 오버레이하는 안전망(`applyLivePrice`)도 함께 추가

## 4. 문제 2 — Toss API 429 폭주

### 실측 (수정 전, 10분 표본)

```
/api/v1/candles     1,903건 (94%)  ← 압도적 1위
/api/v1/trades          48건
/api/v1/orderbook       36건
/api/v1/stocks           7건 (직전 세션에 이미 배치화)
```

### 원인 1 — `/api/v1/candles`: 마감된 봉을 30초마다 재조회

`refreshRawCandles`가 1분봉 7,200개(`maxIntradayRawBars`)를 목표로 매 30초 tick마다 요청. Toss 캔들 API는 배치가 없고 페이지당 최대 200봉이라 **심볼당 36페이지**. 그런데 이 7,200봉의 대부분은 이미 마감되어 MySQL `candle_bars`에 저장돼 있는 불변 데이터였습니다.

```
13개 추적 심볼 × 37회(1분봉 36 + 일봉 1) ÷ 30초 = 16.0 회/초   vs 한도 5회/초 → 320% 초과
```

같은 패턴이 시세 통계 계산(`fetchIntradayStats`, 시가/고가/저가/거래량)에도 별도로 있었습니다 — 60초 캐시가 만료될 때마다 `GetCandles(Count:480)`을 직접 호출.

### 원인 2 — `/api/v1/trades`, `/api/v1/orderbook`: 조회하지 않는 종목도 갱신

`refreshTerminalSnapshot`(호가+체결+종목정보 전체 조회)이 **관심종목·보유종목이면 실제로 보고 있지 않아도** 5초마다 실행되고 있었습니다. 사용자가 아무도 안 보고 있는 화면의 호가창을 5초마다 새로고침하던 셈입니다.

### 수정

| 파일 | 변경 |
|------|------|
| `be/internal/service/candles_intraday_delta.go` (신규) | DB의 마지막 저장 봉 시각 확인 → 그 갭(+15분 버퍼)만큼만 Toss 요청. DB 이력과 병합해 집계·캐시·페이지네이션 커서는 기존과 동일한 깊이 유지 |
| `be/internal/service/quotes_marketdata.go` | `refreshRawCandles`가 델타 페치 사용하도록 통합 |
| `be/internal/service/quotes_enrich.go` | `fetchIntradayStats`: DB에 오늘자 1분봉 있으면 그걸로 계산, 콜드스타트만 Toss 호출 |
| `be/internal/service/quotes_stock_batch.go` (신규) | `/api/v1/stocks` 틱당 1회 배치 조회 (직전 세션에 적용, 이번 릴리스에 포함) |
| `be/internal/service/market_poller.go` | `tickFast`: 호가·체결·forming봉 전체 갱신을 **실제로 조회 중인(active) 심볼로만** 제한. 관심·보유(pinned)는 배치 가격 호출로만 신선도 유지 |
| `be/internal/service/quotes_background.go` | `triggerQuoteStatsRefresh`: 캐시 TTL이 아직 넉넉하면(20초 이상) 재요청 스킵 — 30초 tick이 60초 캐시를 절반쯤 헛돌게 하던 것 제거 |
| `be/internal/toss/rate_limit.go` (신규) | 모든 Toss 응답의 `X-RateLimit-*` 헤더 파싱·로깅 — 429가 나기 전에 잔여량 경고 |
| `be/internal/toss/errors.go`, `client.go` | `toss.Error.RetryAfter` 필드 추가, 429 응답 헤더에서 실제 대기 시간 파싱 |
| `be/internal/service/quotes_toss_retry.go`, `market_data_store.go` | 고정 2초/60초 대기 대신 서버가 알려준 실제 값 사용; 죽어있던 `parseRetryAfterHeader`(호출되는 곳 없던 함수) 제거 |

### 실측 (수정 후)

```
/api/v1/trades       0건  (75건 → 0)
/api/v1/orderbook    0건  (59건 → 0)
/api/v1/stocks      낮음  (49건 → 7건, 직전 세션 대비 유지)
/api/v1/candles     크게 감소 (94% 비중 → 소수 비중; 컨테이너 재기동 직후
                     장시간 오프라인 격차를 따라잡는 구간 제외하면 심볼당
                     30초 1페이지 수준으로 수렴)
```

컨테이너를 재기동한 뒤 실제로 심볼 하나(000660)가 **9시간치 격차**를 안고 있는 상태를 관측했는데, 델타 페치 로직이 이를 상한선(`maxIntradayRawBars`) 안에서 안전하게 따라잡고 몇 tick 만에 정상 델타 크기로 수렴하는 것을 확인했습니다 — 설계가 의도한 그대로였습니다.

## 5. 1000배 트래픽 대비 — 무엇이 바뀌었는가

| 데이터 | 이전 확장 성질 | 이번 릴리스 이후 |
|--------|----------------|------------------|
| 관심·보유종목 호가/체결 | **관심종목 수**에 비례 (배치 불가 API) | **동시 조회 중인 종목 수**에만 비례 — 관심종목이 아무리 늘어도 아무도 안 보면 비용 0 |
| 현재가 | 이미 배치(200개/요청) | 변화 없음 — 이미 안전 |
| 1분봉/일봉 | tick마다 전량 재조회 | **DB 이후 델타만** — 추적 대상 늘어도 tick당 비용은 갭 크기에만 비례 |
| 종목 기본정보 | 이미 배치 (직전 세션 수정) | 변화 없음 |

**남은 구조적 한계** (설계 문서 phase 4, 이번 릴리스 범위 밖):
- `PortfolioService.AllTrackedSymbols`가 활성 브로커 연동 사용자 수만큼 순회 — 다만 1분 캐시로 이미 스로틀되어 있어 긴급도는 낮음
- 계좌/잔고 조회는 Toss `ACCOUNT` 그룹이 사용자당 1건이라 근본적으로 사용자 수에 비례 — 실시간성을 포기할 지점을 제품 차원에서 정해야 함
- 폴러 자체의 다중 인스턴스(리더 선출/샤딩) 대비는 미착수
