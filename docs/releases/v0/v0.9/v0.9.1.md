## 1. 한 줄 요약

발표일 종가와 반응 종가를 **시각이 아니라 달력일(YYYY-MM-DD)** 로 짝 맞춘다. MySQL DATE가 KST 0시로 스캔되고 발표일 문자열은 UTC 0시라, `Equal`/`Before`가 9시간 차이로 장전·장중을 전부 놓쳤다.

---

## 2. v0.9.0 → v0.9.1 변경 요약

| 영역 | v0.9.0 | v0.9.1 |
|------|--------|--------|
| 장전·장중 반응 | 당일 종가가 있어도 `Equal` 실패 → 「집계 중」 | 같은 달력일이면 당일 종가로 계산 |
| 장후 반응 | 이미 대체로 숫자 (Before/After가 우연히 맞음) | 달력일 비교로 동일. 다음 세션 미마감은 그대로 집계 중 |
| `gapDays` | `Hours()/24` (TZ 섞이면 하루가 줄어듦) | 달력일 차 |
| FE package | `0.9.0` | `0.9.1` |

실측(수정 전, 이번 주 확정): 장전 49/49 nil, 장후 24/27 숫자. TGT·HD·LOW·ADI는 발표일 종가가 DB에 있었음.

---

## 3. 원인

DSN `loc=Asia/Seoul`이 `stock_daily_closes.trade_date`를 KST 자정으로 스캔한다. `reactionFor`는 발표일을 UTC 자정으로 파싱한다. 같은 8/12라도 `time.Time.Equal`은 거짓이다.

- 장전·장중: `closeOn`이 당일 종가를 못 찾음 → nil → 「집계 중」
- `closeOn`만 고치면 `lastCloseBefore`가 발표일 종가를 기준으로 집어 **0%**
- 장후는 `Before`/`After`가 9시간 어긋나도 방향이 맞아 대부분 통과

종가 백필은 이 버그의 전제가 아니다. 8/19·8/20처럼 종가 행 자체가 없는 소형주만 따로 남는다.

---

## 4. 수정

`be/internal/service/earnings_reaction.go`: `calendarDay` / `cmpDay`로 `closeOn` · `lastCloseBefore` · `lastCloseOnOrBefore` · `firstCloseAfter` · `gapDays`를 통일. 반응 JSON의 날짜도 달력일.

테스트: UTC 기존 케이스 + KST 스캔 재현(장전 9.1%·장후 −25%·0% 금지) + `gapDays` 5일.
