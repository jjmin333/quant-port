## 3. 왜 EDGAR가 필요했나

`/stock/earnings`가 주는 날짜는 **달력 분기로 반올림한 기간말**이지 발표일이 아니다. 그대로 캘린더에 올리면 네 날짜에 몰린다:

| 기간말 | 종목 수 |
|---|---|
| 2026-06-30 | **3,007** |
| 2026-03-31 | 2,959 |
| 2025-12-31 | 2,894 |
| 2025-09-30 | 2,841 |

아무도 그날 발표하지 않았다. 미국 상장사는 실적을 **8-K Item 2.02**로 공시하고, `data.sec.gov/submissions`가 제출일과 접수 시각을 종목당 1호출로 준다.

### 매칭 규칙과 방어

기간말 기준 **가장 가까운 미사용 8-K**를 1:1로 짝짓고, 간격 **60일** 초과는 버린다(실측 −48~+48일. 분기 간격 90일이라 옆 분기를 안 침범한다). 45일로 잡았다가 AMAT(48일)을 놓쳐 넓혔다.

**단조성 위반이면 그 종목을 통째로 버린다.** 한 칸만 밀려도 모든 분기가 그럴듯한 날짜를 갖고, 화면에서는 「과거 캘린더가 채워졌다」로만 보인다.

### 독립 검증

승격 시험에서 캘린더와 겹친 8개 분기 중 **7개가 날짜까지 정확히 일치**했다(AAPL 07-30, MSFT 07-29, WMT 08-20 …). 1개는 Finnhub의 알려진 이중 라벨(TGT)이고, 덮어쓰기 방지 가드가 작동해 캘린더 쪽이 유지됐다.

### session은 「8-K 접수 시각」이다

`acceptanceDateTime`은 SEC 접수 시각이라 보도자료보다 몇 시간 늦다(실측 WMT는 장전 발표인데 10:59 ET 접수). **그래도 어떤 숫자도 틀리지 않는다** — 반응 계산이 장전과 장중을 똑같이 다루기 때문이다(`earnings_reaction.go`의 sameDay 분기). 갈리는 것은 장후뿐이고, 장후는 접수가 20시 이후로 뚜렷이 분리된다(AAPL 20:30 · NVDA 20:21 vs WMT 10:59 · CVX 10:16).

## 4. 투영 쿼리 결함 (이번 릴리스의 숨은 핵심)

`BackfillStocksFromCandleBarsRange`가 날짜 경계를 **바깥 WHERE에만** 걸고 있었다. `dailyCloseSessionBars`의 필터 자리에 빈 문자열을 넘겨, `candle_bars` 전체(**1,915MB · 1,386만 행**)에 `ROW_NUMBER()`·`LAG()`를 돌린 뒤에야 날짜로 걸렀다.

- 한 달을 뽑든 다섯 달을 뽑든 **비용이 같다**. 월 단위 분할은 같은 전체 스캔의 반복일 뿐이었다.
- 같은 파일의 일일 잡 `IngestStockCloses`는 처음부터 안쪽에 필터를 걸어 빨랐다. 같은 방식을 백필에도 적용했다.
- **30일 여유(lead-in)가 정확성의 핵심**이다. LAG는 필터된 집합 안에서만 이전 행을 보므로, 하한을 `since`에 딱 맞추면 구간 첫날의 등락률이 통째로 NULL이 된다.

실측: **15분+ 미완 → 47초**(7개월 · 579,930행).

### 캘린더 승격은 기존 행을 한 줄도 안 건드린다

`INSERT ... ON DUPLICATE KEY UPDATE id = id`라 충돌 시 아무 일도 하지 않는다. 일반 Upsert를 쓰면 `event_date = LEAST(...)`가 돌아 **소스가 준 진짜 발표일을 우리 역산값이 덮는다**. 검증: AAPL 2026-07-30 · TGT 2026-08-19 · MSFT 2026-07-29 모두 승격 전후 동일.

### ⚠️ MySQL 버퍼 풀을 먼저 확인할 것

이번 작업 중 로컬 MySQL이 **두 번 교착**됐다. 원인은 `innodb_buffer_pool_size`가 **기본값 128MB**인데 `candle_bars`가 1,915MB라, 전체 스캔이 버퍼 풀에 들어가지 못해 InnoDB가 빈 블록을 못 찾은 것이다(에러 로그: `Difficult to find free blocks in the buffer pool`).

**4GB로 올린 뒤 같은 쿼리가 15분+ 실패 → 47초 성공으로 바뀌었다.** 단순 `COUNT`도 20초 타임아웃 → 4~25ms.

- 자체 관리 MySQL이면 `my.ini`의 `innodb_buffer_pool_size`를 **반드시 명시**한다.
- 관리형 DB(RDS·Cloud SQL)는 인스턴스 메모리의 약 75%로 자동 설정하므로 이 문제가 없다.
- **투영·백필 CLI는 앱을 멈추고 하나씩** 돌린다. 클라이언트 타임아웃은 서버 쿼리를 멈추지 않는다 — 끊고 다시 띄우면 같은 전체 스캔이 중첩된다.

### 클라우드 메모리 산정 (실측 기반)

| 테이블 | 크기 |
|---|---|
| `candle_bars` | 1,915MB (1,386만 행) |
| `candle_bars_legacy_v1` | 517MB — **DROP 대상**(026 마이그레이션 잔재) |
| `stock_daily_closes` | 368MB |
| `stock_scores` | 211MB |
| `news_articles` | 161MB |
| **합계** | **약 3.3GB** (legacy 제거 시 2.8GB) |

앱 스택은 compose 기준 약 5.2GB(api 1G · redis 1.5G · 워커 8×256M · fe 512M · nginx 128M).

| 배포 형태 | 권장 | 최소 |
|---|---|---|
| 관리형 DB 분리 | 앱 8GB + **DB 8GB** | 앱 4GB + DB 4GB |
| 단일 호스트 | **16GB** | 8GB |

`max_connections=151`에 앱이 최대 약 114(api 50 + 워커 8×8)를 쓴다. **CLI 백필은 기본 풀이 50**이라 두세 개만 겹쳐도 고갈된다 — `MYSQL_MAX_OPEN_CONNS`를 낮춰 실행할 것.
