## 1. 한 줄 요약

폴러가 **아무도 보지 않는 종목의 차트까지 예열**하느라 `/candles` 한도(20/s)를 상시 소진하고, 그 여파로 **가격 배치가 30초에 133종목**밖에 못 덮고 있었다. 예열 대상을 「누군가 신경 쓰는 종목」으로 좁히고, 가격 배치가 터미널 갱신에 묶이지 않게 떼어 낸다.

예열 대상이 스스로 부풀고 있었다 — pinned에 자기 참조 고리가 있어서다(§3(1)).

## 2. 무엇이 문제였나 (2026-08-23 실측)

### Toss 한도와 실제 소비

| 엔드포인트 | 한도 | `remaining=0` 발생 |
|---|---|---|
| **`/candles`** | 20/s | **10,473회** |
| `/stocks` | 5/s | 122회 |
| `/prices` | **15/s** (200종목/호출 = 3,000종목/초) | 1회 |
| `/orderbook` · `/trades` | 각 15/s | 4 · 1회 |

최근 10분 rate-limit 경고 **2,258건**(초당 3.8건).

### 세 가지가 겹쳐 있었다

**(a) tickSlow가 pinned 전체를 훑는데, 그 pinned가 스스로 부푼다.**

```
pinned = 보유 ∪ 관심 ∪ MarketDataStore.activeSymbols()   // 가격을 요청받은 지 5분 안쪽
```

tickSlow가 pinned를 훑으면서 `EnsurePrices`를 부르면 그 종목이 다시 `activeSymbols`에 등록되어 pinned를 유지시킨다 — **아무도 안 봐도 스스로 살아 있는 고리**다. 그중 실제로 보는 것은 `active`(≤40, TTL 5분)뿐인데, 예열은 종목당 Toss 캔들 호출이라 이것이 `/candles` 20/s를 태우는 주범이다.

**(b) tickFast가 1초 틱을 못 지킨다.** 같은 함수에서 터미널 갱신(40종목 × 3호출)을 하는데 `/orderbook`·`/trades`가 각 15/s라 40종목에 최소 8초다. `fastBusy`가 그 동안 다음 틱을 스킵하므로 **가격 배치도 8초에 한 번씩만** 불린다.

**(c) 가격 배치가 첫 실패에 전체를 포기한다.**

```go
for i := 0; i < len(batch); i += 200 {
    prices, err := s.toss.GetPrices(refreshCtx, batch[i:end])
    if err != nil { ...; return }   // ← 뒤쪽 종목은 그 틱에서 가격을 못 받음
}
```

결과: **30초 누적 고유 종목 133개 = 약 4.4종목/초 = 한 바퀴 약 14분.**

### 그런데도 화면이 빨랐던 이유

조회가 Toss를 기다리지 않기 때문이다.

```
① Redis 스냅샷  md:snap:{종목}:{간격}  →  실측 4ms     ← 거의 여기서 끝
② DB (candle_bars 계층 저장)          →  실측 7~11ms
③ Toss                                →  실측 1,694ms  ← 마지막 수단
```

**속도와 실시간성은 별개였다.** 빠른 것은 캐시 덕이고, 신선도는 최대 14분 뒤처져 있었다.

그리고 v0.10.0의 캔들 계층 저장 덕에 ②가 7~11ms가 되면서, **tickSlow가 지키던 이득이 「1.7초→4ms」에서 「11ms→4ms」로 줄었다.** 그 7ms를 위해 `/candles` 20/s를 상시 태우고 있었다.

## 3. 무엇을 바꾸는가

### (1) 차트 예열 대상을 좁힌다 — `tickSlow`

`pollSymbols`가 주는 pinned 전체가 아니라 **관심 ∪ 보유 ∪ 지금 보는 중**만 예열한다.

`marketPoller`에 `cared`(관심 ∪ 보유) 필드를 새로 두고 `refreshPinned`가 pinned와 함께 채운다. pinned는 그대로 남는다 — 가격은 배치로 계속 받아야 하기 때문이다.

**pinned에 자기 참조 고리가 있었다.** `pinned = 보유 ∪ 관심 ∪ MarketDataStore.activeSymbols()`(가격을 요청받은 지 5분 안쪽)인데, tickSlow가 pinned를 훑으면서 `EnsurePrices`를 부르면 그 종목이 다시 `activeSymbols`에 등록되어 pinned를 유지시킨다. **아무도 안 봐도 스스로 살아 있는 집합**이었다. `cared`는 그 고리 밖이라 사용자가 실제로 담은 만큼만 늘어난다.

### (2) 가격 갱신을 터미널 갱신에서 떼어 낸다 — `tickPrice` 신설

전에는 `tickFast` 한 함수가 ① 배치 가격 ② 터미널 갱신(40종목 × 3호출)을 차례로 했다. `/orderbook`·`/trades`가 각 15/s라 ②만으로 최소 8초인데, `fastBusy`가 그 동안 다음 틱을 통째로 스킵한다 — **①도 8초에 한 번씩만** 불렸다.

1초 티커와 자기 busy 플래그(`priceBusy`)를 따로 둬서, 터미널 갱신이 길어져도 가격은 제 주기를 지킨다.

### (3) 가격 배치가 한 묶음의 실패로 멈추지 않는다 — `RefreshPrices`

레이트리밋이 아닌 일시적 오류는 그 묶음만 건너뛰고 계속한다. 전에는 `return`이라 200종목씩 나눈 묶음 중 두 번째가 실패하면 뒤쪽이 통째로 빠졌다.

### (4) 시청자가 상한을 넘을 때 공평하게 돈다 — `capActiveTargets`

상한(40)은 Toss 한도(호가·체결 각 15/s)에서 나온 값이라 없앨 수 없다. 시청자가 넘치면 누군가는 그 틱에서 밀린다 — 상류 제약이다.

없앨 수 있는 것은 **누가 밀릴지가 매번 임의로 정해지는 것**이었다. 전에는 Go 맵을 그냥 순회해 잘라서, 특정 사용자의 종목이 연속 여러 틱을 굶을 수 있었다. 정렬 + 커서로 바꿔 결정적으로 돈다 — active 100개·상한 40이면 각 종목이 2.5틱마다 정확히 한 번이다.

## 5. 사이드 이펙트·호환

**모달 차트는 영향 없다.** 포트폴리오·랭킹의 종목 클릭 모달은 `QuoteDailyChart`의 `interval="1d"` 하드코딩이고, 일봉은 롤업·삭제 대상이 아니라 DB에 영구히 있다(실측 7ms).

**온디맨드 가격 경로가 예열을 대신한다.** pinned에 없는 종목을 열면 `EnsurePrices`가 그 자리에서 받아 캐시에 넣는다 — 실측으로 068270 요청 시 캐시 0→1, 현재가 192,200 응답.

**영향이 남는 것 하나**: 60일간 아무도 열지 않은 종목의 **인트라데이 차트 첫 열람**이 Toss 왕복 한 번(실측 1.7초)만큼 느리다. 그 뒤로는 4ms다. v0.10.0 계층 저장 덕에 DB에 데이터가 있는 종목은 7~11ms로 복구되므로, 이 지연은 인트라데이 데이터가 아예 없는 종목에만 해당한다.

## 8. 장중 실측으로 드러난 것 — 판단 필요

### (1) 1분봉 적재 대상이 209종목 → 12종목으로 좁아졌다 (회귀)

tickSlow의 대상이 바뀌었다.

| | 대상 | 오늘 1분봉을 받은 종목 |
|---|---|---|
| v0.9.0 | `pollSymbols()` 전체 = **pinned ∪ active** (보유 ∪ 관심 ∪ 최근조회) | 209종목 규모 |
| 현재 | `active`만 = **최근 5분 내 조회된 종목** | **12종목** (관심·보유 209 중) |

작업 중 남긴 주석은 「이 틱은 처음부터 active만 훑었다」고 적고 있으나 그것은 `cared` 변수에 대한 이야기이고, **실효 대상 집합은 실제로 좁아졌다** — v0.9.0은 `symbols`(pinned 포함)를 넘겼다.

- **얻은 것**: `/candles` 한도 소진 0건. 배경 작업이 사용자의 차트 첫 열람을 밀어내던 문제가 사라졌다.
- **잃은 것**: 아무도 안 보는 종목의 장중 이력이 비고, 롤업이 접을 1분봉이 없어 5m/10m/30m/60m 계층도 그만큼 빈다. 되돌릴 수 없다.
- **사용자 체감**: 첫 열람 0.55초(웜 0.013초). 1일봉·점수·랭킹은 무영향.

### (2) 22종목이 매일 7,200봉을 되받는 순환 (경미)

계층 밖(3일+) 1분봉 19,858개는 **전부 오늘 05:30 롤업 이후에 쓰였다**. 490600은 정확히 7,200봉(07-27~08-21), 032350은 7,204봉을 갖고 있고 두 종목 모두 5m/10m/30m 계층이 없다. 「인트라데이 계층이 비어 → `maxIntradayRawBars`(7,200) 통째 페치 → 다음 05:30 롤업이 접어 삭제 → 다시 조회되면 재페치」의 순환이다.

22종목 중 관심·보유는 **2개뿐**이고 나머지는 ETF·지수(069500, 102110, 122630, 114800 …)다. 하루 약 110페이지로 `/candles` 20/s 한도에는 위협이 안 된다 — 낭비이지 장애가 아니다.

### (3) Touch 2계층 분리는 이제 **가능하다**

§7의 신선도 실측(203/203이 1초 내 갱신)이 조건을 충족한다. 차트 시청자를 가격 계층으로 옮기면 「동시 시청자 100명 = Toss `/candles` 0 추가」가 된다. 다만 가격은 **형성 중인 봉**만 움직이고 새 봉을 닫는 것은 `/candles`이므로, 옮길 경우 봉 경계 갱신을 형성봉 경로가 대신하도록 배선해야 한다.

**정정 기록**: 작업 중 분석의 전제 하나가 틀린 것을 확인했다. 「랭킹 추적분 3,652종목」이라 한 것은 `md:rev:*` Redis 키(캔들 리비전 카운터의 누적 흔적)를 센 것이고, 실제 pinned는 44~150종목이었다. 코드 주석의 해당 수치를 걷어냈다. 자기 참조 고리라는 발견 자체는 유효하다.

## 9. v0.10.0으로 복원하기

**이 릴리스에는 Git 태그가 없다.** v0.9.1 이후 모든 릴리스가 문서만 있고 커밋되지 않았으므로, `git restore --source v0.10.0 .`은 동작하지 않는다.

되돌리려면 **§4 변경 파일**의 목록을 보고 해당 변경만 수동으로 되돌린다. 이 릴리스는 폴러 동작만 건드리므로:

- 되돌리면: 폴러가 다시 pinned 전체를 예열하고, 가격 배치가 터미널 갱신에 묶인다.
- 되돌려도 남는 것: **v0.10.0의 캔들 계층 저장·1일봉 밀림 수정·예시 캐싱은 이 릴리스 밖이라 영향 없다.**
- DB 스키마 변경 없음 — 마이그레이션을 되돌릴 것이 없다.
