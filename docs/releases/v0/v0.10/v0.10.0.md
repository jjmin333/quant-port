# Quant Port v0.10.0 — Project Snapshot (백필 정리 · 운영 안전장치)

> **버전:** v0.10.0
> **기준일:** 2026-08-22 (KST)
> **Git 태그:** `v0.10.0` (커밋 후)
> **이전 버전:** [v0.9.3](../v0.9/v0.9.3.md)
> **목적:** v0.9.2–v0.9.3 백필 과정에서 **DB를 두 번 멈춘 사고**가 상용에서 재발하지 않도록 코드·설정·문서로 못박고, 일회성 산출물을 정리한다.
> **범위:** 백엔드(CLI 커넥션 풀 · 부팅 진단) + 설정 권고 + 문서. **기능 변경 없음**

---

## 1. 한 줄 요약

백필 중 겪은 사고의 원인은 **CLI가 서버용 커넥션 풀(50)을 쓴 것**과 **InnoDB 버퍼 풀이 기본값 128MB인 것** 둘이었다. 전자는 코드로 막았고(CLI 전용 풀 4), 후자는 부팅 때 눈에 띄게 만들었다(진단 로그).

---

## 2. 무슨 일이 있었나

2026-08-22 새벽, `stock_daily_closes` 투영을 돌리다 **MySQL이 두 번 멈췄다.** 원인은 셋이 겹친 것이다.

| # | 사실 | 결과 |
|---|---|---|
| 1 | 투영 쿼리가 `candle_bars` **전체**(1,915MB · 1,386만 행)를 스캔 | 15분+ 미완 |
| 2 | `innodb_buffer_pool_size`가 **기본값 128MB** | InnoDB가 빈 블록을 못 찾아 교착 (`Difficult to find free blocks in the buffer pool`) |
| 3 | 클라이언트 타임아웃이 **서버 쿼리를 멈추지 않음** → 끊고 재실행이 중첩 | 커넥션 151개 고갈, DB 전체 정지 |

②는 **관리자 권한 개입 세 번**이 필요했고, ③은 앱까지 함께 죽였다. ①은 v0.9.3에서 이미 고쳤다(날짜를 안쪽 스캔에 푸시다운, 15분+ → 47초).

**교착 상태가 특히 고약했다** — CPU도 IO도 0인데 `SELECT 1`은 즉시 되고 테이블 접근만 영원히 멈춘다. 에러 로그를 못 읽으면 원인을 알 수 없다.

---

## 3. 이번 릴리스가 막는 것

### ① CLI 전용 커넥션 풀 (`NewMySQLForCLI`, 기본 4)

운영 스택이 서버 상한의 대부분을 이미 쓴다:

| 구성 | 커넥션 |
|---|---|
| api (`MYSQL_MAX_OPEN_CONNS` 미설정 → 기본 50) | 50 |
| 워커 8개 × 8 | 64 |
| **합계** | **약 114** / `max_connections=151` |

여유가 **37뿐**인데 CLI가 각자 50을 잡았다. 두세 개만 겹치면 즉시 고갈된다.

CLI 커맨드 **13개 전부**를 `repository.NewMySQLForCLI`로 옮겼다. 환경변수가 명시돼 있으면 그 값이 이긴다 — 운영자가 정한 값을 덮지 않는다. 서버 경로(`server.go`, `worker_bootstrap.go`)는 **그대로 50**이다.

### ② 부팅 시 버퍼 풀 진단 (`CheckInnoDBBufferPool`)

가장 큰 InnoDB 테이블과 버퍼 풀을 비교해 한 줄 남긴다. 실측 로그:

```
mysql: innodb_buffer_pool_size = 4.0GB (최대 테이블 candle_bars = 1.9GB) — ok
```

128MB였다면 경고가 떴다. 고치는 건 서버 운영자의 몫이라(`my.ini` + 재시작) **증상이 나오기 전에 눈에 띄게** 하는 것이 이 진단의 전부다. 부팅을 막지 않는다.

문턱은 최대 테이블의 **50%**다. 실측 사고는 7%(128MB / 1,915MB)였다.

## 4. 상용 배포 시 반드시 확인할 설정

### `innodb_buffer_pool_size` — 이번 사고의 근본 원인

| 환경 | 조치 |
|---|---|
| **관리형 DB** (RDS · Cloud SQL) | **자동** — 인스턴스 메모리의 약 75%. 이 문제가 원천적으로 없다 |
| **자체 설치 MySQL** | `my.ini`/`my.cnf`에 **반드시 명시**. 기본값 128MB는 이 프로젝트 규모에 맞지 않는다 |

효과 실측 (128MB → 4GB):

| | 이전 | 이후 |
|---|---|---|
| 투영 (7개월 · 58만 행) | **15분+ 실패** | **47초** |
| 단순 `COUNT(*)` | 20초 타임아웃 | **4~25ms** |

### 메모리 산정 (실측 기반)

| 테이블 | 크기 |
|---|---|
| `candle_bars` | 1,915MB (1,386만 행) |
| `candle_bars_legacy_v1` | 517MB — **DROP 대상** (026 마이그레이션 잔재) |
| `stock_daily_closes` | 368MB |
| `stock_scores` | 211MB |
| `news_articles` | 161MB |
| **DB 합계** | **약 3.3GB** (legacy 제거 시 2.8GB) |

앱 스택은 compose 기준 **약 5.2GB** (api 1G · redis 1.5G · 워커 8×256M · fe 512M · nginx 128M).

| 배포 형태 | 권장 | 최소 |
|---|---|---|
| 관리형 DB 분리 | 앱 8GB + **DB 8GB** | 앱 4GB + DB 4GB |
| 단일 호스트 | **16GB** | 8GB |

DB 8GB면 버퍼 풀이 약 6GB가 되어 현재 DB 전체가 메모리에 들어간다.

### `max_connections`

관리형 DB는 인스턴스 크기에 비례한다(4GB ≈ 340, 8GB ≈ 680)이라 앱의 114는 여유롭다. **1~2GB 초소형 인스턴스(85~170)는 위험**하다.

### 백필·점검 CLI 실행 규칙

1. **앱을 멈추고**, **하나씩** 돌린다.
2. **클라이언트 타임아웃은 서버 쿼리를 멈추지 않는다.** 끊고 재실행하면 같은 전체 스캔이 중첩된다 — 반드시 완료를 확인하고 다음으로 넘어간다.
3. 오래 걸리는 쿼리는 DSN에 `readTimeout`을 명시해 늘린다(`withDefaultDSNTimeouts`는 **명시값을 우선**한다).

## 5. 일회성 산출물 정리 — 무엇을 남기고 무엇을 지웠나

### 남긴 것: `earnings_surprise_history` 테이블과 그 읽기 경로

**일회성 산출물이 아니라 런타임 데이터 소스**임을 실측으로 확인했다.

- 「꾸준히 기대를 넘는 기업」 카드가 매 조회에서 읽는다.
- 창(730일) 안에 `earnings_events`에 **없는 966분기**를 추가로 공급한다.
- 지우면 후보에서 빠지는 종목에 대형주가 있다 — 스페이스X $1,743B · 엑슨 $688B · 인텔 $465B · 알리바바/ARM(ADR, **8-K가 없어 발표일을 못 붙인다**).
- 크기는 4MB, 조회는 30분 캐시 뒤에 있다.

시간이 지나 일일 Finnhub 배치가 4분기 이상을 쌓으면 자연히 불필요해지는 **전환기 자산**이다. 그때 지우면 된다.

### 남긴 것: 두 백필 커맨드

`cmd/backfill-earnings-surprises` · `cmd/backfill-earnings-announced`. 이미 실행을 마쳤지만 **새 환경을 부트스트랩하는 유일한 수단**이라 남긴다. 스케줄러에는 등록하지 않았다(정기 실행하면 같은 4분기를 매일 3,000호출로 다시 받을 뿐이다).

### 지운 것

- 진단·측정용 임시 커맨드 전부 (`cmd/tmp-probe` 등)
- 임시 심볼 목록 파일 (`be/tmp/closes-gap-2025.txt`)
- API 키가 평문으로 남았던 로그 파일 (커밋 전 삭제 — v0.9.2 §7)

### 후속 정리 대상 (이번 범위 밖)

`candle_bars_legacy_v1` **517MB**. `docs/AGENT_STATE.md`에 「확인 후 수동 DROP」으로 이미 기재돼 있고, DB의 15%다.
