### QA-03 · 보유분을 넘는 매도가 이력에 남는다

- **영역** 데이터 정합성 | **등급** P1 | **상태** 수정 + 회귀 테스트 (**사용자 결정 반영**)
- **재현** `POST /user/holdings/trades` 매수 10주 → 같은 종목 **매도 50주**
- **기대** 거부
- **실제(수정 전)** 200. 이력에는 「50주 매도」가 남고 실현손익은 10주분(10,000)으로
  계산된다. 같은 화면의 두 숫자가 서로를 부정하고, 사용자가 증권사와 대조하면
  **어디에도 없는 40주**를 찾게 된다. 보유가 0인 종목의 「999,999주 매도」도 200이었다
- **root cause** `DerivePositions`가 매도를 보유분까지 깎는다(조회가 음수 포지션을 만들지
  않기 위한 안전망, 그대로 옳다). 그런데 **쓰기에도 같은 관용이 적용돼** 검사가 아예 없었다
- **fix** `repository.FindOversell` 신설 + `service/holding_trades.go`에서 매도 시 거부(400).
  깎는 안전망은 **이미 저장된 옛 행을 위해 그대로 둔다**
  - **날짜 기준 재생** — 매도는 소급 입력될 수 있어 「지금 보유량」이 아니라 「그 날짜까지의
    보유량」과 견준다. 4월 매수를 3월 매도로 적는 순서 뒤집힘도 함께 걸린다
  - **중복 검사 뒤에 배치** — 같은 매도를 재전송하면 첫 번째가 이미 `existing`에 있어,
    순서를 잘못 두면 **멀쩡한 재전송이 「초과」로 거부**된다 (실측으로 확인 후 배치 결정)
- **회귀** Go 단위 8케이스 + API e2e 3건(거부 / 보유 없음 거부 / 정상·재전송 통과)
- **⚠️ 계약 변경** 기존 `holdings-trades.spec.ts`가 「초과 매도는 0으로 깎인다」를 **명시적으로
  고정**하고 있었다. 관용에는 근거가 있었으므로(매수를 다 기록하지 않은 사용자의 정당한
  매도) 임의로 뒤집지 않고 **사용자에게 물어 「거부」 결정을 받은 뒤** 그 테스트를 갱신했다

### QA-04 · 남의 댓글 수정·삭제가 502로 거부된다

- **영역** 보안(계약) | **등급** P1 | **상태** 수정 + 회귀 테스트
- **재현** A가 리서치 콜에 댓글 → B가 `PUT`/`DELETE /research/comments/{id}`
- **기대** 4xx
- **실제(수정 전)** **502** (둘 다)
- **권한 자체는 정상이었다** — 리포지터리가 `user_id`까지 걸어 UPDATE 하므로 A의 댓글은
  한 글자도 바뀌지 않았다. 문제는 **거부를 게이트웨이 장애로 알린 것**이다: 평범한 사용자
  행동에 5xx 알람이 울리고, 클라이언트는 「재시도할 문제」와 「하면 안 되는 일」을 구분 못 한다
- **root cause** `ErrResearchCommentNotFound`가 어디에도 매핑되지 않아 `writeTossError`의
  기본 분기(502)로 떨어졌다. **이 앱이 이미 두 번 고친 것과 같은 계열**(`contract.spec.ts`)
- **fix** `handler/research.go`의 `writeResearchError`에 형제 오류 옆으로 404 매핑 추가.
  「없음」과 「남의 것」을 구분하지 않는다 — ID를 찍어 존재를 알아내는 길을 열지 않는다
- **회귀** `authorization.spec.ts` — 상태코드(<500)와 **원문 불변**을 함께 단언
