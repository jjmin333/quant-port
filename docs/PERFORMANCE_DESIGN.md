# 2차 검토 (2026-08-24) — 조사 결과와 개정

`be/docs/toss-openapi.json`(2026-08-24 갱신본)과 코드 확인으로 나온 것.
**아래 세 항목이 1차 결론을 덮어쓴다.**

## ★ Toss가 웹소켓 실시간 구독을 제공한다 — P0-1의 전제가 바뀐다

OpenAPI 스펙 `Market Data` 태그 설명에 있다:

> 실시간 체결·호가는 **폴링 대신 웹소켓 API(`wss://openapi-ws.tossinvest.com/ws/v1`)로
> 구독**할 수 있습니다 — AsyncAPI 스펙(`/openapi-docs/latest/asyncapi.json`)과
> 연동 가이드의 **웹소켓 연동** 섹션 참고

1차 문서에서 "가장 옳은 구조이지만 전제가 미확인"이라며 보류했던 **옵션 I가 실재한다.**
그리고 이것이 **사용자가 제기한 「20만원 → 22만원 점프」 문제의 유일한 근본 해결책**이다.

왜 그런지가 중요하다. 폴링 기반에서는 어떤 설계를 해도 다음 셋 중 하나를 골라야 한다:

| | 낡은 값 표시 | 로딩 표시 | 갱신까지 대기 |
|---|---|---|---|
| 정확성 | **틀림** | 정확 | 정확 |
| 체감 | 즉시(그러나 점프) | 사용성 저하 | 첫 진입 +100~200ms |

**구독 구조에서는 이 선택 자체가 사라진다.** 구독 중인 심볼은 상류가 변경을
밀어 주므로 캐시가 항상 최신이고, "낡았는지"를 물을 일이 없다.

### 비용 비교 (폴링 vs 구독)

| | 폴링 (현재) | 폴링 (F+H 최적화) | **웹소켓 구독** |
|---|---|---|---|
| 비용 기준 | 심볼 수 × 1/주기 | 심볼 수 × 1/주기 | **구독 유지 수** |
| 10,000 DAU | 60 req/s (한도 400%) | ~9 req/s | **REST 호출 0** |
| 새벽 | 동일 부하 | 0 | 0 |
| 신선도 | 최대 1~5초 stale | 최대 1~5초 stale | **변경 즉시** |
| 20만→22만 점프 | 발생 | 발생 | **구조적으로 없음** |

### AsyncAPI 스펙 실측치 (2026-08-24 조회)

| 항목 | 값 |
|---|---|
| **계정당 동시 연결** | **2개** (초과 시 **가장 오래된 연결이 끊긴다**) |
| **연결당 구독 수** | **100건** (`codes` 합산) |
| **총 구독 슬롯** | **200** |
| 구독 계수 단위 | **채널 × 심볼** — `trade:kr:005930` + `orderbook:kr:005930` = **2건** |
| 선언 빈도 한도 | **5회/초** (초과 시 `rate-limit-exceeded`, 약 1초 후 재선언) |
| 구독 모델 | **선언형 full-replace** — 별도 sub/unsub 없음. 목록에서 빠지면 자동 해지 |
| 채널 | `trade:{us\|kr}:{sym}` · `orderbook:{us\|kr}:{sym}` · `personal:order:{seq}` |
| 유실 특성 | 체결·호가 **LOSSY** (백프레셔 시 프레임 드롭) |
| Idle 타임아웃 | **클라이언트 송신 180초** 무발생 시 서버가 종료 |
| Keepalive | raw text `PING` **60초 권장** → `{"type":"pong"}` |
| 재연결 | 지수 백오프 1s → 2s → 4s (jitter). 배포 시 `server-shutdown` 프레임 선행 |
| 인증 | 핸드셰이크에서 `Authorization: Bearer` 1회. 세션 중 만료돼도 안 끊김 |

**지적대로 200 슬롯은 전 종목을 덮지 못한다.** 다만 아래에서 보듯,
**덮을 필요가 없다** — 슬롯이 소비되는 단위가 사용자가 아니라 **심볼**이기 때문이다.

### ★ 그런데 진짜 수치는 따로 있다

스펙에서 확인된 것: **`/prices`·`/orderbook`·`/trades`가 `MARKET_DATA` 그룹
하나를 공유한다.** (캔들만 `MARKET_DATA_CHART`로 분리)

지금 폴러가 그 한 버킷에 쓰는 양을 다시 계산하면:

```
tickFast  : 40종목 × (orderbook 1 + trades 1) / 1초  =  80 req/s   ← 압도적
tickPrice : ceil(S/200) / 1초                        =   1~60 req/s
                                                    ──────────────
                                          합계        =  81~140 req/s
```

**`tickPrice`가 아니라 `tickFast`가 주범이다.** 감사의 실측
(`/trades` 145건 · `/orderbook` 139건 초과)이 정확히 이 80/s다.
지금까지 P0-1을 "가격 폴러 문제"로 봤는데, **한도를 태우는 건 터미널 스냅샷 쪽이
훨씬 크다.**

그리고 **웹소켓이 없애는 것이 바로 그 80/s다.** 체결·호가는 구독으로 옮기면
REST 호출이 **0**이 된다. 40종목이라는 `marketFastSymbolCap`도 사라진다 —
구독은 140종목까지 되므로 **커버리지가 오히려 3.5배 늘면서 비용은 0**이 된다.

### 웹소켓이 해결하는 것 / 못 하는 것

| | 웹소켓 |
|---|---|
| 현재가 실시간 | ✅ `trade` 채널의 체결가가 곧 현재가 |
| 체결 목록 | ✅ `trade` |
| 호가창 | ✅ `orderbook` |
| **형성봉(forming bar)** | ✅ **체결 스트림으로 서버에서 직접 만들 수 있다** — `refreshFormingBars`의 폴링이 사라진다 |
| 과거 캔들 | ❌ REST 전용 (`MARKET_DATA_CHART`) — **P0-3은 별도로 풀어야 한다** |
| 목록 화면의 수십~수천 종목 | ❌ 슬롯 200 한계 → **폴링 유지** |

# ★ 최종 설계 — 실시간성 vs API 한도의 트레이드오프 해소

> 제기된 문제: *"실시간처럼 느껴져야 하고, 3명이 봐도 3배로 일하지 않아야 하고,
> 사용자가 늘어도 한도를 안 넘어야 한다."*

## 왜 지금 트레이드오프처럼 보이는가

**하나의 폴러가 성격이 완전히 다른 두 요구를 함께 처리하고 있기 때문이다.**

| | 요구 A — 실시간성 | 요구 B — 커버리지 |
|---|---|---|
| 어디서 | **상세 화면** (차트·호가·체결) | **목록 화면** (보유·관심·랭킹) |
| 필요한 신선도 | **즉시** (초 단위도 티가 남) | **5초** (FE가 5초마다 읽음) |
| 필요한 심볼 수 | **사용자당 1개** | 사용자당 수십 개 |
| distinct 규모 | **작다** (인기 편중 극심) | **크다** (누적) |
| 지금 처리 | `tickFast` 1초 · 40종목 캡 | `tickPrice` 1초 · 무제한 |

**두 요구는 정반대 성질을 가진다** — A는 "적은 종목을 매우 빠르게",
B는 "많은 종목을 적당히". 그런데 지금은 **둘 다 1초 REST 폴링**으로 처리한다.
그래서 A를 만족시키려니 한도가 터지고, 한도를 지키려니 A가 죽는다.

**트레이드오프는 이 결합에서 생긴 것이지 본질이 아니다.** 갈라 놓으면 사라진다.

## 설계: 두 축을 분리한다

```
                    ┌─ Tier S : 웹소켓 구독 ── 실시간, 비용 = distinct 심볼 수 (≤200)
   심볼 하나가      │
   어디에 속하나 ───┤─ Tier A : REST 폴링 1초 ── 슬롯 밖 상세 시청 (롱테일)
                    │
                    ├─ Tier B : REST 폴링 5초 ── 목록 노출 (FE 폴링과 동일)
                    │
                    └─ Tier C : 폴링 없음 ────── 요청 시점에만 갱신
```

**핵심 성질: Tier S의 비용은 사용자 수가 아니라 distinct 심볼 수에 비례한다.**
삼성전자를 3명이 보든 300명이 보든 **구독은 1건**이고, fan-out은 이미 있는
`streamHub`가 한다(SSE가 이미 그렇게 동작한다). 이게 "3명일 때 3배로 일하지
않게"의 완성형이다 — 지금은 캐시로 *중복 계산*을 막고 있지만, 구독은 애초에
*상류 호출 자체가 1건*이다.

### ⚠ "40 → 200, 5배"는 정확하지 않다 — 양방향 정정

**정정 A (아래로): 200은 심볼이 아니라 슬롯이다.**
구독은 **채널×심볼**로 센다. 따라서 실제로 얻는 것은 배분에 달렸다.

| 배분 | 체결·가격·형성봉 | 호가 |
|---|---|---|
| `trade`만 | **200종목** | 0 |
| `trade`+`orderbook` 둘 다 | 100종목 | 100종목 |
| **제안 배분** (`trade` 140 + `orderbook` 60) | **140종목** | **60종목** |

**정정 B (위로): 현재의 40은 「1초」가 아니다. 실효 약 8초다.**

`refreshTerminalSnapshot`(`quotes_marketdata.go:34`)이 심볼당 **3호출**을 낸다:

```go
detail, ok := s.getQuoteUncached(ctx, symbol)      // MARKET_DATA
book,  _  := s.getOrderBookUncached(ctx, symbol)   // MARKET_DATA
trades, _ := s.getTradesUncached(ctx, symbol)      // MARKET_DATA
```

```
tickFast 한 바퀴 = 40종목 × 3호출 = 120 MARKET_DATA 호출
그룹 한도 ~15/s        → 한 바퀴에 약 8초
그동안 fastBusy가 다음 틱을 통째로 스킵
```

**코드 주석이 이미 이걸 인정하고 있다** (`market_poller.go:150`):

> `/orderbook`·`/trades`가 각 15/s라 ②만으로 최소 8초가 걸리는데,
> `fastBusy`가 그 동안 다음 틱을 통째로 스킵한다

당시엔 가격까지 묶여 있어서 가격도 8초마다 갱신됐고, `tickPrice` 분리로
**가격은 고쳤지만 호가·체결·형성봉은 여전히 그 8초 경로에 있다.**

> **즉 지금 상세 화면의 호가창·체결·형성봉은 「실시간처럼」이 아니라 8초마다
> 한 번 움직인다.** 제기하신 "실시간처럼 느껴지게"가 지금 실제로는 안 되고 있다.

### 정직한 비교

| | 현재 | 웹소켓 (제안 배분) | 배수 |
|---|---|---|---|
| 호가 커버 | 40종목 | 60종목 | **1.5배** |
| 체결·형성봉 커버 | 40종목 | 140종목 | **3.5배** |
| **실효 갱신 지연** | **~8초** | **수십 ms (푸시)** | **100배 이상** |
| MARKET_DATA 소비 | **120 호출/틱** | **0** | — |

**개수는 5배가 아니다(1.5~3.5배). 그런데 지연이 100배 이상 좋아진다.**
그리고 "실시간처럼 느껴진다"를 만드는 건 개수가 아니라 지연이다.

덤: `MARKET_DATA` 120호출/틱이 0이 되면서 **남은 버킷 전부를 `tickPrice`와
사용자 요청이 쓸 수 있게 된다.** 이게 개수 증가보다 큰 이득이다.

> **정밀도 주의**: 위 「~15/s」는 감사 문서의 관측값이고, OpenAPI 스펙에는
> 숫자가 없다(런타임 `X-RateLimit-Limit` 헤더에만 있다). 8초는 그 가정 위의
> 계산이므로, **착수 전 헤더로 그룹 한도를 실측해 확정할 것.**

### ★ 슬롯이 2배일 가능성 — 확인 필요

`config.go:245`에 **`TOSS_SECONDARY_CLIENT_ID`(별도 OAuth 앱)** 가 있다.
현재는 "PRIMARY가 한 그룹에서 소진되면 그 그룹만 SECONDARY로 넘기는"
오버플로 용도다(`.env.example:34`).

스펙의 한도는 **"계정당 2개 연결"**인데, 여기서 **「계정」이 OAuth 앱 단위인지
그 뒤의 증권 계좌 단위인지가 불명확하다.**

- OAuth 앱 단위라면 → **연결 4개 × 100 = 400 슬롯** (제안 배분 기준 체결 280 + 호가 120)
- 증권 계좌 단위라면 → 200 그대로

**확인 방법**: 두 클라이언트로 각각 연결을 열어 4개가 동시에 유지되는지 본다.
스테이징에서 5분이면 끝난다. 다만 SECONDARY를 웹소켓에 상주시키면
**REST 오버플로 용도가 사라진다** — 그 트레이드오프를 함께 봐야 한다.

### ⚠ 웹소켓이 REST 한도와 별도인가 — **스펙은 침묵한다**

이 설계 전체가 "웹소켓 트래픽은 `MARKET_DATA` 버킷을 안 쓴다"에 기대고 있으므로
정확히 적는다. **AsyncAPI 스펙을 다시 조회해 확인한 결과, 명시가 없다.**

**스펙이 말하는 것:**
- 웹소켓 한도는 **별도로 열거**돼 있다 — 연결 2개 / 구독 100건 / 선언 5회/초.
- REST와 공유하는 것은 **인증뿐**이다: *"REST API 와 인증 체계를 공유하며"*,
  토큰은 같은 `POST /oauth2/token`에서 받는다.

**스펙이 침묵하는 것:**
- 구독·수신이 REST 쿼터를 소비하는지 — **언급 없음**
- 웹소켓 한도가 REST와 독립 예산인지 — **명시 없음**
- 핸드셰이크·인증이 REST 그룹에 계상되는지 — **언급 없음**
- 두 프로토콜을 아우르는 계정 단위 상한이 있는지 — **언급 없음**

**별도일 가능성이 높다고 보는 근거** (추정임을 분명히 한다):

1. 단위가 다르다. REST는 **경로별 그룹의 초당 요청 수**, 웹소켓은
   **연결 수·구독 수·선언 빈도**다. 같은 버킷이면 같은 단위로 쓸 이유가 있다.
2. `Rate Limits Group`이 **HTTP 경로 설명에 붙어 있다.** 푸시 스트림에는
   계상할 "요청"이 없다.
3. 스펙이 웹소켓을 **"폴링 대신"** 쓰라고 권한다. 같은 한도를 먹는다면
   그 권고가 성립하지 않는다.
4. 공유한다고 명시된 것이 **인증뿐**이다.

**그래도 검증 없이 진행하면 안 된다.** 만약 소비한다면 이 설계의 전제가
무너진다. 검증은 싸다:

```
1. REST GET /prices 1회  → 응답의 X-RateLimit-Remaining 기록
2. 웹소켓 연결 + 거래량 많은 종목 구독 → 수천 프레임 수신 (수 분)
3. REST GET /prices 1회  → X-RateLimit-Remaining 다시 기록
   → 소비 패턴이 1과 같으면 별도 예산이다
```

스테이징에서 **10분**이면 끝난다. **웹소켓 착수(11단계)의 첫 작업으로 둔다.**
결과가 "공유"로 나오면 11·12단계를 폐기하고 폴링 최적화(F+H)로 되돌아간다 —
9단계까지의 Tier 구조는 그대로 쓸 수 있으므로 **손실이 없다.**

### 슬롯 예산 (200)

| 연결 | 배정 | 용도 |
|---|---|---|
| Conn-1 | `trade` × 100 | 현재가 · 체결 · **형성봉** |
| Conn-2 | `trade` × 40 + `orderbook` × 60 | 확장 + 호가창 |
| **합계** | **trade 140 · orderbook 60** | |

**지금보다 나아지는 점**: 현재 `marketFastSymbolCap = 40`이 호가·체결의
상한인데, 구독은 **호가 60 / 체결 140**이다. **커버리지가 늘면서 REST 비용은 0.**

`orderbook`을 60만 두는 이유: 호가창은 상세 화면에서도 실제로 보는 사람이
적고, 체결가(=현재가)와 형성봉이 `trade` 하나로 해결되기 때문이다.
슬롯 1건의 가치가 `trade` 쪽이 훨씬 높다.

### 승격·강등 정책

```
score(symbol) = (지금 상세 화면 시청자 수) × 10
              + (최근 30초 상세 요청 수)   × 1
```

- **승격**: 상세 화면 진입 시 즉시 후보. score 상위 140이 `trade` 슬롯을 차지.
- **강등**: 시청자 0명 + **60초 grace** 경과 후.
- **히스테리시스 필수** — 승격 임계값과 강등 임계값을 벌려 둔다.
  경계에서 심볼이 오가면 **5회/초 선언 한도**를 태우고 화면 데이터가 튄다.
- **선언 디바운스 200ms** — 바뀐 것을 모아 1회 선언. 한도의 1/5만 쓴다.
  선언은 full-replace라 "현재 슬롯 전체 목록"을 매번 보내면 된다.

### 상세 화면 진입 시퀀스 (사용자 체감)

```
1. 요청 도착
2. 배치 REST 갱신 1회 (single-flight)   → 정확한 현재가 즉시   [+100~200ms]
3. 구독 슬롯 승격 선언 (디바운스 200ms) → 이후 실시간 푸시
4. SSE로 fan-out                        → 같은 종목 시청자 전원 공유
```

**낡은 값이 렌더되는 순간이 없고**(2단계), **그 뒤로는 진짜 실시간**(3단계)이며,
**시청자가 몇 명이든 상류 비용은 동일**하다(4단계).

## 정량 검증

인기 편중을 반영한다. 국내 개별주 조회는 집중도가 매우 높아
**상위 200종목이 상세 조회의 약 90%**를 차지한다고 본다.

| DAU | 동시 접속 C | 상세 시청 distinct | Tier S 커버 | 롱테일 폴링(1초) | **MARKET_DATA 총 req/s** |
|---|---|---|---|---|---|
| 현재 (~30) | ~1 | ~1 | 100% | 0 | **~1** |
| 1,000 | 40 | ~30 | **100%** | 0 | ~2 |
| 10,000 | 400 | ~180 | **~100%** | ~0 | ~4 |
| 100,000 | 4,000 | ~900 | **~90%(조회 기준)** | 760종목 → 4/s | **~11** |

대조군:

| 구조 | 10,000 DAU에서 MARKET_DATA req/s |
|---|---|
| **현재** (tickFast 80 + tickPrice) | **~140** |
| 폴링만 최적화 (F+H) | ~9 |
| **웹소켓 하이브리드** | **~4** |

**100,000 DAU에서도 ~11 req/s다.** 그리고 그중 상세 화면 몫은 거의 0이다 —
남은 건 목록 화면의 5초 폴링뿐이다.

### 왜 롱테일을 걱정하지 않아도 되는가

100,000 DAU에서 슬롯 밖으로 밀리는 760종목은 **정의상 동시 시청자가 1~2명인
종목**이다. 그 종목에 1초 폴링을 주면 `ceil(760/200) = 4 req/s`로 끝난다.
**"실시간이 절실한 종목"과 "종목 수가 많은 구간"이 서로 배타적**이라
양쪽 다 싸다.

## 실패 모드와 대비 (이게 설계의 절반이다)

| 실패 | 결과 | 대비 |
|---|---|---|
| **체결·호가가 LOSSY** — 백프레셔 시 프레임 드롭 | 가격이 조용히 멈춤 | **심볼별 「마지막 프레임 수신 시각」 감시.** N초 넘으면 즉시 REST 폴백 + 재구독. **구독 심볼도 30초 백스톱 폴링을 유지**한다 |
| **연결 2개 상한** — 초과 시 가장 오래된 연결 종료 | 재배포 때 기존 연결이 끊김 | 웹소켓은 **폴러 컨테이너 1곳만** 소유. 배포는 old drain → new 순서. 인스턴스 2대 되면 **연결 소유자를 반드시 하나로** 고정 |
| **180초 idle 종료** | 조용히 끊김 | 60초 `PING` (raw text). 스펙 권장값 그대로 |
| **`server-shutdown` 프레임** | 상류 배포 시 끊김 | 프레임 감지 → 즉시 재연결 + **전체 재선언** |
| **재연결 폭풍** | 상류에 부하 | 지수 백오프 1s→2s→4s + jitter. **이전 연결을 먼저 닫고** 재연결 |
| **`rate-limit-exceeded` (5회/초)** | 선언 실패 | 200ms 디바운스 + 히스테리시스로 애초에 근처도 안 감. 실패 시 1초 후 재선언 |
| **웹소켓 전면 장애** | 실시간 소실 | **폴링 경로를 지우지 않는다.** Tier S가 비면 자동으로 Tier A(1초 폴링)로 강등 — 지금 수준으로 되돌아갈 뿐 장애가 아님 |

**마지막 줄이 가장 중요하다**: 이 설계는 폴링을 **대체**하는 게 아니라
**앞에 얹는다.** 웹소켓이 죽어도 오늘과 같은 동작으로 내려앉는다.

## 남는 트레이드오프 (없앨 수 없는 것)

정직하게 적는다.

1. **슬롯 200은 하드 리밋이다.** 동시 상세 시청 distinct가 140을 넘으면
   누군가는 1초 폴링으로 밀린다. 1초 폴링도 FE 상세 폴링(2초)보다는 빠르므로
   **체감 차이는 작지만 0은 아니다.**
2. **구현 복잡도가 실질적으로 올라간다.** 연결 관리·재연결·구독 상태 기계·
   백스톱 폴링·히스테리시스가 새로 생긴다. **폴링 코드는 그대로 남는다** —
   코드가 줄지 않고 늘어난다.
3. **디버깅이 어려워진다.** "왜 이 종목만 안 움직이지"의 원인이
   구독 슬롯·프레임 드롭·연결 상태로 늘어난다. → **구독 상태를 `/health`에
   노출하는 것이 선택이 아니라 필수다.**
4. **`personal:order` 채널은 이 설계에 넣지 않았다.** 주문 기능이 생기면
   슬롯 예산을 다시 짜야 한다(계정별 1건씩 소비).

## 단계별 이행 (폴링 → 하이브리드)

각 단계가 **독립적으로 이득이 있고 되돌릴 수 있게** 나눴다.

| 단계 | 내용 | 이득 | 되돌리기 |
|---|---|---|---|
| 1 | 요청-시점 신선도 보장 (배치+single-flight) | **가격 정확성** — 20만→22만 점프 제거 | 쉬움 |
| 2 | Tier B를 5초로 · Redis 파이프라인 · 배치 병렬화 | REST −80%, 신선도 손실 0 | 상수 되돌리기 |
| 3 | 구독 없이 **Tier 구조만** 먼저 도입 (S를 1초 폴링으로) | 구조가 자리잡음. 웹소켓은 나중에 S만 교체 | 쉬움 |
| 4 | 웹소켓 `trade` 구독으로 Tier S 교체 | **tickFast의 80 req/s 소멸** · 형성봉 실시간화 | **플래그로 폴링 복귀** |
| 5 | `orderbook` 구독 추가 | 호가 커버리지 40 → 60, REST 0 | 동일 |

**3단계가 핵심이다.** Tier 구조를 먼저 만들어 두면 웹소켓은 "Tier S의
공급원을 REST에서 구독으로 바꾸는 일"로 축소된다. 실패하면 공급원만
되돌리면 된다 — 이게 이 큰 변경을 안전하게 만드는 유일한 방법이다.

## ✗ Toss는 `1m`·`1d`만 지원한다 — 네이티브 인터벌 안은 폐기

```
/api/v1/candles  interval  enum: ["1m","1d"]  (required)
                 count     max: 200, default 100
```

「확정 사항 4」의 **(a) 네이티브 5m/60m 확인** 안은 **사라졌다.**
5m·10m·30m·60m을 1분봉에서 접는 현재 구조가 **불가피하다.**

따라서 60분봉 120개 = 1분봉 7,200개 = **36회 호출**이라는 산수는 그대로다.
남은 해법은 **(c) 점진적 렌더**와 **(d) 배치 사전 적재**뿐이고,
여기에 하나를 더한다 — **(e) 콜드일 때 표시 봉 수를 줄인다.**
60분봉 첫 화면을 120봉이 아니라 40봉으로 그리면 2,400봉 = **12회**(약 0.55초)다.
스크롤하면 그때 이어 받는다(`NextBefore`가 이미 있다).

## ✓ SSE는 DB 커넥션을 잡지 않는다 — API 풀 16이 안전하다

`quotes_marketdata.go:412` `ServeStream` / `:479` `ServeQuoteStream`을 확인했다.

1. 진입 시 스냅샷 조회 1회 → **커넥션 즉시 반환**
2. 이후 `streamHub.Subscribe`가 준 **Go 채널에서 블록**
3. 이벤트는 폴러가 허브로 밀어 준다 — 스트림 goroutine은 DB를 다시 안 본다

```go
for {
    select {
    case <-ctx.Done(): return
    case ev, open := <-ch:            // ← DB가 아니라 채널
        if !open { return }
        writeSSE(w, flusher, ev)
    }
}
```

**따라서 P1-9의 「API 16」에 SSE는 제약이 아니다.** 스트림이 잡는 것은
goroutine 1개 + HTTP 커넥션 1개이지 DB 커넥션이 아니다.

> 다만 별개로 하나 눈에 띈다(이번 범위 밖): `SetWriteDeadline(time.Time{})`으로
> 쓰기 마감을 없애고 `RequestTimeout`도 SSE를 제외한다. 죽은 클라이언트가
> TCP 타임아웃까지 goroutine과 소켓을 잡는다. 2 OCPU 박스에서 **HTTP 커넥션
> 상한**은 따로 봐야 할 수 있다. DB와는 무관하다.

## 1. 하드웨어 제약 (확정)

| | DB — MySQL.FREE (OCI HeatWave) | API — VM.Standard.A1.Flex |
|---|---|---|
| CPU | **1 ECPU** | **2 OCPU (ARM64 Ampere)** |
| Memory | **8 GiB** (버퍼풀 4 GiB 실측) | 12 GiB |
| Network | 1 Gbps | 2 Gbps |
| Storage IOPS | 3,750 | boot 50 GiB |
| **Storage 처리량** | **29 MiB/s** | — |

**이 두 숫자가 나머지를 지배한다.**

- **DB 1 ECPU** — 커넥션을 늘려도 처리량이 늘지 않는다. 동시에 의미 있게
  실행되는 쿼리는 **2~4개**가 상한이다. 그 이상은 큐잉과 컨텍스트 스위칭이다.
- **스토리지 29 MiB/s** — 버퍼풀 4 GiB **밖**의 읽기가 극도로 비싸다.
  2.4 GB를 훑는 쿼리는 캐시 미스 시 **83초**가 걸린다. `057` 마이그레이션 머리말의
  「프로젝션 47초」가 정확히 이 벽이다.

### 이 제약이 뒤집는 것

| 원래 추천 | 확정 후 |
|---|---|
| P1-9: `max_connections` 250~300으로 **상향** | **상향하지 않는다.** 1 ECPU에서 커넥션을 늘리는 것은 고갈을 늦출 뿐 처리량을 못 늘린다. 대신 **총 풀 배정을 대폭 축소**한다 |
| P1-5: 필요 시 ngram FULLTEXT | **하지 않는다.** TEXT 4컬럼 ngram 인덱스는 4 GiB 버퍼풀을 밀어낸다. 29 MiB/s에서 그건 전면 열화다 |
| P2-12: 백업 테이블 1.27 GB "상시 항목" | **P1로 승격.** 버퍼풀의 32%, 스토리지의 2.5%. 이 스펙에서 가장 값싼 개선이다 |
| P1-5: multi-valued index | **유지.** 심볼 문자열만 담아 인덱스가 작다. 이 제약과 잘 맞는 유일한 구조적 해법 |

**HeatWave 16 GiB**는 별도로 시험할 가치가 있다 — `news_articles` 전체를
올려 두면 P1-5의 스캔이 인메모리 병렬로 처리될 수 있다. 다만 `LIMIT 100`이 붙은
짧은 쿼리는 옵티마이저가 오프로드하지 않는 경향이 있고 고정 오버헤드가 있다.
**시험 대상이지 계획의 기둥은 아니다.**

## 2. API 인스턴스 1대 (확정) — 배치는 별도 인스턴스

**이로써 두 작업이 계획에서 빠진다:**

- **P0-1의 리더 락(E) — 하지 않는다.** 인스턴스가 1대면 중복 폴링이 없다.
- **P1-4의 뉴스 캐시 Redis 이전(E) — 하지 않는다.** 공유할 상대가 없는데
  목록 payload 직렬화 비용만 는다. 프로세스 내 맵을 유지하고 2계층·LRU·바이트
  상한만 넣는다. 12 GiB 중 **128 MB**까지는 여유롭게 줄 수 있다.

**폴러 배치 위치** — 배치 잡을 별도 인스턴스로 빼는 계획에 **가격 폴러를
같이 보내면 안 된다.** Redis가 API 박스의 compose 안에 있어서, 폴러만 다른
박스로 가면 심볼당 Redis 왕복이 0.1ms에서 0.5~1ms로 늘어난다 — P0-1에서
가장 아픈 비용이 오히려 커진다.

> **폴러는 API 박스에 남기되 별도 컨테이너로 분리하고, Redis 로컬성을 유지한다.**
> 무겁고 버스트가 심한 배치 잡(점수 계산·백필)만 다른 인스턴스로 보낸다.
> 이러면 P0-1의 워커 분리(G)에 **추가 인스턴스 비용이 0**이다.

## 3. 결정 Q1 — 안 보는 종목의 가격 갱신

**결론: 끄는 것이 맞다. 우려했던 사용성 저하는 실제로는 일어나지 않는다.**

폴링을 끄면 무슨 일이 나는지 코드를 따라가 봤다. 우려는 "Redis에 없으면
사용자 요청이 Toss를 동기로 불러서 느려진다"였는데, **그 경로가 아니다.**

`GetPrices`(`market_data_store.go:425`)는 Redis 미스를 **DB `symbol_last_prices`로
폴백**하고, 그 값으로 Redis도 다시 채운다:

```go
for sym, p := range s.quoteTerminal.GetLastPrices(ctx, missing) {
    out[sym] = p
    s.cacheMarketPrice(ctx, sym, ...)   // Redis 재적재
}
```

`GetLastPrices`(`quote_terminal.go:287`)는 `WHERE symbol IN (...)` **한 방**이고
PK 조회다. 그리고 `EnsurePrices`가 `missing`을 계산하는 시점은 **이 DB 폴백
이후**라, DB에 값이 있는 심볼은 `missing`에 들어가지 않는다.

**즉 폴링을 꺼도 Toss 동기 호출은 발생하지 않는다.** 실제 시퀀스는:

1. 사용자가 보유 목록을 연다 → Redis MGet 미스
2. **DB `IN` 조회 1회** → 마지막으로 기록된 가격을 즉시 반환 (수 ms)
3. 같은 함수의 첫 줄에서 `s.Touch(sym)`이 이미 불렸다
   (`market_data_store.go:169`) → 그 심볼들이 `active`에 들어간다
4. **다음 `tickPrice`(≤1초 뒤)가 그 종목들을 갱신** → 정확한 값

**따라서 실제 UX 저하는 "로딩 지연"이 아니라 "첫 프레임에 조금 낡은 가격이
보였다가 1초 안에 정정되는 것"이다.** 스피너도, 빈 값도, 지연도 없다.

얼마나 낡는가:

| 상황 | DB에 있는 값 | 체감 |
|---|---|---|
| 장 마감 후 | 그날 종가 | **차이 없음** (마감 중엔 어차피 안 변한다) |
| 장중, 5분 내 누가 봄 | 5분 이내 값 | 거의 없음 |
| 장중, 오랜만에 접속 | 마지막 관측 가격 | **1초간 몇 분 전 값** → 정정 |
| 한 번도 기록된 적 없는 심볼 | 없음 → Toss 동기 1회 | 신규 종목만. 드물다 |

### ⚠ 2차 검토에서 위 결론을 **정정한다**

위 표의 **"장중, 오랜만에 접속" 줄을 「거의 없음」으로 본 것이 틀렸다.**

지적받은 시나리오가 정확하다 — 삼성전자를 하루 만에 열었는데
**20만원이 떴다가 22만원으로 바뀌면**, 그건 "약간 낡은 값"이 아니라
**틀린 가격을 확정적으로 보여준 것**이다. 사용자는 그 사이에 판단을 한다.
1초든 0.5초든 길이의 문제가 아니라 **정확성의 문제**다.

그리고 "갱신 중" 표시로 덮는 안도 **철회한다.** 시세 서비스에서 가격 칸에
상태 문구가 뜨는 것은 그 자체로 품질 저하다 — 실시간처럼 보여야 하는 화면에
"실시간이 아님"을 광고하는 셈이다.

**정정된 원칙: 낡은 가격은 애초에 내보내지 않는다.**

폴링을 유지하든 끄든, 옳은 규칙은 하나다 —
**응답 시점에 값이 신선하지 않으면, 신선하게 만든 뒤에 응답한다.**

```
요청 → 캐시 age 확인
  ├ age ≤ Tier 임계값        → 즉시 응답
  ├ 장 마감 세션              → 즉시 응답 (DB 값 = 종가, 정확하다)
  └ 장중 & age 초과           → 배치 Toss 갱신 후 응답 (single-flight)
```

**핵심은 이게 싸다는 것이다:**

- 갱신이 **심볼 배치**다. 보유 15종목을 열면 **Toss 호출 1회**(200종목/호출).
- **최초 진입에만** 난다. 이후 5초 폴링은 전부 웜이다.
- **single-flight**로 동시 사용자가 접힌다 — `quoteRefreshCoordinator.doSync`가
  이미 있고 `NewsStore.List`가 그 참조 구현이다.
- 비용이 **동시 진입 사용자 수**에 비례한다 — 누적 심볼 수가 아니다.
- 지연은 **첫 응답에만 +100~200ms**. FE는 어차피 초기 요청 동안 무언가를
  그리고 있으므로 **체감되지 않는다.** "낡은 값을 즉시 주는 것"만 안 할 뿐이다.

`filterLiveSessionSymbols`가 이미 있으므로 세션 판정도 새로 만들 필요가 없다.

> **정정된 의견**: Q1의 답은 여전히 "끈다"이지만, 이유가 달라졌다.
> 「낡아도 괜찮으니까」가 아니라 **「어차피 요청 시점에 신선도를 보장할 거라서
> 배경 폴링이 그 일을 대신할 필요가 없기 때문」**이다.
> 배경 폴링은 *정확성*을 위한 장치가 아니라 *지연 감추기*를 위한 장치였고,
> 지연은 배치 + single-flight로 훨씬 싸게 감출 수 있다.
>
> 그리고 **웹소켓 구독이 붙으면 이 논의 전체가 사라진다**(2차 검토 장 참조).
> 구독 중인 심볼은 항상 신선하므로 "낡았으면 갱신"이라는 분기 자체가 죽는다.
> 위 요청-시점 갱신은 **웹소켓 이전까지의 정답이자, 이후에는 폴백 경로**다.

## 4. 결정 Q2 — 예열 없이 첫 열람을 빠르게

**결론: 예열은 없애는 게 맞다. 1.7초는 예열로 가릴 문제가 아니라 과다 페치라는
버그에 가깝다.** 원인을 재면 예열이 필요 없어진다.

### 1.7초의 내역

```
maxIntradayRawBars   = 7,200   (quotes_candles_agg.go:38)
tossCandlePageSize   =   200   (candles_page.go:11)
→ 콜드 인트라데이 1회 = 7,200 / 200 = 36회 순차 Toss /candles 호출
   (fetchTossRawCandles의 페이지 루프, maxPages 40)

intradayDisplayBars  =   120   (quotes_candles_agg.go:41)
```

**7,200봉을 받아서 120봉을 그린다.** 36회 순차 호출 × RTT ≈ 1.6초 — 실측 1.7초와 맞는다.

그리고 이건 성능만의 문제가 아니다. **차트 한 번 여는 데 `/candles` 한도
20/s를 1.8초어치 통째로 쓴다.** P0-3에서 본 429의 상당 부분이 예열이 아니라
이 페치 자체다 — 예열은 그것을 30초마다 반복시켰을 뿐이다.

왜 7,200인가: `candleFetchCount`가 `120 * minutes`다. 60분봉 120개를 그리려면
1분봉 7,200개가 필요하다. 그리고 `mapCandleInterval`(`quotes.go:246`)이
**모든 인트라데이 구간을 `1m`으로 매핑**한다 — 5m·10m·30m·60m을 전부
1분봉에서 접어 만든다.

### 예열 없이 줄이는 방법 (효과 순)

**(a) Toss가 네이티브 5m/10m/30m/60m을 지원하는지 확인 — 최우선**
: 지원하면 60분봉 요청이 **36회 → 1회**가 된다. 1.7초 → 약 50ms.
  코드 변경은 `mapCandleInterval` 한 함수와 집계 분기뿐이다.
  현재 코드는 `toss.CandleInterval`에 `1m`·`1d`만 정의해 뒀는데
  (`types_market_data.go:39`), **그게 Toss의 한계인지 이 코드의 한계인지는
  API 문서를 봐야 안다.** 이것 하나로 문제가 끝날 수 있으므로 **가장 먼저 확인할 것.**

**(b) 롤업 계층을 콜드 경로에서도 읽기**
: `057` 마이그레이션이 `candle_bars`를 `p_1m`/`p_5m`/`p_10m`/`p_30m`/`p_60m`/`p_1d`
  파티션으로 나눠 **상위 계층을 이미 저장하고 있다.** 그런데 콜드 경로는
  DB를 보지 않고 곧장 Toss로 간다. 한 번이라도 적재된 종목이면 60분봉 120개를
  **DB에서 7ms에** 읽을 수 있다. 「60일간 아무도 안 연 종목」만 진짜 콜드다.

**(c) 점진적 렌더 — 먼저 그리고 나중에 채운다**
: 첫 응답을 **일봉 또는 적은 봉 수**로 즉시 주고, 전체 구간은 뒤에서 채운다.
  `CandlesPage.NextBefore` 페이지네이션이 **이미 구현돼 있으므로** 배관은 있다.
  체감상 "1.7초 흰 화면"이 "즉시 차트 + 좌측이 채워짐"으로 바뀐다.

**(d) 예열을 「장중·API·사용자비례」에서 「마감후·배치·고정」으로 옮기기**
: 예열을 정말 유지하고 싶다면, **지금 위치가 문제이지 예열 자체가 문제가 아니다.**

  | | 현재 예열 | 배치 사전 적재 |
  |---|---|---|
  | 실행 위치 | API 인스턴스 | **별도 배치 인스턴스** |
  | 시점 | 장중 30초마다 | **마감 후 1일 1회** |
  | 대상 | active 집합 (사용자 수 비례) | 관심 유니버스 (고정) |
  | 상류 경합 | 사용자 요청과 **직접 경합** | **경합 없음** |
  | 비용 증가 | 사용자 수에 비례 | **상수** |

  일 델타는 작다 — `intraday1mFetchTarget`이 공백만 계산하므로
  하루치 ≈ 391봉 = **2회 호출/종목**. 3,000종목이면 6,000회, 20/s에서 **5분**이다.
  사용자가 10배가 돼도 5분 그대로다.

  다만 스토리지를 봐야 한다. 3,000종목 × 3일치 1분봉(롤업 전) ≈ 350만 행,
  행당 ~72바이트 기준 약 **250 MB**. 50 GiB 볼륨에서는 괜찮지만
  **29 MiB/s 처리량**과 P2-12의 1.27 GB를 함께 계산해야 한다.

> **개인 의견**: (a)를 먼저 확인하고, 지원하면 그것만으로 끝난다 — 예열도
> 필요 없고 차트도 빨라진다. 지원하지 않으면 **(c) 점진적 렌더 + (d) 배치
> 사전 적재** 조합이 답이다. 어느 쪽이든 **지금의 장중 API 예열은 제거**한다.
> 그건 원인이 아니라 증상을 30초마다 덧칠하는 구조였다.

## 이 문서를 쓰면서 새로 확인한 사실

감사 문서에 없던 것 세 가지를 코드에서 확인했다. 선택지의 전제가 되므로 먼저 적는다.

1. **가격 Redis 쓰기가 심볼당 개별 왕복이다.**
   `market_data_store.go:487` → `cache_envelope.go:44`가 `rdb.Set()`을 심볼마다 한 번씩
   부른다. 파이프라인이 없다. 즉 매 틱마다 **`|pinned|`회의 Redis 왕복**이 직렬로 난다.
   감사 문서는 MySQL 쓰기만 봤지만, 심볼 수가 커지면 **이쪽이 먼저 무너진다** —
   왕복 0.1ms 가정에서 12,000종목이면 Redis만으로 1.2초, 1초 틱을 지킬 수 없다.

2. **Toss 클라이언트에 자체 레이트리미터가 없다.**
   `toss/client.go:75`의 `do`는 요청 전 아무 제한도 걸지 않고, 응답 헤더를
   읽어 **로그만 남긴다**(`rate_limit.go:52`). 재시도는 401 토큰 갱신 1회뿐이다.
   `apibudget`에도 Toss provider가 **등록돼 있지 않다**(`providers.go`에 없음).
   따라서 지금의 한도 준수는 "폴러가 알아서 조금만 부르기"에만 의존한다.

3. **FE 폴링 주기가 서버 갱신 주기보다 느리다 — 서버가 5배 과표본한다.**

   | 화면 | FE 폴링 | 서버 갱신 | 배율 |
   |---|---|---|---|
   | 종목 상세 (`use-quote-detail.ts:8`) | 2초 | 1초 | 2× |
   | 보유 목록 (`holdings-page-client.tsx:55`) | **5초** | 1초 | **5×** |
   | 관심 목록 (`watchlist-client.tsx:49`) | **5초** | 1초 | **5×** |
   | 마켓 레이더 (`market-radar-config.ts:11`) | 60초 | 1초 | 60× |
   | 지수 (`use-market-indices.ts:9`) | 30초 | 1초 | 30× |

   **"가격이 몇 초까지 stale해도 되는가"의 답은 이미 FE에 적혀 있다.**
   목록 화면은 5초마다 읽으므로 서버가 1초마다 갱신해 봐야 5번 중 4번은
   아무도 안 읽고 버려진다. 이 사실이 아래 P0-1 추천안의 근거다.

# P0-1. `tickPrice` 무제한 대상 (심층 분석)

## 문제

`market_poller.go:167` `tickPrice`가 **1초마다** `pollSymbols()`가 돌려주는
**pinned 전체**를 갱신한다. pinned는 `AllTrackedSymbols()`
(`market_data_store.go:203`) = `user_holdings` 전체 ∪ `watchlist_items` 전체 ∪
`activeSymbols()`(최근 5분 조회) 이다.

1·2단계(변경 감지 + 다중행 upsert)로 **MySQL 쓰기 비용은 없앴다.** 남은 것은:

- **대상 집합이 누적 사용자에 비례한다.** 가입만 하고 떠난 사용자의 종목도
  영원히 pinned에 남는다. 새벽 3시에 접속자가 0명이어도 같은 부하가 흐른다.
- **상한이 없다.** 같은 파일의 `tickFast`는 `marketFastSymbolCap = 40`,
  `tickSlow`는 `slowTargets`로 좁히는데 `tickPrice`만 무제한이다.
- **Redis 쓰기가 심볼당 개별 왕복이다**(위 "새로 확인한 사실" 1).
- **Toss 배치 루프가 순차다**(`market_data_store.go:531`). 200종목씩 나눠
  `for` 루프로 하나씩 기다린다. RTT 100ms면 12,000종목 = 60회 × 100ms = **6초**.
  1초 티커를 달아 두고 `priceBusy`가 5틱을 통째로 스킵한다.

## 목표

1. 상류 Toss 호출량을 **사용자 수와 무관한 상수**로 묶는다.
2. 화면이 실제로 요구하는 신선도(위 표)를 **떨어뜨리지 않는다.**
3. 아무도 안 보는 시간대의 부하를 **0에 수렴**시킨다.
4. API 인스턴스를 2대 이상으로 늘려도 상류 호출이 배수로 늘지 않게 한다.

## 정량 모델

기호를 먼저 고정한다.

| 기호 | 뜻 | 현재 값 |
|---|---|---|
| `U` | 누적 사용자 수 | ~30 |
| `S` | distinct pinned 심볼 수 | 23 |
| `C` | **동시 접속자** 수 | ~1 |
| `I` | `tickPrice` 주기 | 1s |
| `B` | Toss `/prices` 배치 크기 | 200 (상류 고정) |
| `L` | Toss `/prices` 한도 | **15 req/s** |
| `c` | 한 틱에 가격이 실제로 바뀌는 비율 | 장중 ~0.25 추정 |

비용 공식:

```
Toss 호출/s   = ceil(S / B) / I
Redis 왕복/s  = S / I              <- 파이프라인 없음
DB 행 쓰기/s  = S * c / I
DB 문장/s     = ceil(S * c / 400) / I
틱 소요시간   = ceil(S/B) * RTT_toss + S * RTT_redis   <- 둘 다 순차
```

`S(U)` 추정은 감사 문서의 가정(1인 15종목, 1,000명 → 약 3,000)에 맞춰
`S(U) ≈ 3,000 × (U/1,000)^0.6`으로 잡고, 실질 거래 유니버스 ~12,000에서 포화시킨다.

| `U` | `S` |
|---|---|
| 100 | ~750 |
| 1,000 | ~3,000 |
| 10,000 | ~12,000 |

### 현재 구조(I=1s, 캡 없음)의 비용

| `U` | `S` | Toss/s | **한도 소진** | Redis 왕복/s | DB 행/s | 틱 소요(RTT 100ms/0.1ms) |
|---|---|---|---|---|---|---|
| 30 (현재) | 23 | 1 | 7% | 23 | ~0 (마감) | 0.1초 |
| 100 | 750 | 4 | 27% | 750 | 190 | 0.48초 |
| **1,000** | 3,000 | **15** | **100%** | 3,000 | 750 | **1.8초** ← 틱 붕괴 시작 |
| **10,000** | 12,000 | **60** | **400%** | 12,000 | 3,000 | **7.2초** |

**벽은 사용자 1,000명 근처다.** 그 지점에서 세 가지가 동시에 일어난다:
`/prices` 한도를 폴러 혼자 100% 소진해 **사용자의 on-demand `EnsurePrices`가
전부 429**로 떨어지고, 틱 소요가 1초를 넘어 **폴러가 스스로 주기를 잃고**,
Redis 왕복이 초당 3,000회로 다른 캐시 트래픽과 경합한다.

## 선택지

### A. 현재 구조 유지 + 미시 최적화

**동작 방식** — 대상 집합·주기는 그대로 두고 실행만 고친다. Redis `Set`을
파이프라인으로 묶고(왕복 `S` → 1), Toss 200종목 배치 루프를 동시성 4~8로 병렬화한다.

- **장점**: 대상 집합 정의를 안 건드리므로 신선도 회귀가 **원천적으로 없다.**
  리뷰 부담이 가장 작다. 반나절 작업.
- **단점**: **Toss 호출 총량은 1도 안 줄어든다.** 진짜 벽인 `L=15/s`를 그대로 만난다.
  병렬화는 오히려 순간 버스트를 키워 429를 **앞당길 수** 있다.
- **성능 효과**: 틱 소요 7.2초 → 약 1.2초(10,000명). Redis 왕복 12,000/s → 60/s.
  **1,000명 벽은 그대로.**
- **비용 변화**: Redis 명령 수는 같고 왕복만 줄어 CPU·네트워크 대폭 감소.
  DB 무변화. Toss 무변화. Memory 무변화.
- **데이터 신선도**: 개선(틱 스킵이 사라져 오히려 좋아짐). 손실 없음.
- **장애 가능성**: 낮음. 단 병렬화로 인한 버스트 429가 새 실패 모드.
- **구현 난이도**: 하 (반나절)
- **운영 복잡성**: 변화 없음
- **확장성**: **없음.** 1,000명에서 다시 같은 회의를 한다.

### B. 고정 캡 (polling cap)

**동작 방식** — `tickPrice` 대상을 상위 N개(예: 800)로 자른다. 초과분은 갱신하지 않는다.

- **장점**: 상류 비용이 **완전한 상수**가 된다. 한 줄짜리 변경.
- **단점**: **잘린 종목은 영영 갱신되지 않는다.** 정렬 기준이 고정이면 특정
  사용자의 종목이 항상 밀린다. 단독으로는 채택 불가.
- **성능 효과**: Toss 4/s 고정, Redis 800/s 고정.
- **비용 변화**: 상류·DB·Redis 모두 상수. CPU/Memory 감소.
- **데이터 신선도**: 캡 밖 종목은 **무한히 stale**. Redis TTL 20초가 지나면
  `EnsurePrices`가 요청 경로에서 동기로 Toss를 부른다 → 사용자 체감 지연 발생.
- **장애 가능성**: 중. 조용한 열화(silent degradation)라 지표 없이는 못 알아챈다.
- **구현 난이도**: 하
- **운영 복잡성**: 캡 값을 정하고 감시해야 한다.
- **확장성**: 낮음. C와 합쳐야 의미가 있다.

### C. 캡 + 라운드로빈

**동작 방식** — B의 캡에 커서 순회를 얹는다. `capActiveTargets`
(`market_poller.go:252`)에 **이미 구현이 있다** — 정렬 + 커서로 매 틱 다른
구간을 돈다. `tickPrice`에도 같은 것을 적용한다.

- **장점**: 상류 비용이 상수이면서 **모든 종목이 공평하게** 갱신된다.
  기존 코드 재사용이라 새 개념이 없다.
- **단점**: 심볼별 실효 갱신 주기가 `S/cap × I`로 **사용자 수에 따라 나빠진다.**
  운영자가 그 값을 예측하기 어렵다.
- **성능 효과** (cap=800, I=1s):

  | `U` | `S` | Toss/s | 심볼별 실효 주기 |
  |---|---|---|---|
  | 100 | 750 | 4 | **1.0초** |
  | 1,000 | 3,000 | 4 | **3.8초** |
  | 10,000 | 12,000 | 4 | **15초** |

  10,000명의 15초는 **Redis TTL 20초에 아슬아슬하다.** TTL을 넘기면 캐시가 비고
  요청 경로가 동기 Toss 호출로 떨어진다.
- **비용 변화**: Toss·Redis·DB 전부 상수. 사용자가 늘어도 인프라 비용 불변.
- **데이터 신선도**: **사용자 수에 반비례해 나빠진다.** 이게 이 안의 본질적 결함이다.
- **장애 가능성**: 낮음. 열화가 점진적이고 균등하다.
- **구현 난이도**: 하~중 (기존 `capActiveTargets` 재사용)
- **운영 복잡성**: 캡 하나. 낮음.
- **확장성**: 중. 비용은 막지만 **신선도로 대가를 치른다.**

### D. 배치 요청 최적화

**동작 방식** — 한 호출에 더 많은 심볼을 싣는다.

- **평가**: **이미 200종목/호출이고 이건 상류가 정한 값이다.** 더 키울 수 없다.
  실제로 고칠 것은 `market_data_store.go:531`의 **순차 루프**뿐이다(옵션 A에 포함).
  호출 **총량**은 `ceil(S/200)`으로 변하지 않는다.
- **결론**: 독립 선택지가 아니다. A의 일부로 흡수한다.

### E. Shared cache / 폴러 리더 선출

**동작 방식** — Redis 락으로 API 인스턴스 중 **한 대만** 폴링하게 한다.
나머지는 Redis에 쓰인 결과를 읽기만 한다.

- **장점**: 인스턴스를 늘려도 상류 호출이 **배수로 늘지 않는다.**
- **단점**: 지금은 API가 1대라 **효과가 0이다.** 다중 인스턴스의 *전제조건*이지
  현재 문제의 해결책이 아니다.
- **성능 효과**: 인스턴스 K대에서 Toss 호출 `K배 → 1배`.
- **비용 변화**: Redis 키 1개(락). 그 외 없음.
- **데이터 신선도**: 무영향. 리더 장애 시 락 TTL만큼 갱신 공백.
- **장애 가능성**: 중. 리더 교체 구간의 공백, split-brain 시 중복 폴링.
- **구현 난이도**: 중
- **운영 복잡성**: 중 (리더가 누구인지 관측 가능해야 한다)
- **확장성**: **수평 확장의 필수 조건.** P1-9와 세트로 봐야 한다.

### F. 계층 주기 (tiered refresh interval) ★

**동작 방식** — pinned를 하나로 보지 않고 **화면이 요구하는 신선도별로** 나눈다.
주기는 FE 폴링 주기에서 그대로 가져온다.

| Tier | 대상 | 주기 | 근거 |
|---|---|---|---|
| A | `Touch`된 심볼 = 지금 상세 화면 | **1초** | FE 2초 폴링 |
| B | 보유·관심 (목록에 뜨는 것) | **5초** | FE 5초 폴링 |
| C | 나머지 pinned | **30초** | Redis TTL 20초를 채우는 용도 |

- **장점**: **신선도를 한 톨도 잃지 않으면서** 비용이 줄어든다. 지금 서버는
  목록 종목을 FE보다 5배 빠르게 갱신하고 그 4/5를 버리고 있다. 그 낭비만 없앤다.
  개념이 단순하고(주기 상수 3개), 회귀 위험이 매우 낮다.
- **단점**: Tier 판정 로직이 필요하다(`activeSymbols` vs pinned 차집합).
  Tier 경계에서 심볼이 오가면 갱신 주기가 튄다.
- **성능 효과** (A = 동시접속 × 5종목, B/C는 `S`를 절반씩 가정):

  | `U` | A | B | C | Toss/s | **한도 소진** |
  |---|---|---|---|---|---|
  | 100 | 30 | 400 | 320 | 1 + 0.4 + 0.07 = **1.5** | 10% |
  | 1,000 | 150 | 1,500 | 1,350 | 1 + 1.5 + 0.23 = **2.7** | 18% |
  | 10,000 | 600 | 5,000 | 6,400 | 3 + 5 + 1.1 = **9.1** | **61%** |

  현재 구조의 60/s가 9.1/s가 된다 — **6.6배 감소, 신선도 손실 0.**
- **비용 변화**: Toss −85%, Redis 왕복 −80%, DB 행 −80%. CPU 감소. Memory 무변화.
- **데이터 신선도**: **화면 기준으로는 무변화.** 아무도 안 보는 Tier C만 30초로 낡는다.
- **장애 가능성**: 낮음. Tier C가 늦어도 `EnsurePrices` 폴백이 받는다.
- **구현 난이도**: 중 (티커 3개 + Tier 분류)
- **운영 복잡성**: 낮음. 상수 3개가 FE 상수와 1:1 대응이라 근거가 자명하다.
- **확장성**: 중~상. 10,000명까지는 한도 안. 그 위는 H가 필요하다.

### G. 전용 백그라운드 워커 분리

**동작 방식** — 폴러를 API 프로세스에서 떼어 `worker-prices` 컨테이너로 옮긴다.
이 코드베이스에 **이미 선례가 있다** — `market_data_store.go:110` 주석이
실적 캘린더·인사이트를 워커로 옮긴 이유를 적어 뒀다.

- **장점**: 사용자 요청 처리 프로세스가 상류 사정으로 느려지지 않는다.
  API 커넥션 풀 압박이 줄어(P1-9와 직결) API를 자유롭게 스케일아웃할 수 있다.
  폴러만 따로 재기동·조절할 수 있다.
- **단점**: 컨테이너가 하나 늘고 배포·감시 대상이 는다. 워커가 죽으면 가격이
  전부 멈춘다(단일 장애점) — 헬스체크가 필수.
- **성능 효과**: 상류 호출 총량은 **불변.** API의 CPU·커넥션·goroutine이 줄어든다.
- **비용 변화**: DB 커넥션이 API 풀에서 워커 풀로 이동. 컨테이너 1개 분량의 Memory 증가.
- **데이터 신선도**: 무영향.
- **장애 가능성**: 중 (새 단일 장애점, 다만 `EnsurePrices` 폴백이 완충)
- **구현 난이도**: 중
- **운영 복잡성**: 중
- **확장성**: **상.** E와 합치면 다중 인스턴스가 열린다.

### H. 수요 기반 구독 (demand-driven subscription) ★★

**동작 방식** — pinned의 **정의 자체를 바꾼다.**
"전체 사용자가 언젠가 담아 둔 종목"(재고) → "**지금 열려 있는 화면이 요구하는
종목**"(수요).

이 코드베이스에 **절반은 이미 있다** — `MarketDataStore.Touch`/`activeSymbols()`
(5분 TTL)가 정확히 그 레지스트리다. 지금은 그 위에 `AllTrackedSymbols`의
전역 합집합을 **덧붙여서** 효과를 지우고 있을 뿐이다.

바꿀 것: 목록 화면(보유·관심)이 요청할 때 자기 심볼을 `Touch`하도록 하고,
`refreshPinned`에서 `holdings.ListAllSymbols` / `watchlist.ListAllSymbols`
전역 조회를 **뺀다.**

- **장점**:
  - 대상 크기가 **누적 사용자가 아니라 동시 접속자**에 비례한다.
    가입자가 100만이어도 새벽 3시엔 `S=0`이다.
  - `AllTrackedSymbols`의 매분 `SELECT DISTINCT` 두 방도 함께 사라진다.
  - `cared`의 자기 참조 고리(`market_poller.go:38` 주석)가 자연히 풀린다.
- **단점**:
  - **첫 요청이 콜드가 된다.** 사용자가 오랜만에 접속하면 그 종목들은 Redis에
    없고 `EnsurePrices`가 요청 경로에서 동기로 Toss를 부른다(수백 ms).
    → 완화: 화면 진입 시 **선등록(prewarm) 힌트**를 보내고, 첫 응답은
    DB last-good으로 낸다.
  - `Touch` 호출 지점을 빠짐없이 심어야 한다. 하나 빠지면 그 화면만 조용히 느려진다.
- **성능 효과** (동시 접속률 = DAU의 4% 가정):

  | DAU | 동시 `C` | `S_demand` | Toss/s (I=1s) | Toss/s (**F와 결합**) |
  |---|---|---|---|---|
  | 100 | 4 | ~60 | 1 | **~1** |
  | 1,000 | 40 | ~500 | 3 | **~1.4** |
  | 10,000 | 400 | ~2,500 | 13 | **~2.3** |
  | 100,000 | 4,000 | ~10,000 | 50 | **~7** |

  **F와 곱해지면 100,000 DAU에서도 7/s로 한도 안이다.** 새벽에는 0/s.
- **비용 변화**: Toss −80~95%. Redis 왕복 동일 비율 감소. DB에서 매분 도는
  `SELECT DISTINCT` 2개 제거. Memory 감소(pinned 슬라이스가 작아짐).
- **데이터 신선도**: 보고 있는 종목은 **동일하거나 더 신선**(대상이 작아 틱이
  안 밀린다). 안 보는 종목은 정의상 신선할 필요가 없다. 단 **재진입 첫 화면**의
  콜드 지연이 새로 생긴다 — 이게 이 안의 유일한 실질 대가다.
- **장애 가능성**: 중. `Touch` 누락이 조용한 열화를 만든다.
  → 지표: "요청 경로에서 발생한 동기 Toss 호출 수"를 세면 누락이 바로 보인다.
- **구현 난이도**: 중~상 (레지스트리 + 호출 지점 심기 + 선등록)
- **운영 복잡성**: 중
- **확장성**: **최상.** 비용이 동시성에 비례하므로 인프라 비용과 사용자 규모가
  선형으로 맞물린다. 100배 트래픽에서도 구조를 다시 갈아엎을 필요가 없다.

### I. 상류 실시간 스트림 (WebSocket)

**동작 방식** — Toss가 시세 푸시를 제공한다면 폴링 자체를 없앤다.
비용이 **심볼 수가 아니라 구독 유지 수**에 비례한다.

- **평가**: **가장 옳은 구조이지만 전제가 미확인이다.** `internal/toss/`에
  스트림 클라이언트가 없고, 제공 여부·한도·인증 방식을 확인하지 않았다.
- **장점**: 폴링 오버헤드 0. 신선도 최상(변경 즉시).
- **단점**: 연결 관리·재접속·백프레셔가 새로 필요하다. 상류가 끊기면 폴링
  폴백이 여전히 있어야 하므로 **코드가 줄지 않고 늘어난다.**
- **구현 난이도**: 상
- **운영 복잡성**: 상
- **확장성**: 최상
- **결론**: **먼저 조사 대상.** 제공된다면 H·F의 장기 대체안이 된다.
  제공되지 않으면 H·F가 최선이다.

## 추천안

**단기 patch (반나절)** — `A` + `F`의 Tier B만
: Redis 파이프라인화 + Toss 배치 병렬화 + **목록 종목 갱신 주기를 1초 → 5초로.**
  마지막 하나는 상수 변경 한 줄에 가깝고 **FE가 이미 5초로 읽으므로 화면이
  전혀 달라지지 않는다.** 즉시 상류 호출 5배 여유가 생긴다. 위험 대비 효과가
  이 목록에서 가장 좋다.

**장기 architecture (2~3주)** — `H` × `F` × `C` × `G` × `E`
: 대상은 **수요 기반**(H)으로, 주기는 **계층**(F)으로, 그 위에 **캡+라운드로빈**(C)을
  폭주 방지 안전판으로 둔다. 실행은 **전용 워커**(G)에서 하고, 인스턴스가
  늘면 **리더 락**(E)이 중복 폴링을 막는다.

### 왜 이 조합인가

세 축이 서로 다른 문제를 막기 때문에 **곱해진다.**

- **F는 낭비를 없앤다.** 화면이 안 읽는 갱신 4/5를 제거한다. 대가가 0이라
  논쟁의 여지가 없다.
- **H는 증가율을 바꾼다.** 비용의 기준을 "누적 가입자"에서 "동시 접속자"로
  옮긴다. F만으로는 10,000명에서 61%까지 차고, 100,000명에서 터진다.
  H가 있어야 그 기울기 자체가 눕는다.
- **C는 상한을 보장한다.** H·F가 예측을 벗어나도(이벤트로 동시 접속 폭증,
  `Touch` 버그로 대상 폭증) 상류 호출이 절대 한도를 넘지 않는다.
  **F·H는 최적화이고 C는 안전장치다** — 성격이 달라 둘 다 필요하다.

### 해결되는 문제

| 지금 | 추천안 적용 후 |
|---|---|
| 1,000명에서 `/prices` 한도 100% 소진 → 사용자 요청 429 | 100,000 DAU에서도 ~7/s (한도의 47%) |
| 새벽 3시에도 12,000종목 갱신 | 동시 접속 0 → 상류 호출 0 |
| Redis 왕복 초당 12,000회 | 파이프라인 + 대상 축소로 초당 수십 회 |
| 틱 소요 7.2초 (1초 티커가 무의미) | 대상 축소 + 병렬화로 0.2초 이하 |
| API 인스턴스 2대 = 상류 호출 2배 | 리더 락으로 1배 유지 |
| 폴러가 API의 CPU·커넥션을 먹음 | 별도 워커 (P1-9 여유 확보와 직결) |

### 신선도 기준별 적합 구조

"가격이 몇 초까지 stale해도 되는가"에 대한 답별로 정리한다.

| 허용 stale | 적합 구조 | 비고 |
|---|---|---|
| **1초 이내 (전 종목)** | 어떤 구조로도 불가 | `S>3,000`이면 Toss 한도가 물리적으로 못 준다. 상류 스트림(I)만이 답 |
| **1초 (보는 종목) / 5초 (목록)** | **F + H** ← 현재 FE가 요구하는 수준 | 추천안. 화면 변화 없음 |
| **5초 (전 종목)** | F 단독으로도 충분 | 10,000명까지 한도의 15% |
| **15~30초 허용** | C 단독 (cap=800) | 가장 단순. 100,000명도 상수 비용 |

## 제품/운영 결정 필요 여부

개발자가 임의로 정하면 안 되는 것:

1. **아무도 보지 않는 보유 종목의 가격을 갱신해야 하는가?**
   "아니오"면 H를 바로 채택할 수 있다. "예"(예: 푸시 알림·가격 알림이 서버측
   실시간 감시를 전제)라면 H는 **알림 대상 심볼을 별도 Tier로 유지**해야 하고,
   그 집합의 크기 상한을 제품이 정해야 한다.
2. **재진입 시 첫 화면에서 수백 ms의 가격 로딩을 허용하는가?**
   H의 유일한 실질 대가다. 허용하지 않으면 선등록(prewarm) 구현이 필수가 된다.
3. **Tier별 허용 stale time** — 상세 1초 / 목록 5초 / 그 외 30초를 확정할 것.
   (FE 현재값과 일치하므로 "확인" 수준이지만 문서로 못박아야 한다.)
4. **Toss `/prices` 호출량 상한** — 한도 15/s 중 폴러가 쓸 비율.
   권장 60%(9/s), 나머지는 사용자 요청 몫으로 남긴다.

# P0-3. 배경 예열이 Toss 쿼터를 상시 소진한다

## 문제

`market_poller.go:368` `tickSlow`가 30초마다 `slowTargets`의 종목마다
`refreshRawCandles`를 부른다. 그 함수는 **종목당 Toss `/candles`를 2회**
호출한다(`quotes_marketdata.go:163,164` — 1m + 1d).

- `/candles` 한도는 **20 req/s**인데, 예열이 그 버킷을 **사용자 요청과 공유**한다.
- **`slowTargets`에 상한이 없다.** `tickFast`는 `marketFastSymbolCap = 40`으로
  자르는데 `tickSlow`는 자르지 않는다. 대상 N개 = 한 틱에 **2N 호출**,
  동시성 4로 나가므로 **버스트가 초당 수십 건**이 된다.
- **`cared`가 항상 비어 있다**(P2-15). `loadWatchlistSymbols`가
  `authctx.UserID(ctx)`를 요구하는데 폴러 ctx엔 사용자가 없다
  (`quotes_overlay.go:69`). 따라서 실제 `slowTargets` = `active`뿐이다.
  즉 **P0-3 완화책으로 도입된 `cared` 분리가 아무 일도 하지 않는다.**
- **클라이언트 레벨 방어가 전무하다.** `toss.Client.do`는 요청 전 제한이 없고
  429를 받아도 재시도하지 않을 뿐 **다음 틱에 그대로 다시 시도**한다.
  `apibudget`에 Toss provider가 등록조차 안 돼 있다.

실측(최근 30분, 실사용자 없음): `/candles` rate-limit exceeded **343건**,
low 경고 375건.

## 목표

1. 사용자 요청이 배경 작업 때문에 429를 맞는 일을 **구조적으로** 없앤다.
2. 배경 예열의 비용을 대상 수와 무관하게 **상한**으로 묶는다.
3. 예열이 실제로 얼마의 이득을 주는지를 **측정 가능**하게 만든다.

## 선택지

### A. 예열 제거 (tickSlow의 캔들 부분 삭제)

**동작 방식** — `tickSlow`에서 `refreshRawCandles` 호출을 없앤다.
`triggerQuoteStatsRefresh`만 남긴다.

- **장점**: `/candles` 배경 소비가 **즉시 0**이 된다. 코드가 줄어든다.
  주석(`market_poller.go:378`)이 이미 결론을 적어 뒀다 — v0.10.0 계층 저장
  이후 예열 이득이 "1.7초 → 4ms"에서 **"11ms → 4ms"로 줄었다.**
  7ms를 위해 한도를 태우고 있다.
- **단점**: **"60일간 아무도 안 연 종목"의 인트라데이 차트 첫 열람이 1.7초**가
  된다(주석의 실측). 일봉 모달은 롤업·삭제 대상이 아니라 DB에 영구히 있으므로
  영향 없다(실측 7ms).
- **성능 효과**: 배경 `/candles` 호출 2N/30s → 0. 사용자 요청의 429가 사라진다.
- **비용 변화**: Toss `/candles` −100%(배경분). DB 쓰기(`storeRawTail`) 감소.
  CPU·Memory 감소. **Redis 미스가 늘어 DB 읽기가 소폭 증가**(11ms 경로).
- **데이터 신선도**: 캔들은 요청 시점에 받으므로 **오히려 더 신선**해질 수 있다.
  예열은 30초 전 데이터를 캐시에 넣어 두는 것이라 stale일 수도 있었다.
- **장애 가능성**: 낮음. 제거는 새 실패 모드를 만들지 않는다.
- **구현 난이도**: **하** (호출 한 줄 삭제)
- **운영 복잡성**: 감소
- **확장성**: 상. 배경 비용이 0이면 사용자 수와 무관해진다.

### B. 예열 유지 + 캡·라운드로빈

**동작 방식** — `slowTargets`에 `capActiveTargets(active, N)`을 적용한다.
`/candles` 20/s ÷ 2호출 ÷ (30초 주기) 를 역산하면 **N ≈ 100**이 안전선이지만,
사용자 몫을 남기려면 N=30 정도가 현실적이다.

- **장점**: 예열의 UI 이득을 지키면서 비용에 상한이 생긴다.
  `tickFast`와 동일한 패턴이라 새 개념이 없다.
- **단점**: 여전히 **사용자 요청과 같은 버킷을 쓴다.** 사용자 트래픽이 몰리는
  순간 예열이 그 몫을 먹는 성질은 그대로다. 예열 대상이 캡 밖이면 이득도 없다.
- **성능 효과**: 배경 `/candles` = `2N/30` = N=30일 때 **2/s** (한도의 10%).
- **비용 변화**: Toss −70~90%(현재 대비). DB·CPU 비례 감소.
- **데이터 신선도**: 캡 밖 종목의 캔들 캐시가 낡는다 → 첫 열람 11ms(일봉)/1.7초(인트라데이).
- **장애 가능성**: 낮음
- **구현 난이도**: 하
- **운영 복잡성**: 캡 값 하나 추가
- **확장성**: 중. 상한은 걸리지만 전경/배경 경합은 남는다.

### C. `apibudget`에 Toss 등록 + 배경 예산 분리

**동작 방식** — `apibudget.Provider`에 `toss_candles`·`toss_prices` 등을
추가하고, 폴러가 호출 전 `Check`를 거치게 한다. 배경 소비자에게
**한도의 30% 상한**을 두고 초과 시 이번 틱을 건너뛴다.

- **장점**: 기존 `apibudget` 인프라를 재사용한다. `/health/api-quotas`에
  Toss 소비량이 **처음으로 보이게 된다** — 지금은 로그 grep 말고는 볼 수가 없다.
  provider별로 관리하므로 다른 Toss 엔드포인트에도 확장된다.
- **단점**: `apibudget`의 창(window)이 분/일 단위라 **초 단위 버스트를 못 막는다.**
  `MinInterval`로 흉내낼 수는 있으나 동시성 4와 궁합이 나쁘다.
  즉 이것만으로는 20 req/s를 지키지 못한다.
- **성능 효과**: 일·분 단위 총량은 통제되나 **순간 429는 남는다.**
- **비용 변화**: Redis 카운터 키가 provider 수만큼 증가(무시할 수준).
- **데이터 신선도**: 예산 소진 시 예열 스킵 → B와 유사.
- **장애 가능성**: 낮음
- **구현 난이도**: 중
- **운영 복잡성**: 중 (예산 비율을 정하고 감시)
- **확장성**: 중

### D. Toss 클라이언트에 엔드포인트별 토큰버킷 + 우선순위 ★

**동작 방식** — `toss.Client`에 엔드포인트 그룹별 토큰버킷
(`golang.org/x/time/rate`)을 넣고, 호출자가 **우선순위**를 함께 넘긴다.

```
prices:    15/s   |  orderbook: 15/s  |  trades: 15/s  |  candles: 20/s
우선순위:  foreground(사용자 요청) > background(폴러·예열)
```

배경 호출은 **잔여 토큰이 있을 때만** 통과시키고(`Allow()`), 전경 호출은
대기(`Wait()`)한다. 배경은 거부되면 조용히 스킵한다.

- **장점**:
  - **한도 초과가 구조적으로 불가능**해진다. 대응이 아니라 예방이다.
  - `/candles`만이 아니라 **모든 Toss 엔드포인트**를 한 번에 보호한다
    (P0-1의 `/prices`, `tickFast`의 `/orderbook`·`/trades` 포함).
  - 전경/배경 분리가 **호출 지점이 아니라 클라이언트 층**에 있어,
    새 배경 작업을 추가해도 자동으로 규칙이 적용된다.
  - 429가 사라지면 `market_data_store.go`의 `priceBackoff` 같은 사후 대응
    코드의 부담이 줄어든다.
- **단점**:
  - 전경 호출이 **대기**하게 되므로 요청 지연이 늘 수 있다 → 대기 상한 필수
    (`quoteRefreshWait = 5s` 선례를 따를 것).
  - 다중 인스턴스에서는 **프로세스별 버킷**이라 합계가 한도를 넘는다.
    → 인스턴스 수로 나눠 배분하거나 Redis 기반 분산 버킷이 필요(복잡도 급증).
  - 엔드포인트 → 버킷 매핑 표를 유지해야 한다(상류가 바꾸면 어긋난다).
- **성능 효과**: 429 발생 **0에 수렴**. 배경 작업의 처리량은 잔여분만큼 줄지만
  사용자 요청은 항상 통과한다.
- **비용 변화**: Toss 호출 총량은 **한도 이하로 강제**된다. CPU/Memory 무시할 수준.
- **데이터 신선도**: 배경 작업(예열·가격 폴링)이 혼잡 시 밀린다 → Tier C가 낡는다.
  전경은 무영향.
- **장애 가능성**: 중. 버킷 설정이 틀리면 **전경이 자기 자신을 굶긴다.**
  → 배경 거부율·전경 대기시간을 반드시 메트릭으로.
- **구현 난이도**: 중~상
- **운영 복잡성**: 중
- **확장성**: **상** (단일 인스턴스), 다중 인스턴스는 분산 버킷 추가 필요.

### E. 예열을 "콜드 대상만"으로 좁힌다

**동작 방식** — `refreshRawCandles`를 무조건 부르지 않고, **DB에 인트라데이
데이터가 없거나 오래된 종목만** 대상으로 한다. 즉 예열의 이득이 실제로 큰
(1.7초짜리) 케이스에만 비용을 쓴다.

- **장점**: A(제거)의 비용 절감을 대부분 얻으면서 **A의 유일한 단점(첫 열람 1.7초)을
  정확히 그 지점에서 막는다.** 이론적으로 가장 정확한 해법이다.
- **단점**: "콜드인지" 판정에 DB 조회가 필요하다 — 대상마다 1쿼리.
  대상이 많으면 그 자체가 N+1이 된다(배치 조회로 완화 가능).
  판정 기준(며칠 이상 비면 콜드인가)이 또 하나의 매직 넘버다.
- **성능 효과**: 정상 상태에서 예열 대상 ≈ 0 → `/candles` 배경 소비 거의 0.
  새 종목이 관심에 담기는 순간에만 1회.
- **비용 변화**: Toss 대폭 감소, DB 읽기 소폭 증가(배치 1회/틱).
- **데이터 신선도**: 무영향(예열은 캐시 채우기일 뿐).
- **장애 가능성**: 낮음
- **구현 난이도**: 중
- **운영 복잡성**: 중 (판정 기준 유지)
- **확장성**: 상

## 추천안

**단기 patch (0.5일)** — `A` (예열 제거) + `cared` 정리
: 예열의 이득이 이미 11ms → 4ms로 줄었음을 **코드 주석의 실측이 인정**하고 있다.
  7ms를 위해 `/candles` 한도를 분당 11건씩 넘기는 것은 명백한 손해다.
  동시에 항상 비어 있는 `cared`를 걷어내고 주석을 실제에 맞춘다(P2-15).
  **되돌리기 쉽고**(한 줄), 효과는 즉시 측정된다.

**장기 architecture (1~2주)** — `D` (클라이언트 토큰버킷 + 우선순위)
: P0-3의 근본 원인은 "예열이 너무 많다"가 아니라 **"전경과 배경이 같은 버킷을
  무방비로 쓴다"**이다. 예열을 지워도 P0-1의 가격 폴러와 `tickFast`의
  호가·체결이 같은 문제를 갖는다(실측에 `/stocks` 429가 40건 있다).
  **D는 그 부류 전체를 한 번에 해결한다.**
  D가 들어간 뒤라면 예열을 다시 켜는 것도 안전해진다 — 배경 우선순위로
  잔여 토큰만 쓰기 때문이다. `E`는 D 이후의 선택적 개선으로 남긴다.

### 왜 A → D 순서인가

A는 **지금 새고 있는 구멍을 막고**, D는 **다음 구멍이 생기지 않게** 한다.
D를 먼저 하면 예열이 잔여 토큰 안에서 계속 돌아 "이득 7ms에 비용을 쓰는" 상태가
유지된다. A를 먼저 하면 D를 만드는 동안에도 429가 멈춘다.
반대로 A만 하고 멈추면 P0-1 개선으로 `/prices` 사용이 늘 때 같은 종류의
경합이 다시 나타난다.

# P1-4. 뉴스 목록 캐시의 전면 flush

## 문제

`news_store.go:296` `rememberList`:

```go
if len(st.listCache) >= 64 {
    // 만료분 제거 후에도 64 이상이면
    st.listCache = map[string]newsListCacheEntry{}   // 전면 flush
}
```

캐시 키(`:269`)는 `market ⊕ sourceID ⊕ sort ⊕ Query ⊕ Symbol ⊕ limit`이고
`Query`·`Symbol`은 **사용자 입력**이라 키 공간이 무한하다.

**감사에 없던 추가 문제 두 가지를 확인했다:**

- **ingest가 캐시를 통째로 버린다.** `news_store.go:853`이 `st.listCache = nil`을
  한다. 뉴스 폴러는 **2분 주기**이고 소스 5개가 staggered로 돈다. 즉 어떤
  LRU를 넣어도 **캐시 수명의 상한이 사실상 수십 초**다.
- **market이 분리돼 있지 않다.** 미국 뉴스가 들어와도 **국내 목록 캐시까지**
  함께 날아간다.

즉 지금 구조에서 캐시 히트율의 지배 요인은 64 상한이 아니라 **ingest 무효화**다.
LRU만 넣으면 기대만큼 안 좋아진다.

## 목표

1. 사용자 입력이 만든 키가 **기본 목록 캐시를 밀어내지 못하게** 한다.
2. ingest 무효화의 범위를 **실제로 바뀐 것만**으로 좁힌다.
3. 메모리 상한을 엔트리 수가 아니라 **바이트**로 건다.
4. (장기) API 다중 인스턴스에서 각자 빌드하지 않게 한다.

## 선택지

### A. 전면 flush → LRU 축출

**동작 방식** — 가장 오래 안 쓰인 1건만 제거한다.

- **장점**: 최소 변경. 기본 목록이 검색어에 밀려 통째로 날아가는 일이 사라진다.
- **단점**: **ingest 무효화가 그대로라 효과가 제한적**이다. 또 LRU는
  "자주 쓰이는 것"을 지키지만 여기서 지켜야 할 것은 **"비싼 것"**(기본 목록)이다.
  둘이 대개 일치하지만 검색 트래픽이 몰리면 어긋난다.
  메모리 상한이 엔트리 수로만 걸린다(엔트리 = 최대 300건 기사 payload).
- **성능 효과**: 검색 트래픽 하에서 기본 목록 히트율 개선. ingest 주기 때문에
  전체 히트율 상한은 여전히 낮다.
- **비용 변화**: Memory 상한이 불명확해진다(엔트리 크기 편차). DB 읽기 소폭 감소.
- **데이터 신선도**: 무영향(TTL·무효화 정책 불변).
- **장애 가능성**: 낮음. 단 엔트리 크기 상한이 없으면 **OOM 여지**가 생긴다.
- **구현 난이도**: 하
- **운영 복잡성**: 변화 없음
- **확장성**: 낮음

### B. 2계층 분리 (canonical / ad-hoc) ★

**동작 방식** — 키 공간을 성격으로 나눈다.

| 계층 | 키 | 상한 | TTL |
|---|---|---|---|
| **canonical** | `market × sourceID × sort × limit` — **유한**(대략 2×6×2×3 = 72) | 없음(유한하므로) | 15초 |
| **ad-hoc** | `Query`/`Symbol`이 있는 키 | 작은 LRU (예: 32) + 바이트 상한 | 15초 |

- **장점**: **사용자가 실제로 보는 기본 목록이 절대 밀려나지 않는다.**
  ad-hoc이 아무리 몰려도 canonical은 무사하다. 키 공간이 성격별로 분리돼
  용량 계획이 가능해진다(canonical 72개 × 평균 payload).
- **단점**: 캐시 코드가 두 벌이 된다. 어느 계층인지 판정하는 규칙이 필요하다.
- **성능 효과**: 기본 목록(`/news/domestic`, `/news/us`)의 히트율이
  **검색 트래픽과 무관**해진다. 감사의 "사용자 64명이 서로 다른 종목을 보기만
  해도 캐시가 비워진다" 시나리오가 사라진다.
- **비용 변화**: Memory 상한이 계층별로 명확. DB 읽기 감소(미스 1건 = 298~320ms).
- **데이터 신선도**: 무영향.
- **장애 가능성**: 낮음
- **구현 난이도**: 중
- **운영 복잡성**: 낮음
- **확장성**: 중~상

### C. market별 선택적 무효화 ★

**동작 방식** — `st.listCache = nil` 대신 **해당 market의 키만** 버린다.
더 나아가 **버전 카운터**를 두고 키에 포함시키면(캐시 키에 `market:rev`),
무효화가 O(1)이고 옛 엔트리는 TTL로 자연 소멸한다.

- **장점**: 미국 뉴스 ingest가 국내 목록을 날리지 않는다.
  **이게 히트율의 실제 지배 요인이다** — LRU보다 효과가 크다.
- **단점**: 버전 카운터 방식은 옛 엔트리가 TTL까지 메모리에 남는다(짧아서 무해).
- **성능 효과**: ingest 1회당 무효화 범위가 절반으로. staggered 5소스를
  market별로 묶으면 무효화 빈도도 실질적으로 절반.
- **비용 변화**: Memory 소폭 증가(옛 엔트리 잔존). DB 읽기 감소.
- **데이터 신선도**: **무영향** — 새 기사는 여전히 즉시 반영된다(같은 market이므로).
- **장애 가능성**: 낮음
- **구현 난이도**: 하~중
- **운영 복잡성**: 변화 없음
- **확장성**: 중

### D. `?q=` 검색을 캐싱 대상에서 제외

**동작 방식** — `Query`가 있으면 캐시를 읽지도 쓰지도 않는다.

- **장점**: 가장 단순. 키 공간 폭발의 주범을 원천 차단.
- **단점**: **검색 미스 비용이 그대로 노출된다** — P1-5의 실측으로
  매칭 0건일 때 **320ms + 67,558행 스캔**이다. 캐시를 빼면 그 비용이
  요청마다 난다. **P1-5를 먼저 고치지 않으면 이 안은 위험하다.**
  검색은 사용자가 임의로 만들 수 있으므로 그대로 두면 DoS 벡터다.
- **성능 효과**: 기본 목록 히트율 개선. 검색 응답은 악화.
- **비용 변화**: DB 읽기 **증가**.
- **데이터 신선도**: 검색은 항상 최신(개선).
- **장애 가능성**: **중~상** (P1-5 미해결 시 penetration)
- **구현 난이도**: 하
- **운영 복잡성**: 변화 없음
- **확장성**: 낮음
- **결론**: **P1-5 해결 후에만** 검토할 것. 단독 채택 불가.

### E. Redis로 이전

**동작 방식** — 프로세스 내부 맵을 Redis로 옮긴다.

- **장점**: API 인스턴스 간 **공유**된다 — 2대로 늘려도 각자 빌드하지 않는다.
  TTL·메모리 관리가 Redis에 위임된다(`volatile-lru`가 축출을 맡는다).
  재기동해도 캐시가 살아 있다.
- **단점**:
  - 목록 payload(최대 300건 기사)를 **직렬화·역직렬화**해야 한다.
    현재 프로세스 내 맵은 그 비용이 0이다 — **웜 히트가 느려질 수 있다.**
    (`recordsToArticles` + `filterArticles`의 결과를 저장하므로 payload가 크다.)
  - Redis 메모리를 먹는다. 현재 `used_memory_peak 592MB / maxmemory 1GB`이고
    **축출이 시작되면 `volatile-lru`가 다른 캐시를 버려 stampede가 된다**(P2-14 주의).
  - `doSync` 단일 비행이 프로세스 내부 개념이라 다중 인스턴스에서는
    **분산 락**이 추가로 필요하다.
- **성능 효과**: 다중 인스턴스에서 빌드 횟수 K배 → 1배. 단일 인스턴스에서는
  직렬화 비용만큼 **소폭 악화 가능**.
- **비용 변화**: Redis Memory 증가(목록 payload × 키 수). 네트워크 왕복 추가.
- **데이터 신선도**: 무영향.
- **장애 가능성**: 중 (Redis 압박 → 축출 → 다른 캐시 붕괴)
- **구현 난이도**: 중~상
- **운영 복잡성**: 중 (Redis 메모리 감시 필수)
- **확장성**: **상** (다중 인스턴스의 전제)

### F. 엔트리 바이트 상한 + 캐시 통계

**동작 방식** — 엔트리 수가 아니라 **누적 바이트**로 상한을 걸고,
히트/미스/축출을 카운터로 노출한다.

- **장점**: Memory 상한이 **예측 가능**해진다. A~C 중 무엇을 골라도
  이건 함께 있어야 한다. 통계가 없으면 개선 효과를 검증할 수 없다.
- **단점**: 엔트리 크기를 재야 한다(대략 추정으로 충분).
- **구현 난이도**: 하~중
- **결론**: 독립 선택지가 아니라 **필수 부속.**

## 추천안

**단기 patch (1일)** — `C` + `B` + `F`
: 순서가 중요하다. **`C`(market별 무효화)가 히트율에 가장 큰 영향**을 준다 —
  지금은 2분마다 미국 ingest가 국내 캐시를 날리고 있다. 그 위에
  `B`(2계층)로 사용자 입력이 기본 목록을 밀어내지 못하게 하고,
  `F`(바이트 상한 + 통계)로 메모리와 검증 수단을 확보한다.
  `A`(LRU)는 B의 ad-hoc 계층 안에 자연히 포함된다.

**장기 architecture** — `E` (Redis 이전)
: **단, API 인스턴스를 실제로 2대 이상 띄우기로 결정한 다음에** 한다.
  지금 하면 직렬화 비용만 늘고 얻는 게 없다. P1-9(커넥션 풀)의
  수평 확장 결정과 **묶어서** 판단해야 한다.
  이전할 때는 P2-14의 경고를 지킬 것 — Redis `maxmemory` 여유를 먼저 확보하고,
  `evicted_keys`를 감시하며 넣는다.

### 왜 이 순서인가

`B`(LRU/2계층)만 하면 **효과가 기대에 못 미친다.** ingest 무효화가 캐시 수명을
수십 초로 묶고 있기 때문이다. `C`를 먼저 해야 `B`의 이득이 드러난다.
`F`가 없으면 어느 쪽이 얼마나 기여했는지 알 수 없어 다음 결정을 근거 없이 하게 된다.

`D`(검색 캐싱 제외)는 **P1-5를 고치기 전엔 위험하다** — 두 항목이 결합돼 있다.

## 제품/운영 결정 필요 여부

1. **뉴스 목록의 허용 stale time** — 현재 `listCacheTTL = 15초`.
   ingest 무효화를 market별로 좁히면 실효 stale이 지금보다 늘 수 있다.
   "새 기사가 몇 초 뒤에 보여도 되는가"를 정해야 한다. (권장: 15초 유지)
2. **뉴스 캐시에 허용할 프로세스 메모리 상한** — 권장 64MB.
   canonical 계층은 상한 없이 두므로 그 크기를 실측해 정해야 한다.
3. **API 인스턴스를 2대 이상 운영할 계획이 있는가** — E의 착수 조건.
   P1-9와 함께 결정할 것.
4. **검색(`?q=`) 기능의 트래픽 비중** — 낮다면 D를 P1-5 이후에 채택해 단순화 가능.

## 구현 계획

1. **계측 먼저** — 캐시 히트/미스/축출/전면 flush 카운터 추가, 1일 관찰.
2. `st.listCache = nil` → **market별 선택 무효화**로 교체 (`C`).
3. 재측정 — 히트율 변화 확인. (이 단계만으로 상당 부분 해결될 가능성이 있다.)
4. 캐시를 canonical / ad-hoc **2계층으로 분리** (`B`).
5. ad-hoc 계층에 LRU + **바이트 상한** 적용 (`F`).
6. `news_store_swr_test.go`에 축출 정책 테스트 추가
   (canonical이 ad-hoc 폭주에 살아남는지).
7. **벤치마크**: 서로 다른 `?symbol=` 100개를 던진 직후
   `/news/domestic` 응답시간 측정 (현재는 미스 → 300ms 예상).
8. (조건부) API 다중화 결정 시 `E` Redis 이전 착수.

# P1-5. 뉴스 필터가 매칭 0건일 때 67,558행을 스캔한다

## 문제

`news_repo.go:409,413`:

```sql
WHERE market = ?
  AND JSON_CONTAINS(symbols_json, JSON_QUOTE(?))
  AND (headline LIKE ? OR summary LIKE ? OR headline_ko LIKE ? OR summary_ko LIKE ?)
ORDER BY published_at DESC LIMIT ?
```

두 조건 모두 인덱스를 못 탄다(JSON 함수, 선행 와일드카드). MySQL은
`idx_news_market_published`를 `published_at DESC` 순으로 훑으며 필터링하고
`LIMIT`이 차면 멈춘다 — **매칭이 없으면 멈출 수 없다.**

실측: `symbol=999999` → **298ms / 67,558행**, `q=zzqqxx` → **320ms / 67,558행**.

> 감사 문서는 "파티션 전체"라고 썼지만 `news_articles`는 파티션 테이블이 아니다
> (`migrations/010_news_articles.sql`). 실제로는 **해당 market의 인덱스 레인지
> 전체**다. 결론은 같다.

**증가 계수**: 기사 81k → 500k면 이 비용이 선형으로 늘어 **약 1.8초**가 된다.
검색어는 사용자가 임의로 만들 수 있으므로 **cache penetration 벡터**다.

## 목표

1. 매칭 0건 케이스의 비용을 **행 수와 무관한 상수**로 만든다.
2. 기사 수가 10배가 돼도 종목 필터 응답이 유지되게 한다.
3. 스키마 변경을 **재태깅 배치와 어긋나지 않게** 한다.

## 선택지

### A. Negative caching (즉효 완화)

**동작 방식** — 결과 0건인 `(market, symbol, query)` 조합을 짧은 TTL(예: 60초)로
"없음"으로 캐싱한다.

- **장점**: **스키마 변경 없음.** 코드 수십 줄. 즉시 penetration을 막는다.
  P1-4의 캐시 계층에 자연히 얹힌다.
- **단점**: **첫 요청은 여전히 298ms**다. 근본 해결이 아니다.
  키 공간이 사용자 입력이라 negative 캐시 자체가 무한히 늘 수 있다
  (→ 작은 LRU + 바이트 상한 필요).
  기사가 새로 들어오면 negative가 틀려진다 → TTL을 짧게 유지해야 한다.
- **성능 효과**: 반복 요청 298ms → ~0ms. 첫 요청 무변화.
- **비용 변화**: DB 읽기 대폭 감소(반복분). Memory 소폭 증가.
- **데이터 신선도**: **최대 TTL만큼 "뉴스 없음"이 늦게 풀린다.**
  종목 상세에서 그 종목의 첫 기사가 60초 늦게 보일 수 있다.
- **장애 가능성**: 낮음
- **구현 난이도**: **하**
- **운영 복잡성**: 낮음
- **확장성**: 낮음 (첫 요청 비용이 기사 수에 선형)

### B. Multi-valued index (MySQL 8.0.17+) ★

**동작 방식** — `symbols_json` 배열에 multi-valued index를 건다.
현재 MySQL은 **8.0.46**이라 지원된다.

```sql
ALTER TABLE news_articles
  ADD INDEX idx_news_symbols_mv ((CAST(symbols_json->'$' AS CHAR(16) ARRAY)));
```

쿼리는 `JSON_CONTAINS(...)` → `? MEMBER OF (symbols_json->'$')`로 바꿔야
인덱스를 탄다.

- **장점**:
  - **ALTER 한 방.** 쓰기 경로 코드 변경이 **전혀 없다** — `symbols_json`을
    쓰면 인덱스가 자동으로 따라온다.
  - **재태깅 배치와 어긋날 여지가 원천적으로 없다**(같은 컬럼이므로).
    조인 테이블 방식의 가장 큰 위험을 회피한다.
  - 매칭 0건이 **인덱스 프로브 1회**로 끝난다 — 이 항목의 병리적 케이스가 사라진다.
- **단점**:
  - `ORDER BY published_at DESC`를 인덱스로 만족시키지 못한다 →
    **매칭 행을 모아 filesort** 한다. 다만 매칭 행은 보통 수십~수백 건이라
    정렬 비용이 작다. 흔한 종목(`005930`, 760행)에서 현재 2.28ms 대비
    **회귀 가능성이 있다** — 반드시 전후 `EXPLAIN ANALYZE` 비교 필요.
  - 배열 원소 타입이 섞여 있으면 인덱스가 안 만들어진다(전부 문자열이어야 함).
    → 사전에 `symbols_json` 값 검증 필요.
  - 쓰기 시 인덱스 엔트리가 **원소 수만큼** 생긴다 → ingest 쓰기 비용 증가.
  - 온라인 DDL이지만 81k행에서도 **락 구간**이 있다 → 저트래픽 시간대 필요.
- **성능 효과**: `symbol=999999` **298ms → 1ms 미만**.
  기사 500k에서도 상수. 흔한 종목은 소폭 변동(측정 필요).
- **비용 변화**: 인덱스 크기 증가(기사당 평균 심볼 수 × 16바이트).
  ingest 쓰기 비용 소폭 증가. DB 읽기 대폭 감소.
- **데이터 신선도**: **무영향**(동기화 지연이 존재하지 않는다).
- **장애 가능성**: 낮음. 단 DDL 중 락.
- **구현 난이도**: 중 (ALTER + 쿼리 1곳 수정)
- **운영 복잡성**: 낮음
- **확장성**: **상**

### C. 정규화 조인 테이블

**동작 방식** — `news_article_symbols(symbol, published_at DESC, article_id)`를
만들고 인덱스를 건다.

- **장점**: 표준적이고 이식성이 좋다(MySQL 버전 의존 없음).
  `(symbol, published_at DESC)` 인덱스가 **정렬까지 커버**하므로
  B의 filesort 단점이 없다 — 흔한 종목도 빨라진다.
  종목별 기사 수 집계 같은 **다른 질의도 열린다.**
- **단점**:
  - **쓰기 경로가 하나 늘고 동기화 위험이 생긴다.** `symbols_json`을 갱신하는
    모든 지점(ingest, `news_store_retag.go`의 재태깅 배치)이 두 저장소를
    **한 트랜잭션에서** 갱신해야 한다. 어긋나면 조용히 틀린 결과가 나온다.
  - 백필 마이그레이션이 필요하다(81k행 × 평균 심볼 수).
  - 진실의 원천이 둘이 된다 — 정합성 점검 배치가 추가로 필요.
- **성능 효과**: 매칭 0건 **1ms 미만**, 흔한 종목도 **개선**(정렬 커버).
- **비용 변화**: 새 테이블 + 인덱스(대략 기사수 × 평균심볼수 × ~40바이트).
  ingest 쓰기 2배 경로. DB 읽기 대폭 감소.
- **데이터 신선도**: **동기화 실패 시 어긋난다** — 이 안의 핵심 위험.
- **장애 가능성**: **중** (동기화 누락, 부분 커밋)
- **구현 난이도**: **상** (스키마 + 백필 + 쓰기 경로 2곳 + 정합성 배치)
- **운영 복잡성**: 중~상
- **확장성**: **최상**

### D. FULLTEXT 인덱스 (텍스트 검색)

**동작 방식** — `headline, summary, headline_ko, summary_ko`에 FULLTEXT를 걸고
`MATCH ... AGAINST`로 바꾼다. **한국어는 ngram 파서가 필수**다
(`WITH PARSER ngram`, `ngram_token_size=2`).

- **장점**: 검색이 인덱스를 탄다. 매칭 0건이 상수 시간.
  관련도 정렬(relevance)도 얻는다.
- **단점**:
  - ngram 인덱스는 **크다** — TEXT 컬럼 4개에 걸면 인덱스가 본문 크기에
    육박할 수 있다. 현재 news 테이블 크기를 먼저 재야 한다.
  - **부분 문자열 검색 의미가 달라진다.** 현재 `LIKE '%반도체%'`는 어디든
    걸리지만 ngram은 토큰 경계에 따라 결과가 달라진다 — **검색 결과가 바뀐다**.
    이건 성능이 아니라 **제품 동작 변경**이다.
  - ingest 쓰기 비용이 눈에 띄게 증가한다.
- **성능 효과**: `q=zzqqxx` **320ms → 1ms 미만**.
- **비용 변화**: 디스크·버퍼풀 **상당히 증가**(4GB 버퍼풀에 부담).
  ingest 쓰기 증가.
- **데이터 신선도**: 무영향.
- **장애 가능성**: 중 (버퍼풀 압박, P2-12의 1.27GB 백업 테이블과 겹침)
- **구현 난이도**: 중~상
- **운영 복잡성**: 중
- **확장성**: 중 (수백만 건부터는 외부 검색엔진이 낫다)

### E. 외부 검색엔진 (Meilisearch / OpenSearch)

**동작 방식** — 검색을 DB에서 떼어낸다.

- **장점**: 검색 품질(오타 보정, 형태소, 랭킹)이 근본적으로 좋아진다.
  DB 부하가 0이 된다. 기사 수백만 건까지 확장.
- **단점**: **인프라가 하나 는다.** 색인 파이프라인·재색인·정합성이 새 운영 부담.
  현재 기사 81k에는 **명백한 과잉**이다.
- **성능 효과**: 검색 상수 시간, DB 무부하.
- **비용 변화**: 컨테이너 + Memory(수백 MB~) 추가.
- **데이터 신선도**: 색인 지연(초 단위)이 생긴다.
- **장애 가능성**: 중 (새 의존성)
- **구현 난이도**: 상
- **운영 복잡성**: 상
- **확장성**: 최상
- **결론**: 지금 규모에는 부적합. **기사 100만 건 또는 검색이 핵심 기능이 될 때** 재검토.

### F. 종목별 뉴스를 사전 계산

**동작 방식** — 종목 상세가 필요로 하는 것은 **최근 N건**뿐이다.
`news_symbol_recent(symbol, article_ids_json, updated_at)` 같은 요약 표를
ingest 시점에 갱신한다.

- **장점**: 종목 상세 뉴스가 **PK 조회 1회**가 된다. 가장 빠르다.
- **단점**: 필터 조합(source, sort)을 못 받는다 — **유연성을 잃는다.**
  ingest마다 갱신 대상이 늘어난다.
- **성능 효과**: 종목 상세 뉴스 최상. 일반 검색은 무해결.
- **구현 난이도**: 중
- **확장성**: 중 (특수 목적)
- **결론**: B/C를 대체하지 않는 **보완재**. 종목 상세가 병목으로 남으면 검토.

## 추천안

**단기 patch (0.5일)** — `A` (negative caching)
: P1-4의 캐시 개편과 **같은 작업으로 묶어서** 넣는다. 스키마를 안 건드리고
  penetration 벡터를 즉시 막는다. TTL은 짧게(30~60초).

**장기 architecture** — **종목 필터는 `B`(multi-valued index),
텍스트 검색은 당분간 `A`로 버티고 필요 시 `D`**
: 두 조건을 **분리해서** 다루는 것이 핵심이다.

  - **종목 필터**는 `B`를 고른다. `C`(조인 테이블)가 성능은 조금 더 좋지만,
    **감사 문서 스스로 지적한 위험**(재태깅 배치와의 동기화 어긋남)이
    `B`에서는 **존재하지 않는다.** 쓰기 경로를 안 건드리는 것이 이 시스템의
    현 상태에서 훨씬 값지다. 같은 값을 두 곳에 쓰는 구조는
    "언젠가 어긋난다"가 기본값이고, 그때 조용히 틀린 뉴스가 나간다.
    ALTER 하나로 되돌릴 수도 있다(`DROP INDEX`).
  - **텍스트 검색**은 지금 손대지 않는다. `D`(ngram FULLTEXT)는
    **검색 결과 자체가 달라지는 제품 변경**이고, 인덱스가 버퍼풀을 크게 먹는다.
    검색 트래픽 비중을 먼저 측정해서, 낮으면 `A`로 충분하다.

  `C`로 갈 조건: 기사가 100만 건을 넘거나, 종목별 집계 질의가 여러 개
  필요해질 때. 그때는 `B`에서 `C`로 옮기는 것이 처음부터 `C`로 가는 것보다
  안전하다(쿼리만 바꾸면 되고 `B`를 롤백 경로로 남길 수 있다).

## 제품/운영 결정 필요 여부

1. **`ALTER TABLE news_articles ADD INDEX`를 돌릴 수 있는 시간대** —
   81k행이면 짧지만 온라인 DDL 중 락 구간이 있다. 저트래픽 시간 확보 필요.
2. **negative caching TTL** — "기사가 하나도 없던 종목에 첫 기사가 떴을 때
   몇 초 늦게 보여도 되는가". 권장 60초.
3. **검색(`?q=`) 트래픽 비중** — 측정 후 결정. 낮으면 D를 안 해도 된다.
4. **검색 결과 의미 변경 허용 여부** — D를 채택하면 `LIKE` 부분일치가
   ngram 토큰 매칭으로 바뀐다. 제품이 이를 받아들일 수 있는가.
5. **버퍼풀 여유** — D는 인덱스가 크다. P2-12의 1.27GB 백업 테이블 드롭이
   선행돼야 여유가 생긴다.

## 구현 계획

**Phase 1 — 즉효 (0.5일, P1-4와 묶음)**
1. `symbols_json` 값 검증 스크립트 — 배열 원소가 전부 문자열인지, 최대 길이 확인.
2. 매칭 0건 결과에 negative caching (TTL 60초, 작은 LRU).
3. 검색·종목 필터의 요청 비중 로깅 (Phase 3 결정 근거).

**Phase 2 — 종목 필터 인덱스 (1일)**
4. `migrations/060_news_symbols_mv_index.sql` — multi-valued index 추가.
   (기존 `059_news_popular_index.sql`의 머리말 형식을 따를 것.)
5. `news_repo.go:409`의 `JSON_CONTAINS` → `MEMBER OF`로 교체.
6. **`EXPLAIN ANALYZE` 전후 비교 4종**:
   `symbol=005930`(흔함) / `symbol=999999`(없음) / 정렬 커버 / 인덱스 선택.
   흔한 종목이 회귀하면 인덱스 힌트 또는 롤백.
7. ingest 쓰기 지연 측정 (인덱스 추가로 인한 회귀 확인).
8. **벤치마크**: 감사의 실측표(298ms/67,558행)와 동일 조건 재측정.

**Phase 3 — 텍스트 검색 (조건부)**
9. Phase 1의 로깅으로 검색 비중 판단.
10. 비중이 높으면 ngram FULLTEXT를 **스테이징에서 먼저** — 인덱스 크기와
    결과 차이를 실측해 제품 결정에 올린다.

# P1-9. 커넥션 풀 총합이 서버 상한의 76%다

## 문제

- API `defaultMaxOpenConns = 50` (`mysql.go:19`)
- 워커 8개 × `MYSQL_MAX_OPEN_CONNS: "8"` = 64 (`docker-compose.yml`)
- 합계 **114 / `max_connections = 151`** (76%)
- 실측 `Max_used_connections = 34`, `Threads_connected = 19` — **실제로는 남는다.**
- **이미 한 번 터졌다** — `mysql.go:35` 주석: 2026-08-22 「Too many connections」로
  DB 전체 정지. 그래서 CLI 기본값을 4로 낮춘 상태다.
- `Aborted_connects = 267`.

**결과**: API를 2대로 늘리면 50+50+64 = **164 > 151** → 기동 즉시 고갈.
**현재 구성은 수평 확장이 원천 차단**돼 있다.

## 목표

1. 재배포·CLI 동시 실행에서 커넥션이 고갈되지 않게 한다.
2. API 인스턴스를 2~3대로 늘릴 여유를 만든다.
3. 풀을 줄일 때 **대기가 생기는지를 지표로 확인**하며 줄인다.

## 선택지

### A. 풀 크기를 실측 기반으로 재조정

**동작 방식** — `Max_used_connections = 34`가 관측값이므로 API 50은 과하다.
API 25 / 워커 4로 낮추면 25 + 8×4 = **57** (여유 94).

- **장점**: **설정 변경만.** 마이그레이션도 재기동 순서도 필요 없다.
  즉시 API 2~3대 여유가 생긴다. 비용 0.
- **단점**: 풀을 낮추면 **SSE 스트림·배경 폴러가 커넥션을 오래 잡는 구간**에서
  요청이 대기한다. 34는 "현재 트래픽에서의" 최대치이지 **피크 보장이 아니다** —
  실사용자가 늘면 부족해질 수 있다.
  워커 4는 배치가 병렬 쿼리를 쓰면 병목이 된다.
- **성능 효과**: 정상 시 무변화. 피크에서 대기 발생 가능.
- **비용 변화**: MySQL 메모리 사용 감소. 그 외 없음.
- **데이터 신선도**: 무영향.
- **장애 가능성**: **중** — 너무 낮추면 요청 대기가 타임아웃이 된다.
  `quantport_mysql_wait_total`(현재 0)을 보며 내려야 한다.
- **구현 난이도**: **하**
- **운영 복잡성**: 변화 없음
- **확장성**: 중 (인스턴스 2~3대까지)

### B. `max_connections` 상향

**동작 방식** — 151 → 300~500으로 올린다.

- **장점**: 가장 직접적. 현재 값을 하나도 안 건드려도 여유가 생긴다.
- **단점**: **메모리를 먹는다.** MySQL 커넥션당 기본 오버헤드에
  세션 버퍼(`sort_buffer_size`, `join_buffer_size`, `read_buffer_size` 등)가
  붙는다. 대략 커넥션당 0.5~1MB로 보면 500개 = **250~500MB**가
  **버퍼풀 4GB와 별도로** 필요하다. **호스트 RAM 여유를 먼저 확인해야 한다.**
  또한 커넥션이 많다고 처리량이 늘지 않는다 — InnoDB는 동시 실행 스레드가
  많아지면 오히려 느려진다(컨텍스트 스위칭·락 경합).
- **성능 효과**: 고갈 방지. 처리량은 개선 없음(오히려 과다 시 악화).
- **비용 변화**: **Memory 증가**(호스트 RAM).
- **데이터 신선도**: 무영향.
- **장애 가능성**: 중 (RAM 부족 시 OOM — 고갈보다 나쁜 실패)
- **구현 난이도**: 하 (MySQL 설정 + 재기동)
- **운영 복잡성**: 낮음
- **확장성**: 중 (선형으로 밀 수 있지만 상한이 있다)

### C. A + B + 대기 지표 (조합) ★

**동작 방식** — 풀을 실측 기반으로 낮추고(A), `max_connections`도 여유 있게
올리고(B), **커넥션 대기 시간·횟수를 지표로 노출**한다.
`sql.DB.Stats()`의 `WaitCount`/`WaitDuration`을 그대로 쓸 수 있다.

배분 규칙을 문서화한다:

```
api_pool  = floor((max_connections * 0.7 - worker_total - cli_reserve) / api_instances)
예) max_conn=300, workers=8*4=32, cli_reserve=20, api=2
    -> floor((210 - 32 - 20) / 2) = 79  (넉넉)
```

- **장점**: A의 위험(과소 설정)을 B가 받치고, 지표가 **다음 조정의 근거**가 된다.
  "왜 이 숫자인가"에 답할 수 있는 유일한 안이다.
  `cli_reserve`를 명시적으로 남겨 **2026-08-22의 사고를 구조적으로 재발 방지**한다.
- **단점**: 메트릭 배선이 필요하다. `max_connections` 변경에 MySQL 재기동.
- **성능 효과**: 고갈 방지 + 대기 가시화.
- **비용 변화**: B의 Memory 증가(단, A로 실사용이 줄어 실제 점유는 낮다).
- **데이터 신선도**: 무영향.
- **장애 가능성**: 낮음
- **구현 난이도**: 하~중
- **운영 복잡성**: 낮음
- **확장성**: 상

### D. 워커 프로세스 통합

**동작 방식** — 8개 워커 컨테이너를 **1개 프로세스 + 스케줄러**로 합친다.
커넥션 64 → 8~12로 줄어든다.

- **장점**: 커넥션·메모리·컨테이너가 대폭 준다. 배치 큐가 이미
  `HasPending`/`ClaimNext`(`SELECT ... FOR UPDATE`)로 원자적 클레임을 하므로
  **스케줄링 기반이 이미 있다.**
- **단점**: **실패 격리를 잃는다.** 지금은 워커 하나가 죽어도 나머지는 돈다.
  통합하면 한 배치의 패닉이 전부를 멈춘다(`safego`로 완화 가능하나 완전하지 않다).
  개별 워커의 리소스 상한(`x-worker-deploy`)을 따로 못 건다.
  리팩터링 범위가 크다.
- **성능 효과**: 커넥션 −52. CPU/Memory 절감.
- **비용 변화**: Memory 대폭 감소(컨테이너 7개 분).
- **데이터 신선도**: 무영향.
- **장애 가능성**: **중~상** (격리 상실)
- **구현 난이도**: 상
- **운영 복잡성**: 초기 상승, 이후 감소
- **확장성**: 중

### E. ProxySQL 등 커넥션 멀티플렉서

**동작 방식** — 앱과 DB 사이에 프록시를 두고 **커넥션을 다중화**한다.
앱 커넥션 1,000개가 DB 커넥션 50개를 공유한다.

- **장점**: **커넥션 수 문제를 근본적으로 없앤다.** 앱은 풀 크기를 마음껏
  잡아도 된다. 쿼리 라우팅·읽기 복제 분산으로 자연히 확장된다.
- **단점**: **인프라 컴포넌트가 하나 늘고 단일 장애점이 된다.**
  트랜잭션·`SELECT ... FOR UPDATE`·세션 변수·prepared statement가
  멀티플렉싱과 궁합이 나쁘다 — 이 코드베이스는 `ClaimNext`에서
  `FOR UPDATE`를 쓰므로 **멀티플렉싱을 꺼야 하는 구간**이 생긴다.
  설정·디버깅 난이도가 높다.
- **성능 효과**: 커넥션 제약 제거. 쿼리 지연은 프록시 홉만큼 소폭 증가.
- **비용 변화**: 컨테이너 + Memory 추가.
- **데이터 신선도**: 무영향.
- **장애 가능성**: **중~상** (새 단일 장애점, 트랜잭션 오작동 여지)
- **구현 난이도**: 상
- **운영 복잡성**: **상**
- **확장성**: 최상
- **결론**: 현재 규모(피크 34 커넥션)에는 **명백한 과잉.**
  API 인스턴스가 5대 이상 되거나 읽기 복제가 필요해질 때 재검토.

### F. 폴러 워커 분리 (P0-1 G와 동일)

**동작 방식** — API의 배경 폴러를 워커로 옮긴다.

- **평가**: P1-9 관점에서 **API 풀을 낮출 수 있게 만드는 선행 작업**이다.
  주석(`mysql.go:15`)이 "API가 열댓 개 배경 폴러를 돌려서 작은 풀은
  전부를 직렬화한다"고 적어 놓았는데, **그 폴러를 옮기면 그 이유가 사라진다.**
  A와 시너지가 크다.
- **결론**: P0-1의 Phase 4와 **같은 작업.** 중복 투자가 아니다.

## 추천안

> **[2026-08-24 확정으로 개정됨]** 하드웨어가 **1 ECPU / 8 GiB**로 확인되면서
> 아래 `B`(`max_connections` 상향)를 **철회한다.** 원문은 이력을 위해 남긴다.

**단기 patch (0.5일)** — `A` + 지표 (**`B` 제외**)
: 1 ECPU에서는 커넥션을 늘려도 처리량이 늘지 않는다. 동시에 의미 있게 실행되는
  쿼리가 2~4개인데 커넥션 상한을 300으로 올리면 **고갈을 늦출 뿐 아무것도
  빨라지지 않고**, 8 GiB 중 커넥션 오버헤드만 커진다. `max_connections = 151`은
  이 스펙에 오히려 **이미 과하다.**

  해야 할 것은 반대다 — **총 배정을 대폭 줄여 상한 근처에 가지 않게** 만든다.

  1. `sql.DB.Stats()`의 `WaitCount`/`WaitDuration`/`InUse`를 `/health`에 노출한다.
     **이것 없이는 아래 값을 내리면 안 된다.**
  2. 배정을 다시 짠다:

     | | 현재 | 개정 권장 | 근거 |
     |---|---|---|---|
     | API | 50 | **16** | 1 ECPU. 실측 피크 34는 폴러 포함값이고, 폴러는 아래에서 분리된다 |
     | 폴러 컨테이너 | (API에 포함) | **6** | 배치 upsert + `SELECT DISTINCT`뿐 |
     | 배치 워커 8개 | 8×8 = 64 | **8×3 = 24** | 대개 순차 쿼리. 별도 인스턴스로 이동 |
     | CLI 예비 | (없음) | **8** | 2026-08-22 사고 재발 방지를 **규칙으로** 고정 |
     | **합계** | **114 / 151 (76%)** | **54 / 151 (36%)** | |

  3. `max_connections`는 **151 그대로 둔다.**
  4. 예비분과 배분 규칙을 `mysql.go` 주석과 `docker-compose.yml`에 문서화한다.

  **주의**: API 16으로 내리기 전에 **SSE 스트림이 DB 커넥션을 오래 잡는지**
  확인해야 한다. 잡는다면 스트림 수만큼 별도 여유가 필요하다 — 이건 아직 안 봤다.

  **덤**: 이 스펙에서 가장 값싼 개선은 커넥션이 아니라 **P2-12의 백업 테이블
  1.27 GB 드롭**이다. 버퍼풀 4 GiB의 32%를 차지할 수 있는 크기이고,
  스토리지 처리량이 **29 MiB/s**라 버퍼풀에서 밀려나는 순간의 대가가 매우 크다.
  롤업 검증이 끝났다면 P1 우선순위로 올려야 한다.

**장기 architecture** — `F` (폴러 워커 분리) → `A`의 재조정 → 필요 시 `D`
: `F`가 들어가면 API는 순수 요청 처리 프로세스가 되고, 풀 크기를
  **동시 요청 수 × 요청당 커넥션**으로 정직하게 계산할 수 있다.
  그때 API 풀을 15~20까지 낮출 수 있고, 배분 공식대로 인스턴스 3~4대가 열린다.
  `D`(워커 통합)는 커넥션이 다시 부족해질 때의 다음 카드로 남긴다.
  `E`(ProxySQL)는 **지금 규모에서는 하지 않는다.**

### 왜 이 순서인가

`A`(풀 축소)만 하면 위험하다 — 34는 현재 트래픽의 피크이고 보장이 아니다.
`B`(상향)만 하면 근본이 안 바뀌고 메모리만 먹는다.
**지표 없이 둘 중 하나를 하는 것이 가장 나쁘다** — 대기가 생겨도 알 수 없고,
장애가 나면 원인을 못 찾는다. 그래서 `C`가 최소 단위다.

## 제품/운영 결정 필요 여부

1. **DB 호스트의 RAM 여유** — `max_connections` 상향폭을 정하는 유일한 근거.
   현재 버퍼풀 4GB + 커넥션당 ~0.5~1MB. **측정 필요.**
2. **목표 API 인스턴스 수** — 1대 유지인가, 2~3대인가.
   이 답이 P1-4의 Redis 이전(E)과 P0-1의 리더 락(E) 착수 여부를 함께 결정한다.
3. **CLI/배치용 예비 커넥션 수** — 권장 20. 동시에 돌릴 수 있는 CLI 수의 상한.
4. **허용 가능한 커넥션 대기 시간** — 이 값을 넘으면 풀을 다시 올린다는 기준.
   권장: p99 < 50ms.
5. **워커 통합(D) 시 실패 격리 상실을 받아들이는가** — 장기 카드의 전제.

## 구현 계획

1. **지표 먼저** — `sql.DB.Stats()`의 `WaitCount`·`WaitDuration`·`InUse`·`Idle`을
   `/health` 또는 메트릭 엔드포인트에 노출. API·워커 모두.
2. DB 호스트 RAM 여유 측정 (`free -h`, `docker stats`).
3. `max_connections` 상향 (RAM 확인 후 250~300), MySQL 재기동.
4. API 풀 50 → 30, 워커 8 → 6으로 조정.
5. **1주 관찰** — `WaitCount`가 0을 유지하는지. 0이 아니면 되돌린다.
6. 배분 공식과 `cli_reserve`를 `mysql.go` 주석과 `docker-compose.yml`에
   **함께** 문서화 (기존 주석 스타일을 따를 것).
7. **부하 테스트**: 재배포 시나리오(9개 프로세스 동시 기동) + CLI 3개 동시 실행에서
   `Aborted_connects`가 늘지 않는지 확인.
8. (P0-1 Phase 4와 함께) 폴러 워커 분리 후 API 풀 재조정 + 인스턴스 2대 실험.

## DDL 시간대 제안 (질문 4에 대한 답)

**권장: 매일 03:40 – 04:25 KST 사이. 목표 시작 04:00 KST.**

배치 시간표(`be/docs/BATCH_SCHEDULE.md`)에서 이 구간만 **예약된 잡이 하나도 없다**:

```
01:30 ─────── warnings_sync (전 종목, 약 2시간) ───────► ~03:30
                                                   03:40 ┃ 빈 구간 ┃ 04:25
04:30  data_retention (가벼움)
05:30  candle_rollup (DB 무거움)
06:00  earnings_overseas 전체 창
```

근거:

| 조건 | 04:00 KST |
|---|---|
| KRX | 마감 (09:00–15:30) |
| 국내 사용자 트래픽 | 최저 |
| 예약 배치 | **없음** (03:30 종료 ~ 04:30 시작 사이) |
| DB IOPS 경합 | 없음 — 29 MiB/s를 DDL이 독점 |
| 소요 예상 | 81k행 보조 인덱스 빌드 → **1분 내외** |

**주의 3가지:**

1. **뉴스 폴러가 이 테이블에 2분마다 쓴다.** `ALTER`는
   `ALGORITHM=INPLACE, LOCK=NONE`으로 DML을 허용하지만, **시작·종료 시점에
   메타데이터 락**을 잡고 열린 트랜잭션을 기다린다. 폴러 트랜잭션과 겹치면
   그 뒤 모든 쿼리가 락 뒤에 줄을 선다.
   → **DDL 동안 뉴스 폴러를 잠시 멈추는 것**이 가장 안전하다. 4분이면 끝난다.
2. **사전 검증이 필요하다.** multi-valued index는 배열 원소가 전부
   `CHAR(16)`으로 캐스팅 가능해야 만들어진다. `symbols_json`에 문자열이 아닌
   원소나 16자 초과 심볼이 하나라도 있으면 `ALTER`가 실패한다.
   → **전날 검증 스크립트를 먼저 돌린다**(구현 계획 Phase 1의 1번).
3. **미국장은 열려 있다**(겨울 기준 23:30–06:00 KST). 국내 서비스라 트래픽은
   최저지만 0은 아니다. `LOCK=NONE`이므로 읽기·쓰기는 계속된다.

**대안 창**: 04:35 – 05:25 KST (data_retention 종료 후 ~ candle_rollup 시작 전).
04:00을 놓쳤을 때 같은 날 재시도할 수 있는 구간이다.
